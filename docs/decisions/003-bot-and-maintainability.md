# 003：基础人机与适度封装

2026-10-01 建立，2026-10-02 更新。状态：平台座位／受限调度／恢复、SDK、独立模板和宝可梦完整策略均已实现；当前增加三档人机。具体形式由[决策004](004-phase02-game-spec-and-bot-file.md)采用独立 TS 默认，实际接入见[开发指南](../game-development/README.md)。

## 问题与采用范围

原始首版需求将 AI 玩家排除在外。用户现要求在游戏中添加电脑，能对全部游戏操作作简单决策，并独立维护电脑决策文件；同时要求开发注意面向对象的适度封装以优化可维护性。

因此基础 bot 纳入首版，新增游戏也需提供其逐选择策略；不以智能强度、胜率或联网大模型为目标。原“AI 玩家不纳入首版”条款由新要求替代，调试与纠错专项仍按既有后续规划处理。

工程上对有生命周期、依赖及不变量的能力适度封装，优先组合和明确接口；纯规则、计分与投影可保留纯函数，持久化仍采用普通数据。用户要求不等于全类化、深层继承或通用机器人平台。

## 理由与后果

- 电脑策略和规则执行分开，平台负责座位、授权、调度、校验、保存与恢复，具体游戏负责完整选择策略。bot 不取得额外秘密或调试权限，也不自动接管掉线真人。
- 新增独立文件、策略版本和恢复数据约定，需要补充 SDK／注册、模板、逐节点验证与人机混合整局；文件形式及逐选择上下文已有规格，正式签名在第四阶段接入。
- 第二阶段补规格与职责设计，第三至六阶段吸收实现／验证责任；已完成的第一阶段记录保持历史范围，不将新增要求计为既有成果。
- 维护时以职责和变化点审查封装，以实际行为回归证明改动；不按类或设计模式的数量评价可维护性。

具体行为和文件要求见 [人机规格](../reference/bot-players.md)，封装与依赖原则见 [工程结构](../reference/architecture.md#面向对象与适度封装)，B01 采用默认及逐节点覆盖见 [游戏人机规格](../games/pokemon-encounters/bot.md)。产品验收 AC-19 至 AC-23 已在首版交付时验证，历史证据见 [验收](../reference/acceptance.md)。

## 三档本地策略（2026-10-02 增补）

用户要求盒子提供“默认／豆包／绝悟”，分别简单决策、初步局势分析、全面分析当前优解。采用同一游戏策略入口的显式等级分发，保留基础档原有行为、标识与版本；平台只保存和传递等级，不参与游戏评分。高级策略独立拆分计算及记忆，使用本人安全投影和合法意图，不复用完整规则状态做全知搜索。名称作为本地等级，不引入云账号或外部模型依赖，符合正式离线聚会目标。

旧座位／快照缺省等级按默认级读取；高级记忆明确校验、随 checkpoint 回退。级别只能在准备大厅由房主设置，进行中禁止切换，以免恢复或旧任务发生策略漂移。模板等未声明多档的游戏只能默认级，不能悄悄接受高级名称却运行原策略。策略智能以场景和计算目标界定，不因暗牌未知而承诺全局最优或固定胜率；具体方法见 [首版人机](../games/pokemon-encounters/bot.md)。

## 人机等待与测试加速（1.4.0 增补）

用户要求普通聚会时人机给出可感知的思考时间，测试快速完成。采用服务端运行模式控制调度、前端关闭测试装饰表现，避免 UI 计时伪造提交或测试走另一套规则。普通启动强制 `play`，高级别等待略长；隐蔽房主快捷入口可以切换当前模式，手机或 public 不能改。设置和调度取消使用原有事务与修订流程，失败保持原值；模式不回退进游戏 checkpoint，不消耗规则／策略 RNG。测试不能扩大信息权限、绕过动作验证或自动接管真人。明确入口与数值见 [通用规格](../reference/phase-02-platform-spec.md#实际游玩与测试模式140)。
