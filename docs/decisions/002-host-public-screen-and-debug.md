# 002：公共大屏兼房主管理与调试模式

2026-10-01。状态：第三阶段已实现正式公共主机兼房主管理；跨游戏调试与纠错目标已写入需求，后续独立规划，尚未实现。

## 问题与依据

此前需求基线与工程基础把公共屏、手机和房主管理作为三个界面入口。用户在第二阶段规则确认中明确要求“房主管理界面等于公共大屏”，并要求房主界面增加调试模式，可查看更多信息及执行额外操作和修改。按用户最新指示调整后续产品设计，保留第一阶段既有工程验证结果。

## 已采用选择

- 桌面公共大屏兼房主管理，在同一界面呈现对局和房主操作；手机继续承载本人游戏动作及授权信息。
- 用户所说主机展开全部弃牌，归属该合并桌面界面；手机普通视图仍只显示弃牌堆顶。
- 房主界面增加显式调试模式；用户随后明确尽可能覆盖盒子内所有游戏，支持游玩中纠错及撤回／恢复。长期目标统一在[需求第 6.5 节](../requirements/TableMax_需求文档_v1.0.md#65-跨游戏调试与纠错后续独立规划)，详细字段、动作及显示范围留待专项定义。
- 服务端继续校验普通管理动作和玩家动作的身份；界面合并采用同一视觉表面，身份与动作授权按服务端权限执行。

## 未确定范围

用户要求调试另行规划，本轮不继续逐项追问调试权限。查看暗牌、牌库／随机状态，改牌、牌序、分数或阶段，以及是否直接投屏，均为专项待定义项。状态结构、撤回／恢复、历史、待处理选择和退出调试后继续游玩的详细语义在专项补齐；普通游戏的既有恢复要求继续执行。

普通模式仍按规则投影秘密信息；调试模式的例外字段单列。2026-10-02 用户变更：电脑房主仅为管理员，不参赛、不取得玩家座位；手机使用独立普通玩家身份。

## 落地与交接

正式主机在同一牌桌承载公共游戏信息与按需展开的房主管理。`/host`、只读 `/public` 和本人 `/player` 是盒子入口，各自的 `/game` 子路由承载独立牌桌；游戏投影依据凭证选择，管理不授予额外秘密。通用原型保留旧三角色对照，首版原型也已合并主机。调试能力尚未实现；历史三入口检查与截图继续保留。

## 盒子与游戏分开（2026-10-01 增补）

用户在首版完成后要求盒子与游戏独立页面，电脑和手机的游戏尽量全屏，简化非必要环节，并让视觉、动效和结构更成熟。已采用独立路由与持续会话：盒子负责加入、准备和邀请，开局同步自动进入牌桌；返回盒子或前进后退只切换页面，不暂停、不退座、不创建新游戏。刷新游戏子路由仍能读到服务端授权状态。

牌桌保留紧凑工具栏、游戏场地与必要反馈，房主管理、帮助和历史进入菜单，对手场地在手机按需查看。直接取牌、弃牌、放弃能力及关闭查看省去二次确认；卡位选择仍使用明确动作确认，避免一触即改变位置。破坏性管理操作继续确认。理由是让用户操作桌游组件，并保持提交、秘密权限和恢复边界。当前落地为 1.0.1；游戏规则／状态／策略版本不变，旧存档继续使用原兼容检查。详细行为维护在 [通用规格](../reference/phase-02-platform-spec.md#盒子与独立牌桌) 与 [游戏交互](../games/pokemon-encounters/interaction.md)。

第二阶段记录要求，第三、四阶段已实现合并界面、真实授权、可靠动作与恢复，并演进协议／SDK，详见[决策005](005-platform-authority-and-recovery.md)。调试专项日期与实施阶段未定，按[任务索引后续范围](../tasks/README.md#后续范围)另行规划。调试模式最终需另列验证场景，旧三入口走查不证明其已实现。

本决策更新 [001 工程基础](001-engineering-foundation.md) 的后续产品界面划分；独立服务、服务端权威、身份连接不回退、本地资源及前端工程方向继续沿用。实际行为规格集中在[通用交互与交接规格](../reference/phase-02-platform-spec.md#公共大屏兼房主管理与调试模式)。

## 单牌桌与管理员身份（2026-10-02 变更）

程序启动即提供唯一牌桌，盒子不要求创建或选择房间。房主电脑承担管理和公开显示，不参加游戏；移除 hostToken 加入参数和参赛入口，首局第一位由服务随机选取。旧存档的 hostSeat 只为兼容读取保留，不再影响新局初始化；已经存在的普通玩家座位和当前对局不删改。内部 RoomCoordinator／存档标识仍承担动作串行、身份和恢复职责，无需为文案变化重命名协议。

此变更依据用户最新指示，替代旧房主参赛及首位优先方案；普通玩家仍无法执行管理动作。实现与验证见当前需求 AC-10、服务接口检查、规则随机重放与身份测试。历史阶段验收不倒改。
