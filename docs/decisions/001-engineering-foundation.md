# 001：工程基础技术方向

状态：已采用。技术方向、版本、进程组织、游戏目录组织和工程配置已落地，开发运行时与本机便携 ZIP 解压运行验证通过；正式产品验收仍待后续阶段。

历史采用记录：本页保存第一阶段的选择和证据。2026-10-03 用户授权的 [决策 008](008-small-native-desktop.md) 已替代桌面包装、独立服务启动与桌面验证工具部分；当前采用 net48／WinForms、共享 WebView2 和包内 Node，按新体积要求重新验收。本页 Electron／utilityProcess／electron-builder 表述属于原方案，其余平台与前端选择继续沿用。

## 问题与依据

TableMax 需要在用户本机 Windows 11 上提供便携桌面程序、本地局域网服务与手机网页。用户通过阶段选项确认：开发和维护省心优先，可以接受较大的程序包；前端优先考虑 AI 协作开发质量。

本文记录第一阶段当时采用的方向。产品要求仍以 [需求基线](../requirements/TableMax_需求文档_v1.0.md) 和用户最新指示为准，当前交付以 [验收记录](../reference/acceptance.md) 为准。

## 已采用方向

| 事项             | 采用方向                                               | 理由与边界                                                                                                                           |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 目标系统         | 用户本机 Windows 11 x64                                | 依据用户最新指示缩小覆盖范围；不承诺其他 Windows 版本或架构                                                                          |
| 语言与前端       | TypeScript、React、Vite                                | 用户授权按 AI 协作质量选择。采用 TSX、共享类型与统一组件约定属于项目工程判断，不声称已有 React 的 AI 生成质量普遍优于 Vue 的证据     |
| 桌面包装         | Electron                                               | 接受较大包体以携带桌面运行时；桌面主进程管理窗口与生命周期，启动独立服务进程                                                         |
| 本地 HTTP 服务   | Node.js、Fastify                                       | 承载构建后的网页、本地资源和平台接口；正式运行不使用 Vite 开发服务                                                                   |
| 实时通信         | Socket.IO                                              | 提供通信、确认和重连基础；动作去重、权威状态同步和回退分支隔离仍属于平台机制                                                         |
| 数据校验         | Zod                                                    | 校验外部消息等运行时数据；TypeScript 类型不能代替运行时校验                                                                          |
| 存档             | SQLite，使用 `node:sqlite` 的 `DatabaseSync`           | 基础绑定集中在服务适配器；开发 Node 22.14.0 中为实验 API，采用版本锁定与最小兼容验证，不引入需 Electron ABI 重编译的 npm SQLite 绑定 |
| 工程管理         | pnpm workspace                                         | 采用 `apps/`、`packages/`、`games/` 划分应用、共享模块与游戏；只建立当前实际需要的工程目录                                           |
| 验证工具         | Vitest、Playwright                                     | Vitest 验证数据库／HTTP，Playwright Electron API 验证真实桌面与三个网页入口；本阶段只验证工程基础，不提前实现业务验收                |
| 网页入口         | 一个网页工程，分开公共屏、手机端和房主管理的入口与布局 | 共享组件与构建配置以减少维护；路由和界面可见性不承担授权，服务端独立校验身份与权限                                                   |
| 运行数据         | Windows 当前用户的本地应用数据目录                     | 存档和日志与程序包分离；实现时解析系统目录并放入 TableMax 专用子目录，不硬编码用户路径，不把目录放在仓库中                           |
| 游戏目录         | 每款游戏集中在 `games/<游戏标识>/`                     | 内部分开规则、公共屏 UI、手机 UI、资源和验证；规则入口与客户端入口分离，禁止客户端导入服务端秘密状态或服务依赖                       |
| 代码检查与编辑器 | TypeScript strict、ESLint、Prettier；保存时格式化      | 使用项目固定工具与配置；不修改其他项目的全局开发环境                                                                                 |

## 已确认的运行边界

桌面主进程负责启动和停止独立服务进程、窗口管理及桌面生命周期。服务进程负责 HTTP、实时通信与数据库访问，构建后的网页和本地资源由服务提供。公共屏与手机通过服务端取得各自获授权的视图。

独立服务采用 Electron 自带的 `utilityProcess`。最小工程已验证进程通信、就绪确认、优雅关闭及 SQLite 集成，并通过进程指标确认服务确实拥有独立进程。异常退出和启动超时有明确处理入口。独立进程不是保证服务永不崩溃，也不意味着游戏存档或恢复机制已经实现。

桌面程序整体退出时协调停止服务；服务不脱离桌面程序成为系统后台服务。公共屏窗口与游戏服务的生命周期分开，关闭公共屏不能删除对局。完整业务行为在后续平台阶段实现。

2026-10-01 新增人机与适度面向对象封装见 [决策 003](003-bot-and-maintainability.md)。这是进行中及后续开发约定的扩充，不表示第一阶段已验证电脑策略、调度或封装后的业务行为。

## 后果与未解决项

- 需求中的 Vue 建议由本次 React 方向替代；需求原件保留，采用选择以本决策为准。游戏规则逻辑继续独立于前端框架。
- 网页工程需要明确区分角色入口、组件与状态，禁止将完整秘密状态发送给客户端。
- 程序包可独立替换，但搬移程序目录不会自动搬移存档；后续使用说明需告知实际数据位置。
- 独立服务增加进程通信与退出协调工作，用于将窗口管理与服务职责分开；每次运行时或数据库适配升级需复验两个运行时和打包产物。
- 打包使用解压运行 ZIP，不在本阶段引入安装器、系统服务、自动升级或签名发布流程；正式无开发环境电脑验收归第六阶段。
