# 005：真实平台授权与可靠恢复

2026-10-01，第三、四阶段采用并实现。需求依据：[平台交互](../reference/phase-02-platform-spec.md)、[人机规格](../reference/bot-players.md)、[逐决策恢复](../games/pokemon-encounters/information-and-decisions.md)。

公共主机兼管理，游戏信息保持 public 投影。服务启动时生成独立房主随机凭证，通过父进程消息交给桌面窗口，URL fragment 初始化后立即移除；凭证不进入二维码、health、日志或普通客户端消息。手机使用独立随机凭证，存档仅保存 SHA-256 摘要；换绑撤销旧身份，通过两分钟的一次性绑定码恢复原座位。房主身份每次服务启动更新，玩家身份跨正常重启保留。

平台核心用单房间队列处理所有游戏、生命周期、管理和身份变更；游戏选择在副本中执行。SQLite 最新记录与修订 journal 同事务写入，成功后才交换权威状态并发送确认。实例、分支、修订和决策绑定意图；相同编号／相同内容返回已有 ACK，改写内容拒绝，旧分支即使曾成功也拒绝。保存失败不更新内存、历史或随机数据。

游戏与策略的 before 数据保存在有效 checkpoint 链。回退截断后续有效链、增加分支和修订，保持当前身份，且先暂停。重启先校验存档与全部历史／策略版本，已进行对局恢复为暂停并分配新分支；不兼容或损坏不静默新建，原文件保留。追加 journal 保留已撤销分支和上一实例的审计数据，但网页不能查询完整记录。

bot 策略在正式服务的独立 Worker 执行，输入只有本人授权投影、合法意图、本人记忆及策略随机；350ms 步间隔保证管理可响应，2s 超时／取消终止 Worker。它走同一队列和事务，不代掉线真人。规则与策略随机分别保存，迟到结果再校验；策略版本不兼容拒绝恢复，不偷偷替换。

这样将生命周期职责收敛在 RoomCoordinator、BotScheduler、WorkerBotExecutor 和 SqliteSaveRepository，状态、投影、计分与简单策略仍是普通数据／纯函数。存档校验独立维护，平台核心不依赖具体游戏、数据库或 Socket.IO。后果是策略替换须重建注册入口，历史保存会随对局增大；首版不引入热加载、历史压缩或多房间体系。

实际入口、版本、操作与验证见 [工程结构](../reference/architecture.md)、[开发环境](../reference/development.md) 和 [游戏接入指南](../game-development/README.md)。模板证明基础能力，首版完整游戏与实机产品验收仍属第五、六阶段。

## 加入确认与原班续局（2026-10-02）

1.2.0 将可靠确认扩展至 HTTP 加入／换绑。只在内存缓存回复无法跨崩溃恢复；直接存明文凭证违背身份存储边界。因此手机先生成并保存 256 位请求密钥，服务只存其摘要、原内容指纹和以该密钥加密的随机玩家凭证（AES-256-GCM），与座位摘要同事务写入。最多保留 128 条有效回复，24 小时恢复窗口；密钥冲突、过期及已经撤销的凭证拒绝恢复。原有无请求密钥的开发调用仍兼容，新 UI 始终使用请求密钥。公开投影不包含密钥、回复、绑定或身份摘要。

换绑码摘要和期限也由存档保存，消耗与新凭证及回复同事务提交；保存失败可安全重试，已完成兑换不因回复丢失而再次消耗码。存档格式仍为 1，通过可选字段接续旧存档，不改游戏规则／状态／策略版本；网络契约增加确认和历史上下文，protocolVersion 为 3。

“再玩一局”与“清空牌桌”分为独立房主意图。前者仅清空游戏进度，保留有绑定的真人及电脑配置，让朋友重新准备；后者明确撤销全部身份。两者创建新实例并保留转换 ACK，丢失转换确认时重复请求不会二次创建；旧游戏动作仍因实例不同被拒绝。过去实例保留在事务 journal，游戏回退不跨实例。
