### 安装范围与框架推荐

**推荐单用户安装。**平台由一台 Windows 主机运行，朋友通过浏览器加入，并不需要为这台电脑的全部 Windows 账户安装共享服务。全机安装虽更接近传统 Program Files 布局，却要求可写数据根分离、管理员提升、公共快捷方式、跨会话运行保护和全机卸载登记，扩大首版验证面。首版不提供单用户／全机双模式切换。

Inno Setup 的 `PrivilegesRequired=lowest` 不主动请求提升、采用非管理员安装；产品登记归 HKCU，快捷方式归当前用户。运行程序保持当前 asInvoker，不增加开机自启、系统服务、文件关联或防火墙规则。用户手动以其他管理员账户运行安装器时不能假装仍属于原用户安装，应拒绝或明确返回正确用户上下文；运行组件的官方安装可能有独立权限提示，不能把安装器不提升误写成所有依赖都无需提升。[安装权限](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm)、[安装范围](https://jrsoftware.org/ishelp/topic_admininstallmode.htm)

**推荐 Inno Setup，不自研完整向导和卸载器。**WiX／MSI 的组件与升级管理更适合企业部署，本项目暂没有此需求；全自研需要长期维护登记、快捷方式、权限和失败删除。Inno 可处理系统集成，项目负责动作排空、精确模块保全、持久更新状态和健康确认，不能把这些职责交给框架默认文件覆盖。只采用完整安装和升级，不增加下载游戏的安装类型。

框架版本在阶段 1 按官方完整发行、许可证和哈希锁定于项目工具缓存；本轮不安装编译器。官方当前列出稳定 7.1.0，可作为评估候选，不因推荐而全局升级工具。个人朋友项目与未来商业使用的许可背景需按实际用途核对；不在本轮采购。[官方发行](https://jrsoftware.org/)、[许可说明](https://jrsoftware.org/isinfo.php)

默认安装位置为 **installer 当前所在目录本身**，对应 Inno 的 `{src}`；不自动追加一层 TableMax，不改为 LocalAppData 或根据所在盘猜测位置。首次始终显示该实际路径并允许用户修改；原安装升级使用已核验的原路径，不因新版 installer 下载到 updates 暂存目录而改变安装根。安装包必须原样显示用户指定提示：

> 不推荐安装在C盘，因为这是一个有良心的安装包

该提示是用户指定产品文案，不表示 C 盘禁止安装；用户在 C 盘选择有效可写目录仍可继续。目录不可写或指向磁盘根／系统受保护位置时明确提示重新选择，不静默回退到 C 盘或其他位置。`{src}` 是安装器来源目录，`{userprograms}` 是开始菜单目录，二者不能混用。[目录常量](https://jrsoftware.org/ishelp/topic_consts.htm)、[复用原安装目录](https://jrsoftware.org/ishelp/topic_setup_usepreviousappdir.htm)

默认来源目录可能包含其他下载文件，**不要求整个安装根为空**。只检查本产品将写入的入口、helper、卸载文件和 TableMax/app 等受管目标是否有不可覆盖的冲突；无关文件保留。首次默认创建当前用户开始菜单启动／卸载入口；桌面快捷方式默认勾选并可取消，升级保留选择。快捷方式固定指向根目录 TableMax.exe。

### 目录结构推荐

**保留现有三目录含义，不先引入 data 子目录。**令安装根为 I，配置根为 B=`I/TableMax`，运行目录为 A=`B/app`；默认数据根 D=B，自定义 D 继续按 `B/TableMax.config.json` 解析；游戏仓库 G=`B/games`。对应前文布局，只有 installer 管理入口和 app 的方式改变，现有 `TABLEMAX_BOX_DIRECTORY`、相对 `"."`、gamesDir 和缓存路径可以少改。

| 对象                                                 | 归属与升级规则                                                                                             | 卸载默认行为                                           |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `I/TableMax.exe`、`I/UpdateHelper.exe`、框架卸载文件 | 安装器管理的自有程序；版本／SHA 纳入安装清单                                                               | 删除已登记且归属有效的程序文件                         |
| `I/.tablemax-install.json`（建议名称）               | 记录固定产品 ID、安装实例 ID、安装范围、入口、配置根、构建身份及清单引用；不能单凭这个可写文件授权任意删除 | 清除本产品安装登记；保留数据所需路径信息按留存协议处理 |
| `B/app`                                              | installer 唯一负责完整替换；含包内 Node、原生壳、网页及预装载荷                                            | 按准确文件清单移除；不递归删除含未知文件的整个 B       |
| `B/TableMax.config.json`、默认 D 内配置／存档／缓存  | 用户运行数据；升级不覆盖，重装读取已有合法配置                                                             | 保留并显示位置                                         |
| `B/games`                                            | 服务核验的当前／历史模块；可替换 app 之外，不能靠修改 D 一起迁移                                           | 保留，尤其保护外置数据引用的旧局模块                   |
| `B/updates`                                          | 下载候选、恢复日志、临时 helper 的事务区域；准确记录阶段与文件归属                                         | 活动或未判定事务保留；完成事务按精确清单清理           |
| 外置 D、未知文件、旧便携原根                         | 不属于安装器可随意覆盖的程序范围                                                                           | 不自动删除或移动                                       |

稳定启动入口只定位 B／A、验证安装身份并启动内部原生壳，不继续携带并每次解压第二份完整载荷。内部游戏模块仍从本地签名预装内容修复，保留当前映射与旧局发行的服务职责；首版不改为网络修复，也不重构游戏目录或资源。

旧便携迁移推荐显式选原 B，默认复制核验并保留原件。原 D=B 时复制完整受保护运行数据与 G；原 D 为外置绝对路径时保留该指向并复制／核验配置根中的 G，不把外置目录自动搬进新安装根。只有用户明确选择搬迁才另做停机复制和切换。不能以新实例锁成功就认定原 Windows 会话已退出。

首版卸载建议只提供默认保留及保留位置提示；若需要「同时删除数据」，应作为显式附加动作单独核验，外置目录和未知／共享路径仍不自动递归删除。安装目录卸载后留有 TableMax 数据子目录是正常结果，不应为追求空文件夹删掉旧局。重新安装时识别留下的配置和数据，避免创建空库覆盖。

### 更新架构、时机与事务推荐

**推荐原生更新管理＋C# helper＋完整 installer。**盒子网页仅显示状态并提交受限请求；网络获取、下载路径和校验由原生层决定，不接受网页传入任意 URL、目标路径或 shell 命令。仅受管理本地主机管理员可应用更新，公共屏、玩家、frame 和远程浏览器均不得获得系统写入能力。

常驻更新服务、计划任务和单独 Node 更新守护进程都不是首版必要组件。小型 net48 helper 与现有技术栈一致；在替换开始前把受校验 helper 复制到本事务的暂存位置，从该位置运行，等待原入口／主机／服务／本程序 WebView2 退出。安装器可更新 I 中的 helper，临时 helper 完成交接后退出，下次启动再清理该已完成事务；不能边运行根目录 helper 边要求 installer 覆盖同一个 EXE。

首次安装和升级的文件复制由同一 installer 实现。手动运行 installer 升级也走同一停止、互斥、状态与确认流程；网页内更新只是准备可信候选并协调调用，不再实现第二套替换算法。

推荐首版主动点击「检查更新」，无启动自动检查或周期后台轮询；下载可取消并在当前程序运行时进行。下载完成只进入待应用状态，无进行中对局且用户点击后才进入关闭屏障；「暂停了对局」仍属于进行中，不能作为随时可升级的空闲条件。需继续对局时保留候选，结束后再应用。

事务推荐至少区分：准备／下载 → 完整校验 → 请求保存关闭 → 全部相关进程退出 → 安装切换 → 目标实例确认 → 已完成清理。安装互斥锁与数据实例锁分开；不以通用进程名结束其他程序。关闭失败、强制清理、尚未保存或无法排空均不能直接转到切换成功。

目标确认绑定具体安装实例、B／D、构建版本、payload／当前映射及实际服务健康，由已启动目标进程的受控通道取得；不能只扫描端口。超时仍须判断迁移是否开始，必要时停留在可诊断失败状态。恢复旧程序文件仅限尚未产生不兼容数据库变化的阶段；用户新产生的数据不得用旧快照覆盖。对数据库迁移采用原有备份／校验事务，并增补升级交接，不承诺框架的普通覆盖天然具备全应用原子回滚。

### 发布源与更新描述推荐

**推荐 GitHub 正式 stable Release，无自建更新服务器或 Pages。**保持两附件：完整 installer EXE 和 source ZIP。普通用户无需 GitHub token；公开附件名继续三位版本，签名描述记录四位构建与实际摘要。只有本轮明确授权发布后才改变线上程序类型。

在 Release 正文追加一个带固定标记的机器块，内容为签名 envelope；网页更新说明只显示人类说明，机器块独立解析和留证，不把它当 Markdown 执行。本轮推荐隐藏 HTML 注释中的 Base64 envelope，具体单块提取和限长规则需在阶段 1／4 用真实 GitHub API body 回归，不通过抓取浏览器排版结果取描述。

选择**预先可确定的资产定位字段**，签名包含固定仓库、releaseTag、assetName、长度和 SHA-256；不强制把 GitHub 上传后才分配的 asset ID 纳入签名。获取时从该仓库／标签的资产中找到唯一匹配者，记录实际 release／asset ID，校验名称、大小与流式摘要；未知或重复匹配拒绝。这样最终 EXE 字节固定后即可生成并审阅完整正文，减少上传与签名之间的循环依赖。

| 描述字段组（推荐）                                           | 作用                                                     |
| ------------------------------------------------------------ | -------------------------------------------------------- |
| schemaVersion、productId、channel、os、arch、installProtocol | 固定解释与目标边界，拒绝未知协议和不适用平台             |
| releaseVersion、buildVersion、releaseTag、repo、assetName    | 区分公开版本和精确构建，限定可信资产定位                 |
| bytes、sha256、payloadManifestSha256、currentMappingSha256   | 验证外层候选与新版实际运行身份；签名后不再改包           |
| keyId、可授权后继公钥的信息                                  | 选择内置信任根并支持提前轮换，不能由网络任意指定验签算法 |

推荐把需签名的 UTF-8 JSON 原始字节编码为 Base64，并对原始字节签名；C# 验签原字节后才严格解析。避免 Node 与 .NET 各自重新序列化后产生不同 canonical JSON。重复字段、多个机器块、超长输入、未知字段／协议、签名算法降级都应有明确拒绝策略；展示给用户的目标版本来自已验证描述。

发布顺序为：冻结并验收最终字节 → 生成签名描述及已审完整正文 → 经授权创建草稿并上传两附件 → 核验实际附件与描述一致 → 发布 → 复查正文、资产与签名映射。现有全文 notes 校验需针对已审最终正文调整输入，不发布后临时追加未审机器块。

下载只使用所选官方 HTTPS 资产与受控 GitHub 下载重定向链，不接受任意镜像或 HTTP 降级。当前历史 Release 没有这种描述时提示不支持可信在线更新，保留手动发布页入口；不得把缺签名降为仅用 GitHub digest 自动执行。断网不会影响已安装程序或游戏。

### 项目更新签名与 Windows 代码签名推荐

**两者分别设计。**项目更新签名证明候选来自内置受信发布密钥；Authenticode 向 Windows 证明文件发布者并支持系统策略。前者不会让 Windows 自动信任 EXE，后者也不代替安装范围、资产和精确版本校验。

| 路线                               | 适用性与代价                                                                            | 推荐结论                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 独立应用 RSA 签名描述              | Node 22 打包端签名、net48 原生端验签；仅增加很小的公钥／签名，无需新运行时和证书购买    | 首版自动更新的必要基础                                         |
| 复用现有游戏 Ed25519 密钥          | Node 可复用实现，但现有原生工程没有对应验签依赖；游戏密钥同时获准发布整个程序会扩大权限 | 不复用现有私钥；如选 Ed25519，应独立应用密钥并另评估原生验证库 |
| 原生依赖服务 Node 来验签           | 能调用已有 Node crypto，但服务关闭与 helper 更新交接更复杂                              | 原生应用更新认证不依赖服务 Job 存活                            |
| 可信 Authenticode                  | 能提供系统可识别的发布者，但需要证书／服务资格、成本和凭证管理                          | 明确不购买；免费产品签名不依赖它，保留 Windows 安全提示限制    |
| 自签 Authenticode 并让用户导入证书 | 不自动获得公开 Windows 信任，增加用户系统信任修改                                       | 不推荐作为朋友安装的常规步骤                                   |

RSA 方案推荐 RSA-3072、SHA-256 和固定 PKCS#1 v1.5 **签名填充**，不涉及 RSA 加密。它利用 .NET Framework 的现成 RSA API，避免为 net48 引入 Ed25519 验签库，也不引入不同提供者的 PSS 支持差异；具体公钥导入方式和 Node／C# 互操作留到阶段 4 的签名验证工作，以固定向量核验，不能从文档支持推定已通过。[Node 22.14.0 crypto](https://nodejs.org/download/release/v22.14.0/docs/api/crypto.html#cryptosignalgorithm-data-key-callback)、[.NET RSA API](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rsa.verifydata)

应用私钥与现有游戏私钥分离，只存在受保护签名环境／本地 secrets，并通过私有管道或受保护文件提供给签名工具；不进 Git、installer、命令行输出或测试日志。阶段0当时未生成密钥；2026-10-15已取得单独明确授权并生成，保管与恢复操作见[免费应用签名](../reference/release.md#完整安装器与免费应用签名2026-10-15)。程序只内置应用公钥及 keyId；正常轮换先用旧根签署包含后继公钥的可信完整程序，再在后续发行切换签名。首版不提供网络换根接口，未实测的轮换发行不标为已通过。密钥丢失／泄露不能靠网络提供一把新钥直接恢复信任。

用户明确选择现在及未来始终采用免费开发方案，不购买 Authenticode 证书或付费签名服务；应用更新使用独立项目公钥验证，绝不降为只校验未签名摘要。这不是 Windows 系统信任或安全策略兼容保证。Smart App Control 的可信证书要求、自签证书和 SmartScreen 信誉是不同问题；即使有可信证书也不能保证新 EXE 从不出现信誉提示，不建议关闭保护功能。[代码签名选择](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)、[SmartScreen 信誉](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)、[Smart App Control 签名](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control)

付费 Authenticode 路线已排除；不要求安装者导入自签根证书。若未来另行明确采用不付费的系统签名渠道，只对项目自有启动器、原生壳、helper、框架卸载器和 installer 按已审策略签名；官方 Node／WebView2 等第三方字节保持原发行，不重新签名破坏当前哈希来源。内部自有文件签名后再形成清单，最终 installer 签名及时间戳后再计算外层 SHA 和更新描述。更新协议从开始就允许记录 Authenticode 策略，后续增强不得让用户可随意绕过项目签名。

### 版本、安装身份与旧程序推荐

固定产品 ID 与每次安装生成的实例 ID 分开：前者供安装框架判断本产品升级／卸载，后者绑定安装根、用户和更新事务。产品 ID 不带公开版本；只支持当前用户一份受管理安装，旧便携 EXE 不自动变成已登记的安装实例。

| 情况                                                    | 推荐行为                                                                                                       |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 目标四位构建大于当前，公开标签和安装协议匹配            | 提供升级，下载前后均校验已签描述和字节                                                                         |
| 同三位公开版本、目标本地修订更高                        | 作为已发布修订提示，仍需经发布授权更新签名描述                                                                 |
| 同四位构建、相同 SHA                                    | 视为相同候选，不重复升级；损坏修复属于显式安装器修复流程                                                       |
| 同四位构建、不同 SHA                                    | 拒绝作为正常在线更新；冻结恢复／原载荷重封仍按现行规则不递增修订，但重签改变外层字节须明确受审重签／再发布策略 |
| 目标低于当前，或本地维护修订高于线上                    | 不自动降级；不把三位附件名当作本地修订 0 强制覆盖                                                              |
| 历史 Release 缺可信更新描述、安装协议更高、原局模块缺失 | 保留当前程序和数据，解释需手动处理的版本／协议；不降级信任或替换旧局规则                                       |

保存最高已接受的有效构建／描述身份，拒绝回退或同身份换字节；签名只证明来源，不保证服务器提供的是全世界最新版本。首版不建设在线密钥吊销或完整抗冻结协议，不能宣称能排除首次联网遇到旧但合法描述的情况。

旧局缺原发行时，原便携程序仍按原字节保留，用户可在明确的隔离／原数据路径下使用兼容旧完整程序；新安装器不因此提供一键降级或覆盖新数据库。初次从旧便携进入安装体系仍手动安装，线上切换不改原标签、原 SHA 映射或旧附件。
