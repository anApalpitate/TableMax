## 1. 产品定位与目标

TableMax 是供自己和朋友线下聚会使用的全数字桌游盒子。电脑运行局域网服务端，并将公共信息页面投屏到显示屏；玩家通过手机扫码打开网页，在个人界面查看信息和作出决策。

产品不依赖实体棋盘、卡牌或棋子。对应游戏需要的组件、操作、流程与结算全部由软件承载。电脑和手机连接在能够互相访问的局域网中，正式游玩不依赖互联网。

平台需要长期支持多种桌游。新增游戏通过编写代码模块实现，规则、公共屏、手机界面和资源均可独立开发，通常不需要修改平台核心。

### 1.1 成功标准

- 玩家无需安装手机 App，也无需注册云账号，即可加入并完成一局游戏。
- 电脑解压便携包后双击启动，无需预装 Node.js 或开发工具；2026-10-03 新采用的外壳需要系统 .NET Framework 4.8 与共享 WebView2，缺少 WebView2 时提示官方安装入口并允许取消，安装后可离线运行。
- 公共屏适合共同观看，手机适合个人操作；两端可以采用不同布局。
- 全局状态由服务端统一管理，秘密信息按身份隔离。
- 手机掉线或刷新后可以恢复原座位；电脑程序重启后可以恢复未结束的游戏。
- 房主可以选择历史决策点进行回退，并同步所有设备。
- 第一款游戏有完整玩法、可用 UI、本地美术资源和必要的操作反馈。
- 房主可以添加电脑玩家；基础 bot 能在无需人工代选的情况下完成所有规则要求的游戏决策，与真人混合完成整局。
- 平台提供游戏开发模板、接口文档与验证工具，方便后续借助开发助手增加游戏。

## 3. 首版范围与后续边界

### 3.1 首版必须完成

1. Windows 便携程序、服务生命周期管理、公共屏入口。
2. 游戏选择页与单房间大厅。
3. 局域网地址展示、加入二维码、昵称、座位、准备状态。
4. 玩家身份和房主权限管理。
5. 公共屏、手机玩家端、房主管理界面。
6. 服务端规则执行、合法动作校验、全局状态同步。
7. 决策点记录、房主回退、回退后重新决策。
8. 手机重连、刷新恢复、自动存档和程序重启恢复。
9. 《宝可梦奇遇》完整规则、完整对局与结算、专属 UI 和资源。
10. 游戏模块接口、示例模板、开发文档与必要的验证工具。
11. 本局公开操作记录、提示音和静音设置。
12. 电脑座位管理、覆盖全部游戏选择的基础 bot、独立电脑决策文件，以及人机混合对局的权限／回退／恢复验证。

### 3.2 后续目标，仅预留合理边界

- 《电力公司》经典德国地图游戏模块。

- 独立游戏插件包的安装、加载和兼容性检查。
- 多房间、多公共屏。
- 更丰富的游戏目录、规则变体、语言与资源替换。
- 面向盒子内所有游戏的调试与纠错能力，尽可能覆盖撤回与恢复；按第 6.5 节后续独立规划。

预留方式以清晰的房间标识、模块清单、接口版本、存档版本和资源命名空间为主，不为未来功能提前建设完整产品。

### 3.3 首版不纳入

- 多房间实际运行、互联网远程对战、云服务和云账号。
- 手机原生 App、微信小程序、完整 PWA 安装体验。
- 可视化规则编辑器、通用无代码桌游制作工具。
- 插件商店、任意第三方插件的安全隔离、运行中的插件热更新。
- 语音聊天、在线社交系统。
- 跨局排行榜、长期战绩系统和完整回放播放器。
- 《电力公司》的正式游戏实现、其他地图及扩展包。
- 背景音乐、复杂 3D 场景、依赖互联网的动态资源。

本局操作记录与内部恢复历史属于首版基础设施，不等同于面向用户的完整回放系统。

## 4. 角色与信息权限

| 角色                       | 可以查看                                                 | 可以操作                                               |
| -------------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 公共展示（合并主机界面内） | 游戏定义的公共信息、阶段、行动提示、公开结果、连接状态   | 展示与声音；管理操作按房主身份授权                     |
| 普通玩家                   | 自己有权查看的信息，以及游戏允许查看的公共信息           | 自己的合法动作、准备、信息查看                         |
| 房主（合并主机管理区）     | 游戏公共信息和管理信息；没有参赛座位，不查看玩家秘密信息 | 开局、暂停、恢复、座位管理、回退、结束                 |
| 电脑玩家（bot）            | 对应座位按正常游戏规则可见的信息及合法动作               | 为该电脑座位作出合法游戏决策；不授予房主管理或调试权限 |
| 服务端                     | 完整游戏状态与恢复所需数据                               | 规则执行、随机、校验、结算、持久化、调度电脑玩家       |

普通模式中，房主拥有管理权，不自动获得查看其他玩家秘密信息的权限。后续公共大屏兼房主管理，服务端分别验证管理与玩家授权。新增调试模式的查看与修改范围按第 6.5 节独立定义，尚未确定，当前不承诺任意改牌、改分或改身份面板。

公共二维码只授予加入资格，不包含房主凭证。每名玩家使用独立、不可猜测的身份凭证；房主权限与普通玩家身份分别管理。客户端自行提交的玩家编号不能直接作为身份依据。

## 5. 主要使用流程

### 5.1 启动、创建和加入

1. 用户解压便携包，双击 TableMax。
2. 程序启动本地服务，展示可用网卡地址、端口和运行状态。
3. 房主选择游戏，创建单房间；玩家人数限制由游戏模块提供。
4. 程序显示房间二维码，并提供公共屏入口。
5. 玩家先连接同一局域网，再扫码进入手机页面；二维码不代替 Wi-Fi 连接。
6. 玩家输入昵称、取得座位，阅读操作说明并准备。
7. 达到游戏人数和准备要求后，房主开局。

建议大厅支持重复昵称提示、满员提示、关闭新玩家加入和手动座位安排。开局后新连接默认只能恢复已有身份，不能随意创建新座位。是否允许中途替换玩家由游戏模块声明并由房主执行。

### 5.2 正常游戏

- 服务端发布公共视图与各玩家视图。
- 手机显示当前允许的操作、等待原因和提交状态。
- 玩家发送动作意图，服务端校验后执行，保存并确认结果。
- 程序自动完成规则要求的流程推进与结算。
- 公共屏展示行动者、阶段、公共结果及必要动画；手机同步自己的合法状态。
- 公共信息在两端可采用不同形式，例如大屏卡牌阵列与手机列表。
- 合法的秘密信息查看必须由规则明确授权；程序不能为了方便而暴露实体玩法中不可见的信息。

### 5.3 暂停与掉线

- 真人行动默认没有超时惩罚，也不自动替真人作决定；已配置的电脑座位由 bot 主动决策。
- 手机掉线后显示恢复状态；其座位和游戏数据保留。
- 当前行动真人掉线时，游戏保持等待；其他玩家和 bot 不得代提交，也不自动将该座位改为电脑。
- 房主可暂停或结束；暂停期间禁止提交推进游戏的动作。
- 普通掉线不必自动阻止其他规则允许的活动，例如查看公开信息。
- 切换 App、锁屏、刷新后，重新连接并同步当前状态，而不是依赖旧页面继续运行。

### 5.4 程序重启恢复

- 启动时发现未结束存档，向房主提供恢复入口。
- 恢复游戏版本、人数、座位、阶段、待处理决策与有效历史。
- 地址变化时生成新二维码；玩家凭证在有效期内仍可恢复原座位。
- 原浏览器身份丢失或更换手机时，建议通过房主确认重新绑定座位。
- 存档不兼容或损坏时保留原文件并说明原因，不静默重置游戏。

### 5.5 电脑玩家与基础决策

- 房主可在房间中添加或移除电脑座位，默认在开局前配置；人数按真人与电脑合计计算，遵守对应游戏的准备条件与人数范围。进行中加人或切换控制者须由游戏明确允许，不能借 bot 绕过规则人数或中途加入限制。
- 各端清楚标识电脑昵称、座位和当前行动状态；电脑无需手机扫码或云账号。是否已准备取决于对应游戏的准备流程，不能跳过初始选位、翻牌等规则操作。
- bot 必须覆盖全部需要玩家决定的节点，包括初始选择、常规动作、目标和参数、多步选择、被动触发的选择及其他玩家动作引起的响应。“默认”要求简单合法决策；“豆包”能够初步分析局势；“绝悟”全面评估自身合法可知信息，比较当前选择并给出当前优解。三档本地人机在盒子配置，详见下方 2026-10-02 增补。
- 电脑决策只能使用自身授权视图及可合法获得的信息，不能读取其他玩家秘密、未授权牌库顺序或平台完整 checkpoint。平台在本地服务调度策略，正式运行不依赖互联网。
- 电脑提交与真人共用身份绑定、阶段校验、动作队列、去重、事务保存和决策点机制；bot 只提出动作意图，不直接修改权威状态。
- 暂停、回退和结束时停止旧调度；回退、重连同步或重启后按最新分支重新计算。电脑的策略版本及恢复所需的随机／记忆数据纳入兼容检查与存档，旧分支动作不能再次生效。
- 策略异常、缺失或不能给出合法选择时显示具体问题并停止该次推进，保留对局供房主处理；不得无限重试、偷偷换策略或把未确认动作记为成功。
- 每款游戏必须独立保存电脑决策文件，与规则和计分实现分开维护，声明策略标识、版本与覆盖范围。独立 TS 文件为项目默认方案；正式接口由第四阶段设计接入，不承诺编辑器或运行外部脚本；详细规格、验证及阶段归属见 [人机规格](reference/bot-players.md)。

## 6. 游戏模块与高扩展性

### 6.1 模块职责

每款游戏是独立的开发单元，至少包含以下内容：

| 部分       | 必须提供的能力                                                         |
| ---------- | ---------------------------------------------------------------------- |
| 模块清单   | 游戏标识、名称、游戏版本、接口版本、存档版本、人数和入口               |
| 规则数据   | 卡牌、棋盘、角色、数值与版本依据                                       |
| 规则逻辑   | 初始化、合法动作、动作处理、阶段推进、结算、结束判断                   |
| 信息投影   | 公共屏视图、玩家视图、公开操作记录，严格遵守信息权限                   |
| 公共屏 UI  | 棋盘、公共组件、阶段、结果和展示反馈                                   |
| 手机 UI    | 私人信息、可执行操作、目标选择、公共信息查询                           |
| 决策点定义 | 决策边界、可回退标签、随机状态和恢复一致性检查                         |
| 资源       | 图片、卡背、图标、字体、提示音和资源来源清单                           |
| 规则说明   | 简体中文帮助、规则版本、已核实出处与争议项                             |
| 电脑决策   | 独立决策文件，基于授权信息覆盖全部合法选择；声明策略版本与恢复所需数据 |
| 验证内容   | 典型流程、边界规则、秘密信息隔离、回退和恢复、人机覆盖与完整对局样例   |

平台负责房间、身份、权限、通信、持久化、历史机制、客户端外壳和窗口管理；游戏负责具体玩法。平台不应以某一款游戏的卡牌、回合结构或棋盘形状作为通用模型。

### 6.2 接口设计要求

- 规则与电脑策略逻辑应独立于前端框架、Socket.IO、SQLite 和桌面运行时，可直接运行与验证；策略使用授权上下文，不能取得规则层的完整秘密状态。
- 游戏通过平台提供的上下文获取玩家、随机源、动作信息与阶段信息。
- 状态应可序列化；游戏、策略记忆和随机状态保存普通数据，不保存类实例、界面组件、数据库连接、函数或网络对象。
- 所有随机结果可恢复；建议使用服务端统一随机源，并保存随机状态或完整牌堆顺序。
- UI 不能直接修改规则状态或读取其他玩家视图。
- 游戏可以自由设计大屏和手机布局，不被统一表单系统限制。
- 通用 UI 组件和规则工具可复用，但使用它们不是强制要求。
- 核心只依赖抽象游戏契约；具体模块通过注册入口接入。
- 首版可以编译时注册源码模块；不要求运行时加载外部代码。
- 游戏标识、接口版本、存档版本与资源路径必须明确，避免未来独立打包时发生冲突。
- 新游戏采用已有契约时，主要改动应限于自己的模块及注册／构建清单；需要新通用能力时可以演进核心契约。

### 6.2.1 游戏解耦与增量交付增补

2026-10-05 用户确认将游戏与盒子的解耦、独立增量构建及分块组装打包纳入需求，后续明确授权实施并沿用 v1.0.4。本节维护已确认要求，当前实现与实际交付验证分别见下列工程与验收入口。

- 平台与宝可梦奇遇、现代艺术、电力公司分别形成独立构建单元；游戏块覆盖规则、授权投影 UI、人机策略及本地资源。各块通过版本化 SDK、协议及网页宿主接口协作，平台继续统一负责身份、权限、权威动作、保存恢复及调度。
- 支持只构建受影响的游戏或平台部分，复用经过完整性和兼容性校验的未变产物；共享契约、依赖或工具链变化必须使相关缓存失效。
- 最终将平台块和选定游戏块组装成完整运行目录，再生成单一便携 ZIP；不直接连接多个 ZIP 的字节。共享运行时只分发一份，正式运行所需资源全部本地提供。

- 本需求不自动实现游戏下载、安装、用户侧差分更新或外部插件；日常继续交付完整运行 ZIP 与逐文件清单，沿用当前版本规则。

现状和模块边界见 [工程结构](reference/architecture.md#独立构建与模块边界)，增量与组装方法见 [开发环境](reference/development.md#增量构建与分块组装需求)，完成范围见 [任务索引](tasks/README.md#游戏解耦与增量构建打包已实现)，实际同包结果见 [验收](reference/acceptance.md)。

## 7. 房主决策点回退

### 7.1 必须满足的行为

房主可以查看当前对局的有效决策点历史，并选择目标决策点恢复。不能仅提供“上一回合”按钮，不能因为已经揭示秘密信息而一律禁止房主回退。

“决策点”指游戏要求玩家作出一项规则意义上的选择时的状态边界，例如选择抽牌来源、选择替换目标、决定出价或购买资源。翻页、缩放地图、打开帮助等普通 UI 行为不属于决策点。

复合操作必须按游戏规则拆解。例如抽牌后选择目标属于不同阶段时，应分别记录边界；抽牌后的 checkpoint 应保留已抽到的牌，回退到抽牌前则应恢复原牌堆和随机状态。

每个会改变权威状态的合法决策都必须有可恢复边界。若规则中存在不可拆分的原子动作，插件需要说明它对应的决策点。游戏可以定义回退后的处理步骤，但不能任意取消已确认的房主回退权。

### 7.2 一次回退需要恢复的内容

- 玩家相关游戏数据、公共状态、秘密状态。
- 当前阶段、行动顺序、合法动作与待处理选择。
- 卡牌位置、牌堆顺序、弃牌堆、分数和胜负状态。
- 随机源状态与已经生成但尚未结算的随机结果。
- 该决策点之前的有效游戏历史。

玩家身份、房主授权、当前网络连接、网卡地址等平台运行信息不随游戏状态一同倒退。状态修订号／历史分支号必须递增，不能恢复成旧编号。

### 7.3 秘密信息与公平性

回退只能恢复程序状态，不能消除玩家已经看到的信息。游戏模块需要标记涉及抽牌、翻牌、秘密选择揭示等节点，房主选择时提示“已有信息可能被看见”，并说明恢复后是否会再次看到相同随机结果。

该提示用于说明后果，不要求所有玩家授权才允许回退。禁止为隐藏这项局限而悄悄重新洗牌或更换随机结果；若某款游戏确实需要特殊处理，必须在该游戏规格中明示。

### 7.4 同步、记录和持久化

- 回退时暂停动作处理，事务性保存恢复后的状态。
- 作废目标点之后的旧分支，保留必要的管理审计记录。
- 旧分支的待提交动作、重试和动画必须失效。
- 所有客户端收到新的完整授权视图，清除旧选择与提交状态。
- 回退事件要有公开提示，但不能在公共历史中列出被撤销动作涉及的秘密内容。
- 回退后的状态必须可继续游戏，也必须可在程序重启后恢复。
- 普通玩家只能访问公开历史；完整 checkpoint 仅用于服务端恢复，不下发给手机。

## 8. 状态、通信与存档

### 8.1 权威状态

服务端是唯一权威。手机提交动作意图，服务端校验身份、阶段、目标、参数与当前状态。客户端动画和本地选择不代表动作已生效。

建议按房间串行处理动作，确保同时提交、房主回退和自动结算不会交错破坏状态。 TypeScript 类型用于开发约束，外部消息仍需运行时校验。

### 8.2 可靠提交

- 每项提交有唯一操作编号、游戏实例标识和对应历史分支／阶段信息。
- 重复点击、超时重试只能产生一次状态变化。
- 旧阶段或被回退分支的动作必须拒绝并返回可理解原因。
- 游戏动作进入已保存状态后才向客户端返回最终成功确认。
- 客户端区分“待提交”“提交中”“已确认”“失败／需重新同步”。
- 重连后优先同步权威状态，不能直接重放所有旧缓存动作。

Socket.IO 支持自动重连和消息确认，但默认交付语义并不能保证断线消息全部送达；内置连接恢复也可能失败。因此必须自行实现动作去重与重新同步。[消息交付说明](https://socket.io/docs/v4/delivery-guarantees)、[连接恢复说明](https://socket.io/docs/v4/connection-state-recovery)

### 8.3 信息隔离

服务端为公共屏和每位玩家分别生成视图。其他人的秘密信息不能发送后再靠 CSS 隐藏，也不能混入错误消息、操作历史或前端调试数据。卡牌背面、未知身份等只发送当前规则允许的信息。

游戏资源中的卡牌图集可能公开可下载，但图集不应包含本局秘密状态，例如隐藏卡位与实际卡牌的映射。

### 8.4 自动存档

建议使用 SQLite 事务保存有效状态、决策点与必要操作记录，保证恢复时是一致的决策边界。程序突然停止时允许未被服务端确认的操作重新提交或重新选择；已确认操作必须可恢复，除非发生存储介质损坏等超出软件恢复能力的问题。

存档应包括平台格式版本、游戏标识、游戏版本、状态格式版本、规则版本、状态修订号、历史分支号、玩家与座位信息。秘密状态不出现在公开日志中。

建议存档写入用户本地应用数据目录，游戏包保持只读资源；用户能从管理界面知道存档位置。便携指 TableMax 本体“解压运行、无需安装”，不强制将全部数据写在程序目录；2026-10-03 新采用的共享 WebView2 前提见第 11 节和当日增补，运行时缺失时需先安装系统依赖。

升级规则或游戏模块后，应检查兼容性。首版可明确拒绝恢复不兼容存档并保留原文件；不要求实现所有历史版本迁移。

## 9. UI、资源与声音

### 9.1 平台外壳

- 简洁现代、信息层级清晰，游戏列表、房间状态与加入入口直观。
- 公共屏适合横屏显示，手机竖屏优先。
- 建议公共屏以 1920×1080 为首要验证尺寸；手机需覆盖常见窄屏和安全区域。
- 文字、按钮和点击目标应适合聚会距离与触屏操作。
- 暂停、断线、当前行动者和提交结果都有明确反馈。
- 游戏界面与房主管理权限分开；投屏不会显示房主凭证或其他秘密内容。

2026-10-01 用户增补：盒子和游戏应为独立页面，电脑和移动端游戏主体尽量全屏／占据绝大多数面积；从玩家角度去掉非必要步骤与复杂按钮，补充动效和视觉，使其更像游戏。继续优化职责清晰的项目结构和有序文档。当前 1.0.1 已采用独立路由、游戏场景与按需菜单，具体行为及验证在 [通用规格](reference/phase-02-platform-spec.md#盒子与独立牌桌) 和 [验收记录](reference/acceptance.md#首版维护独立牌桌与操作简化)。

### 9.2 游戏专属界面

公共屏和手机视图由各游戏具体设计。手机侧重点是自己的操作与信息，也支持查询允许公开的其他玩家信息；不要求将大屏棋盘缩小复制到手机。

首版《宝可梦奇遇》至少需要大厅、初始布局／设置、正常行动、目标选择、等待、回合／整局结算，以及暂停、重连、回退后的恢复状态。牌面显示、翻牌与卡位布局必须以核验后的规则为依据。

### 9.3 艺术资源工作流

允许在开发准备期间联网搜集参考／素材，或直接使用图像生成工具制作资源。所有最终资源必须经过整理、压缩和视觉核验，随游戏本地打包。

2026-10-03 用户确认的未来计划（未实现）：游戏数量增加时拆分可按需安装的游戏包，盒子仅内置目录、小封面与平台功能。电脑可在游玩前联网下载并本地安装游戏包，也支持离线导入；手机通过电脑局域网获取已安装资源，正式对局仍不依赖互联网。届时“随游戏本地打包”可由独立本地游戏包满足，不要求所有游戏预装在盒子 ZIP 内。当前首版仍完整随包提供，接续与完成标准见 [多游戏安装计划](tasks/README.md#多游戏按需安装未来计划未实现)。

- 建立资源清单：封面、卡面、卡背、角色／组件、背景、图标、提示音。
- 尽量还原原桌游的主题、角色辨识和组件关系，同时适配数字阅读与触控。
- 规则文字、数字和关键符号优先用 HTML／SVG 或可控排版叠加，避免把生图文字错误变成规则错误。
- 资源 ID 与规则 ID 稳定对应；替换美术不应影响游戏规则。
- 记录来源链接、取得日期、使用说明；生成资源记录提示词和版本。
- 当前按私人使用整理。未来公开代码前，逐项检查哪些资源能随仓库公开，必要时拆分或替换资源包；本文不将互联网图片视为自动获得公开分发许可。
- 缺失资源有可识别占位方案，但“完整可玩”验收时不应仍以大面积临时占位替代游戏美术。

### 9.4 声音

提示音只在公共屏播放，覆盖必要的操作确认、行动切换和结算；手机默认不播放，避免多设备重复发声。平台有静音开关，音频资源本地打包，不纳入背景音乐。

音频播放应由公共屏用户手势激活；静音、播放失败或浏览器限制不能阻断游戏。刷新、重连和回退同步不应重复播放历史提示音。

### 9.5 操作动效

游戏内操作必须配有简单动效，动效应协调、自然、美观，并与游戏主题和界面视觉风格一致。

- 动效用于表达操作反馈与状态变化，例如选择、翻牌、组件移动及结算呈现；具体效果由各游戏按玩法设计。
- 同一界面的动效节奏、过渡与运动方式应协调，避免生硬跳变或过度装饰；不遮挡关键信息、不妨碍操作。
- 动效遵守既有服务端确认与信息权限要求，不以动画代替成功确认，也不提前展示无权查看的信息；回退或重新同步时清除失效动画。

## 11. 推荐技术栈与部署结构

下表保留 2026-09-30 的初始技术建议；用户确认优先采用适合场景且便于开发助手协作的语言，例如 TypeScript，未要求锁定每一个库。前端已采用 React／TypeScript；2026-10-03 用户明确授权桌面改为 C# WinForms／.NET Framework 4.8／x64、共享 WebView2 和包内 Node 22.14.0，以满足新增游戏前 ZIP 与解压目录均严格小于 100,000,000 字节。当前方案及理由见 [决策 008](decisions/008-small-native-desktop.md)，历史表格中的 Vue／Electron 不再代表当前采用方案。

| 层        | 建议技术                        | 用途与选择理由                                     |
| --------- | ------------------------------- | -------------------------------------------------- |
| 主语言    | TypeScript                      | 前后端及游戏规则共享契约，支持模块化与开发助手协作 |
| 前端      | Vue 3 + Vite                    | 公共屏、手机端、房主 UI 与专属游戏组件             |
| HTTP 服务 | Node.js + Fastify               | 网页资源、加入接口、状态服务与日志                 |
| 实时通信  | Socket.IO                       | 分组广播、确认、重连基础能力                       |
| 数据校验  | Zod 或统一 JSON Schema 方案     | 校验客户端消息、模块清单和存档数据                 |
| 本地数据  | SQLite                          | 事务性自动存档、checkpoint 与内部历史              |
| 桌面包装  | Electron                        | 携带运行时，提供 Windows 便携程序与窗口管理        |
| 工程组织  | pnpm workspace                  | 独立平台包、UI 包与游戏模块                        |
| 验证工具  | Vitest；关键流程使用 Playwright | 规则验证、状态恢复和多端流程验证                   |
| 二维码    | 本地二维码生成库                | 根据当前有效局域网地址生成房间入口                 |

Vue 与 Fastify 官方文档可作为框架依据；Socket.IO 是带有自身协议的通信库，前后端使用配套客户端与服务端。[Vue](https://vuejs.org/guide/introduction.html)、[Fastify](https://fastify.dev/docs/latest/Reference/Server/)、[Socket.IO](https://socket.io/docs/v4/how-it-works)

SQLite 适合由本机服务统一访问的嵌入式存储场景，手机通过服务端接口访问，不直接共享数据库文件。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

历史建议采用 Electron 自带 Chromium 和 Node.js；2026-10-03 的体积要求已由共享 WebView2 加内置独立 Node 方案替代，旧建议与旧包证据保留用于追溯。[Electron 官方介绍](https://www.electronjs.org/docs/latest/)

正式游玩由本地服务端提供构建后的前端和资源。Vite 用于开发与构建，不把开发服务器当作便携程序的正式部署方案。[Vite 文档](https://vite.dev/guide/)

### 11.1 当前采用的运行结构

```text
Windows 便携程序
  ├─ C# WinForms / net48 / x64 桌面壳 + 共享 WebView2
  │    └─ 管理／公共窗口、显示／声音与服务生命周期
  ├─ 包内 Node 22.14.0 本地 HTTP + Socket.IO 服务
  │    ├─ 平台核心
  │    ├─ 已注册游戏模块
  │    └─ SQLite 存档与决策历史
  └─ 本地构建的公共屏／手机网页与资源

公共屏与手机 ── 局域网 HTTP／实时连接 ── 本地服务
```

不需要云服务器、Redis、独立数据库安装、Docker 或分布式部署。开发 .NET SDK 由 `global.json` 固定为 9.0.102，WebView2 SDK 固定为 1.0.4258.31；编译引用程序集不进入交付包。Node 随包提供，正式程序使用系统共享 WebView2 和 .NET Framework 4.8，缓存与存档进入用户数据目录。必须验证旧 Electron 写出的 SQLite 能被包内 Node 读取、继续保存和恢复，保持原存档格式及身份；不通过删除旧数据解决兼容问题。

桌面与服务使用显式 stdin／stdout 私有 JSON 行管道，管理员凭证仅在该通道交接，不进入命令行、日志或公共接口。原生桥接必须核验本源、顶层文档及窗口角色；Windows Job Object 绑定服务生命周期，正常退出等待保存／关闭，异常退出清理服务后代。正式启动不开放测试 IPC 或 CDP 调试端口。完整边界见 [工程结构](reference/architecture.md)。

### 11.2 面向对象与可维护性

开发必须注意面向对象的适度封装。按职责封装具有生命周期、依赖和不变量的服务或策略，优先通过组合与明确接口协作；不要求把所有函数、数据或 React 组件改写成类，不建立无实际需要的深层继承体系。

规则计算、计分、合法动作和投影继续支持可独立验证的纯函数；平台调度、持久化和生命周期适合按服务职责封装。UI、规则、电脑策略和数据库适配不能互相混入实现；游戏状态与策略恢复数据仍是可序列化普通数据。独立计分与电脑决策文件不得被大一统游戏控制器吞并。

设计和代码审查应核对职责内聚、依赖方向、状态修改入口、对外接口、可替换策略与行为回归验证；不以类数量或设计模式数量衡量完成。具体组织原则见 [工程结构](reference/architecture.md#面向对象与适度封装)。

## 12. 局域网与 Windows 运行要求

- 服务需要监听可供局域网访问的地址，二维码中使用实际可连接的网卡 IP，不使用 0.0.0.0 或手机无法访问的 localhost。
- 多网卡场景可以选择地址，优先排除明显的虚拟／无关网卡；必须保留手动选择能力。
- 同一 Wi-Fi 名称不保证设备能够互访。连接说明涵盖访客网络设备隔离、防火墙和错误网卡。
- 首版不自动配置路由器，不要求用户做公网端口映射。
- Windows 防火墙可能需要用户允许程序在私人网络通信；便携程序不能保证无权限提示。
- 端口被占用时给出明确提示或选取可用端口并更新二维码。
- 电脑休眠会影响服务；公共屏运行期间建议阻止自动休眠，不能把关闭屏幕与关闭服务混淆。
- 电脑与显示屏默认采用扩展显示器，公共屏独立全屏；显示屏放置允许用户选择。
- 如果使用镜像投屏，提供公共屏全屏模式，避免管理页或私人内容出现在投屏画面。
- 关闭整个程序时保存当前游戏并有明确退出行为；关闭公共屏窗口不应意外删除游戏。
- 字体、图片、脚本和声音均本地加载，运行时不使用 CDN 或在线生图。
- 手机浏览器访问局域网 IP 的 HTTP 页面不等于安全上下文。首版不依赖 Service Worker 或网页内摄像头扫码；扫码由手机自带工具完成。需要相关能力时再规划 HTTPS。[安全上下文说明](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)、[Service Worker 要求](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)
- 微信内置浏览器不作为唯一验收环境；使用不兼容时提示到系统浏览器打开。

| AC-22 | 人机回退与恢复   | 暂停／结束不推进，回退／重启后正确恢复策略数据并重新调度；旧分支结果、重复提交与异常重试不会破坏对局                                                                 |
| AC-23 | 决策文件与接入   | 电脑策略独立维护、可定位和替换，版本与兼容边界明确；模板和指南包含策略接入、覆盖验证和故障处理                                                                       |
| AC-24 | 导出与解压体积   | 新增游戏前，Windows x64 ZIP 和实际解压后的全部交付文件各自严格小于 100,000,000 字节；记录实际大小和文件哈希，系统共享运行时、用户存档及缓存不计入（2026-10-03 增补） |

AC-18 的验证模块是开发验证设施，不新增“演示游戏”这一面向用户的首版交付要求。AC-01 按 2026-10-03 的运行时前提补充验证：已有共享 WebView2／兼容 .NET Framework 时无需 Node 或开发工具；缺少 WebView2 时提供官方安装提示并可取消。AC-24 的工程预算为 95,000,000 字节，最终必须用实际 ZIP 和实际解压文件总量验证，不能仅引用构建目录估计。

性能目标建议：在正常家庭局域网中，普通动作从提交到界面确认应接近即时，验证目标可暂定为通常 500 ms 内完成，排除有意展示动画的时长。该数值是设计目标，未经过实测；具体验收机型与网络条件在开发验证阶段记录。

人数上限按对应游戏的已核实规则实现，不凭平台默认值改变游戏人数；平台契约避免硬编码某一款游戏的上限。

## 2026-10-02：单牌桌、卡面与关键动画增补

用户最新要求替代旧房主参赛要求：程序启动即有唯一牌桌，无需创建或选择房间；电脑端为房主，仅管理和观察公开状态，不占玩家名额。手机仍领取独立玩家身份，真人与电脑合计 2–5 人。新局首位由服务随机选择，旧存档保留既有座位和进度；历史 hostSeat 字段仅兼容读取。

盒子采用简约布局，突出游戏、玩家、扫码与开始；管理、连接帮助和规则按需展开。游戏独立页面占据电脑／手机绝大多数可用面积，减少小字，文字、按钮和角标保持清晰对比。

16 类卡牌各自制作角色卡面，形象贴近原版宝可梦及用户实物参考；统一角落分值由代码排版，同类实体牌复用该图。所有美术和声音统一存放、管理并支持替换，保存来源与生成／导入／核验状态。翻开卡片、能力触发、抛硬币、最终结算必须有美观动画；只表现已保存的授权结果，同步／恢复／回退不补播，支持减少动态。

开发验证优先后台、隐藏窗口和隔离数据；截图应使用真实隐藏渲染，不把模拟应用带到前台。代码按职责适度封装、供人阅读维护，当前行为及验证文档同步更新，按可验证阶段提交 Git。

## 2026-10-02 增补：手机聚会、围桌房间与三档人机

所有真人玩家都用各自手机扫码进入、准备和操作。电脑只是房主（管理员），运行本地服务并向现场朋友展示公共画面；房主如果参与，也须用自己的手机领取普通玩家身份，不能由电脑代做游戏动作。电脑公共投影不包含私牌或未来牌序。

盒子房间显示真正的桌子、围桌座位、玩家头像与准备／在线状态，借鉴 QQ 游戏大厅的房间观感，加入的玩家自动上桌。首版仍为唯一牌桌，不由这种视觉引入多房间、账号或联网大厅。

房主在盒子开局前为人机选择“默认”“豆包”“绝悟”，智能逐级上升；“绝悟”的优解基于授权公开／本人信息及获准记忆、可复查的局势评估和有界计算，不通过偷看暗牌或牌库获取全知结果。等级、策略恢复数据与原班续局一并保存；更改等级只在准备大厅执行，不自动接管离线真人。具体算法与验证归入 [人机规格](reference/bot-players.md) 和 [首版策略](games/pokemon-encounters/bot.md)。

用户明确首版最多六位手机真人／人机，须核验六人实际布局及能力、人机、恢复；保留旧人数来源并标明项目扩展，不把六人写为已认证出版事实。具体规则采用依据见 [S21](games/pokemon-encounters/sources.md#s21六人项目扩展2026-10-02)。

- 手机扫码或电脑浏览器打开普通玩家入口，均按本人座位授权；电脑管理员不占座位，公共屏只读，玩家使用电脑不取得管理员或原生桥接权限。
- 状态同步必须自动确认并在超时、断线及回到前台时恢复，等待同步时不能提交陈旧动作。当前源码采用 polling 优先、尝试升级 WebSocket、5 秒确认超时与前台每 10 秒同步；确认回复及广播都按实例／分支／修订拒绝旧状态，重试保留原动作编号，恢复不重播旧结果。
- 新设备可在盒子申请原真人座位，由电脑管理员核对并批准或拒绝。申请有效期 5 分钟，可取消及重试；批准后旧凭证和连接失效，原座位、对局及房主授权保留。加密批准收据可凭新设备请求密钥在 24 小时内跨重启恢复，不重复占座；身份和换机结果不随游戏回退恢复，不能由普通玩家或玩家房主自行批准。
- 管理员可在连接帮助保存 HTTP(S) 映射根地址或带端口地址，二维码与公共屏使用相同已保存入口，支持回到局域网模式。按2026-10-08最新要求，默认链接和二维码归一为网站根地址；旧 `/player` 入口及旧配置继续兼容。不接受凭证、查询参数或任意路径前缀；映射需转发资源、API 和 Socket.IO。配置独立保存于当前数据目录，不改变对局、身份、原生管理来源或系统防火墙。

上述能力已接入当前源码，具体行为与接口边界统一见 [平台连接规格](reference/phase-02-platform-spec.md#浏览器入座换机与外部连接2026-10-07)；交付包、真实界面、外部穿透和设备检查状态仍以 [验收记录](reference/acceptance.md) 为准。
