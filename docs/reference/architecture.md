# 代码结构与工程边界

采用依据：[工程基础决策](../decisions/001-engineering-foundation.md)。本页区分第一阶段工程基础、第二阶段独立原型与后续平台机制；初始契约和合成原型不代表身份、游戏或恢复能力已实现。

后续产品界面按用户最新确认采用[公共大屏兼房主管理与调试模式](../decisions/002-host-public-screen-and-debug.md)；当前下述三入口及窗口行为是工程验证实现，尚未迁移。调试字段、动作和恢复边界待确认，不据此宣称已提供调试权限。

## 已建立的工程

| 路径                | 当前职责                                                                  | 直接依赖方向                                                                      |
| ------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `apps/desktop`      | Electron 窗口、服务启动与退出协调，解析本地数据目录                       | `protocol`；不实现游戏规则，不访问数据库                                          |
| `apps/server`       | Fastify、Socket.IO、静态网页、本地二维码、SQLite 工程验证适配器           | `protocol`；数据库和网络对象仅保留在服务端                                        |
| `apps/web`          | 单一 React 网页工程，公共屏、手机和管理的正式入口布局；另有独立原型入口   | 正式入口依赖 `protocol`；原型仅使用本地合成 UI 数据，均不读取数据库或规则完整状态 |
| `packages/protocol` | 对外工程验证消息及桌面／服务消息的类型与 Zod 校验                         | Zod；不依赖应用、具体游戏或数据库                                                 |
| `packages/game-sdk` | 纯类型初始游戏契约：模块清单、JSON 状态、动作、视图、随机上下文与决策边界 | 不依赖前端、通信、数据库、Electron 或具体游戏                                     |
| `games/README.md`   | 游戏模块布局约定与后续工作入口                                            | 尚无注册游戏或空游戏工程；目标版规则关口未通过                                    |
| `scripts`           | 构建、开发、启动、桌面运行时安装、便携打包、跨层验证及原型走查            | 开发工具；不进入游戏规则                                                          |

`platform-core` 与通用 `ui` 包尚未创建。已有网页组件数量不足以需要独立 UI 包；当前没有房间、身份、动作队列或恢复机制，不为这些功能建立空实现。

共享包通过 pnpm `workspace:*` 声明依赖，开发时导出 TypeScript 源码，由 Vite／esbuild 消费。当前使用根配置统一类型检查；服务与桌面输出独立 CJS 文件，网页输出独立静态资源。服务端运行依赖被打包进 `server.cjs`，便携包不依赖工作区 `node_modules` 或电脑预装 Node.js。

## 面向对象与适度封装

2026-10-01 新增开发要求，后续业务实现遵循以下原则；当前工程未因本次文档更新重构。

- 有生命周期、外部依赖或需维护不变量的能力按职责封装为服务／对象，例如房间动作协调、bot 调度、存档仓储和桌面服务生命周期。名称与接口在实际实现时确定，不提前创建一套空类。
- 依赖通过显式构造或参数传入，优先组合而非深层继承；核心依赖抽象边界，应用注册入口负责组装具体游戏、策略和适配器，不引入全局可变服务容器。
- 规则变换、计分、投影和合法动作适合纯函数或无状态模块；React 沿用函数组件。面向对象不等于把所有函数强制包进类。
- 权威状态只能通过统一游戏动作入口修改；电脑策略返回意图，UI 和策略不能直接写数据库或访问规则的完整秘密状态。
- 存档只含普通可序列化数据；服务对象、函数、连接和定时器不入档。策略若有记忆或随机状态，显式导出数据并在恢复时重建运行对象。
- 计分、电脑策略、规则执行、界面、网络和持久化分别维护，避免巨型游戏控制器；仅对已出现的变化点抽象接口，不为未实施的插件／难度体系铺空层级。
- 审查职责是否内聚、依赖方向是否清楚、策略是否能替换、是否存在状态旁路及回归验证；封装重构保持既有行为，不通过复制实现来测试。

## 运行与入口

```text
Electron 主进程（窗口与生命周期）
  └─ utilityProcess 独立服务（Electron 内置 Node.js）
       ├─ HTTP / Socket.IO
       ├─ 本地构建网页与资源
       └─ SQLite 工程验证数据库

公共屏 /public ─┐
手机端 /player ├─ HTTP / Socket.IO ─ 服务
管理端 /host ──┘
```

桌面在服务报告就绪后打开管理窗口，服务启动超时、端口占用或数据库打开失败时停止启动并提示。公共屏链接打开另一窗口；关闭公共屏保留管理窗口和服务。关闭全部窗口或退出整个桌面程序时通知服务优雅关闭，超过 5 秒才终止服务。服务异常退出时停止桌面程序，避免保持失效管理页。

窗口不启用 Node.js 集成，启用上下文隔离和沙箱；当前没有向网页暴露 Electron IPC 的 preload。桌面限制窗口向其他源导航与创建任意新窗口。公共屏窗口目前不实现显示器选择或全屏控制，这些属于第三阶段。

三个入口当前是**工程验证页**。共享一个工程不意味着共享角色凭证、秘密状态或权限。当前无玩家身份和房主授权，页面路径不授予权限；后续服务必须验证实际身份并生成对应投影。游戏状态不能先全量发送，再靠前端隐藏。

第二阶段另有 `apps/web/prototype.html` 与 `vite.prototype.config.ts`，源码位于 `src/prototype/`。独立配置只构建合成 UI 状态到 `artifacts/phase-02/prototype/`，没有真实服务代理、凭证或完整游戏状态。它不进入正式页面路由，不参与普通桌面构建，不演进协议／SDK；角色切换用于走查，不是授权实现。设计输入与限制见 [通用交互规格](phase-02-platform-spec.md)，运行前提与构建隔离证据见 [开发说明](development.md)。

## 后续机制归属

以下是设计边界，均不表示机制已实现。

| 能力                         | 负责模块                                      | 边界                                                                                           |
| ---------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 房间、身份、房主管理授权     | 未来 `platform-core`，由服务适配通信与持久化  | 普通模式按房主／玩家身份授权；公共大屏兼管理，调试例外字段与动作待单列确认                     |
| 动作参数校验                 | `protocol` 校验平台信封，游戏规则校验具体动作 | 服务绑定真实身份，客户端玩家编号不是授权依据                                                   |
| 动作串行、去重和成功确认     | 未来 `platform-core`                          | 按房间串行；实例、动作编号、阶段／分支校验；事务保存后才确认成功                               |
| 可序列化权威状态             | 具体游戏规则，平台负责存储外层元数据          | 游戏保存普通 JSON 数据；不保存 UI、连接、数据库句柄或框架对象                                  |
| 统一随机源                   | 平台维护随机状态，SDK 提供上下文契约          | 游戏不直接调用 `Math.random()`；决策点保存随机状态，回退不偷偷重随机                           |
| 决策点语义、标签与已揭示信息 | 游戏规则声明，平台形成可恢复记录              | 恢复边界按已核验规则定义；已看到的信息无法从人的记忆撤销                                       |
| 回退与分支修订               | 未来 `platform-core`                          | 修订与分支号递增；迟到的旧分支动作失效；连接和身份不倒退                                       |
| 公共／玩家投影               | 游戏规则定义，平台选择真实身份并调用          | 完整 checkpoint 不进入网页消息；错误与公开操作记录不能泄露秘密                                 |
| 存档事务、格式与恢复         | 核心制定记录，服务 SQLite 适配器执行          | 平台格式、游戏／规则／状态版本分开；损坏或不兼容原文件保留                                     |
| 电脑座位与 bot 调度          | 平台核心协调，服务端提供运行适配              | 标识真人／电脑控制者；只调度合法的电脑选择，统一队列与事务；暂停、回退和结束取消旧计算         |
| 电脑决策文件                 | 对应游戏独立策略，通过 SDK 契约接入           | 只读取该座位授权视图与合法选择，返回动作意图；覆盖全部决策，不依赖 UI、网络、数据库或 Electron |
| bot 版本、记忆与随机恢复     | 平台保存外层记录，游戏策略声明数据格式        | 普通数据入档；兼容检查、分支失效及恢复后重新调度；不读取调试特权数据                           |
| 游戏资源                     | `games/<id>/assets`，构建时按清单收集         | 游戏 ID 命名空间；正式资源随包本地加载，不含本局秘密映射                                       |

未来依赖方向为：应用适配层 → 平台核心 → 游戏 SDK；具体游戏规则 → 游戏 SDK；注册入口组装具体游戏，不让核心依赖宝可梦实现。游戏 UI → React／必要公共 UI 与已授权视图，不能导入规则服务入口。

每款游戏集中在 `games/<id>/`，内部按实际需要建立 `rules/`、`ui/public/`、`ui/player/`、`assets/` 、独立电脑策略及验证。源码模块编译时注册，首版不实现独立插件加载或沙箱。第二阶段核验规则；第三、四阶段演进契约、可靠动作、回退与恢复；第五阶段实现首版完整游戏。

用户要求首版计分独立成文件／纯模块，计划位于对应游戏的 `rules/scoring.ts` 或等价位置，由规则引擎调用，UI 接收授权结算。普通分值配对与百变怪分值解析的先后、边界仍待完整规则确认，当前尚无计分实现。

电脑策略的目标职责与接入要求见 [人机规格](bot-players.md)。建议在每款游戏内设置独立 `bot/` 目录，具体决策文件形态尚待确认；这是计划路径，当前未创建。规则负责判断动作是否合法，策略负责在授权选择中作简单决策，平台负责运行与保存，三者不互相代替。

## 验证分层

- 模块规则验证放在对应游戏内，使用固定随机源；游戏未开发时不制造规则测试。
- bot 按每种实际决策节点验证合法性、授权视图和参数覆盖，再验证人机混合整局；平台层验证暂停、回退、旧分支取消、重启及异常处理。策略替换与封装重构按影响执行行为回归，具体场景见人机规格，当前均未运行。
- 当前 SQLite 事务、重启读取、损坏文件保留与 HTTP 路由验证位于 `apps/server/src/*.test.ts`，由 Vitest 执行。
- 桌面与服务进程、网页连接、消息校验、三个入口、关闭公共屏、服务退出和数据库再次读取由 `scripts/verify-desktop.mjs` 验证。
- 同一验证脚本对开发产物与打包产物运行；打包验证使用受限 PATH，不依赖开发工具位置。正式手机实机、离线整局和无开发环境电脑验收属于第六阶段。
- 独立原型由 `scripts/verify-prototype.mjs` 使用 Playwright／隐藏 Electron 窗口验证已有构建，检查点击、视图、反馈、尺寸和本地请求；不启动正式服务，不测试真实身份、游戏秘密、决策 checkpoint 或存档。规格场景与产品 AC 责任见通用规格。

具体命令、环境和真实结果见 [开发环境与验证](development.md)。
