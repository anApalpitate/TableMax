# 文档维护规则

## 分类与入口

- [总索引](../README.md)：按任务意图定位最小必要内容。
- [reference](README.md)：当前参考知识、目录职责与操作方法。
- [games](../games/README.md)：每款游戏的来源、采用规则、结构化数据、权限与决策、交互、资源、人机及验证场景。
- [decisions](../decisions/README.md)：已确定的重要决策、理由及后果。
- [tasks](../tasks/README.md)：粗粒度阶段总览、进行中的阶段任务与已确认待办；已完成阶段保留状态和归档入口。
- [subagent](../subagent/README.md)：子 agent 的长期职责、派工输入、可写边界与交接标准；具体任务和素材记录保留在各自入口。
- [archive](../archive/README.md)：有历史价值的过程记录，不作为当前实现依据。
- [requirements 中的需求基线](../requirements/TableMax_需求文档_v1.0.md)：保存产品需求基线；用户确认的增补标注日期与状态，产品要求通过入口链接引用，不机械复制。

## 区分要求、现状和计划

已确认需求说明应该实现什么；源文件、配置与验证结果说明目前实现了什么。两者不一致时记录差距，不能以当前实现反向覆盖需求。

需求中的技术建议、未确认想法和未验证结论不能写成已确定方案或已实现行为。进行中的实施计划留在任务记录；已确认但未实现的要求可进入需求说明，明确标注状态。重要决策可以先于实现记录，同时说明落地状态。

每款游戏的规则规格与来源记录在规则研究时建立，记录对应版本、语言、来源、获取日期、适用章节及核验状态。未取得全文的入口、第三方介绍和其他版本不能替代已核验原文。游戏资源应维护来源及用途清单。

阶段状态应与完成标准逐项对应：部分规格已交付不代表整阶段完成，原型合成场景通过不代表平台功能、游戏规则或产品 AC 通过。未闭合的玩法选择不冻结规格；首版按 S19 授权先中文检索、无依据自主落定项目方案，不再追问。原文认证缺口和已采用方案分别记录，不能把自主方案写成官方规则，也不能以原文未取得替代具体规格交付。

运行命令、前提、产物路径和实际工程检查集中维护在 [开发说明](development.md)；设计行为、场景和后续责任维护在对应规格；阶段任务只记录交付入口、证据与剩余工作。有阶段阻塞的来源检索进度留在 tasks；已形成采用基线后将长期来源、原文缺口与游戏知识写入游戏主题页，不提前归档尚待解决的问题。

## 更新与归档

继续优化默认沿用当前版本号，只有用户明确要求推出新版本号才调整版本；不自行递增、重置或改名。同版本更新便携包时先保留原包及其对应验收证据，新的验收记录明确实际包哈希，历史通过结论不覆盖为新包通过。

1. 修改行为、目录、入口或操作方法时同步修订对应主题页；优先更新已有文档，不复制出多个当前版本。
2. 新增、移动、重命名或归档文档时，同步维护总索引、所属分类索引及受影响的相对链接。
3. 任务完成并通过适用验证后，将通用长期知识写入 reference、游戏专属知识写入对应 games 主题；重要选择及其理由、后果写入 decisions。
4. 有历史价值的过程记录移入 archive；归档索引说明原因并链接当前替代页面（如有）。
5. 目录职责、阅读入口、通用约定或用户长期偏好变化时同步维护 [AGENTS.md](../../AGENTS.md)，具体操作与经验留在主题页。
6. 较大任务完成且相关验证通过后自动提交，只纳入本次明确改动；保留用户原有暂存和未提交内容，默认不 push。
7. 开发阶段保持粗粒度，任务索引记录阶段顺序、主要工作、交付物和状态；临近执行时再补充该阶段的范围与完成标准。阶段文档的建立不等于阶段任务已经执行。

已完成的阶段任务从 tasks 移入 archive，保留完成日期、范围、验收清单及证据，补归档原因和当前参考入口，并修复所有入链及文内相对链接。进行中任务的交付缺口与接续步骤优先合并在同一任务页，已形成的长期规则与来源引用游戏主题，保留来源编号、状态及原始资料引用；规则关口未通过的阶段不因部分交付完成而归档。

合并同类文档时，以任务或长期主题确定唯一正文去向，删去重复状态和步骤，索引用链接导航。目录职责、工程依赖、开发操作及交互规格各有独立用途，保持对应主题；命令和验证方法不复制进归档记录成为第二份当前操作说明。

后续开发的阅读与阶段交接维护在任务索引；游戏玩法、字段和决策表只在游戏主题维护，通用平台页通过链接引用。README 与各级索引保留现状及入口，不重复完整规则、契约缺口或验证报告。

## 定向查询与入口维护

- 总索引按任务问题给出最小阅读入口，分类索引只说明正文职责；标题使用主题名称，不以历史版本号作为当前知识分类。旧版本标题可以保留为短转链，避免现有锚点失效。
- 已知主题时先限定到对应文件或 `docs/games/<id>`、`games/<id>`；当前共性查 `docs/reference`，只有追溯原结论、采用原因、耗时或旧哈希时查 `docs/archive`。不默认遍历生成物、截图、日志和全部历史。
- 先用 `rg -n '^#{1,3} ' 路径` 找章节，再以相关术语检索；同一任务复用未变的阅读结果，用 Git diff 与定向 rg 补增量。确有矛盾或入口未知再扩大范围，不能把未返回的搜索结果当作不存在。
- 迁移正文后检查所有入链、相对文件路径与章节锚点。保留已有标题转链；迁移历史时不丢失原始结论、失败、证据、哈希或版本边界，不把旧测试通过升级为当前产物通过。
- [当前验收](acceptance.md)保留最近完整交付、实际包引用和验证边界；较早长记录移入 [历史验收](../archive/acceptance-2026-10-01-to-04.md)。历史正文唯一维护，当前页只留必要导航，不复制每轮摘要或全部指标。

查询示例维护在 [总索引](../README.md#定向查询)，不建设重复标签体系、全库常驻索引或每任务一份查询总结。

## 通用视觉与游戏例外维护

当前职责分为三层：[用户美术偏好](art-preferences.md)保存原话、明确采用与来源；[通用视觉](visual-design.md)保存跨游戏表现要求和验证方法；各游戏主题保存规则、专属组件／主题／声画、规则配图及当前实现状态。身份、计时、保存恢复和显示权限继续归 [平台规格](phase-02-platform-spec.md)，避免在视觉页复制算法或协议。

从某游戏反馈提炼共性时，先确认用户授权与实际用途，写清适用对象和例外。主体、字号、状态语义、标记辨识、集合浏览与保存后反馈可复用；拍卖流程、宝可梦能力表现、德国地图版本和人机记忆不能顺带推广。列表通常可纵向两列，规则棋盘和地图保留空间关系；宝可梦手机首屏要求不能因通用画廊建议被抹掉。不得将 agent 提议、现有实现或某张截图数值记为用户偏好。

2026-10-04 用户要求优化每个游戏规则说明，覆盖此前只为现代艺术增加规则帮助的限制；仍不自动增加强制教程、教学流程或管理权限。按每款游戏已采用版本与来源更新，图文对应真实隔离示例，原图／派生图、用途、尺寸、哈希与界面版本进入已有资源清单。规则或区域布局变化时复核受影响说明与截图，不能用过时配图或外部在线图片交付离线规则界面。

新增反馈先更新偏好与来源，再修订受影响的共性或游戏正文，索引只链接；被替代的历史要求保留覆盖日期和边界。先查短屏／密集／最高人数等风险场景，再完成适用三端、减少动态与最终包检查；静态审查、动态运行和真人听感分别记录，未验证旧页不写成已适配。

## 新增需求与工程约定维护

- 人机要求以需求基线为产品入口，详细行为维护在 [人机规格](bot-players.md)，面向对象与适度封装维护在 [工程结构](architecture.md#面向对象与适度封装)。重大范围变化在 decisions 说明取舍，同时更新阶段范围、交接、验证场景与项目状态，清除与新要求冲突的排除项。
- 游戏规则、独立计分和电脑决策各有主题与源码职责；逐决策 bot 覆盖清单与策略版本维护在对应游戏，未建立游戏模块时将缺口保留在阶段任务。未确定文件形式和接口不能写成既有实现。
- 新需求增加验证责任，不倒改已归档阶段的历史完成证据；既有原型和工程通过记录不证明人机或新封装要求已验收。
- 封装重构同步职责、依赖与实际入口；策略输入、恢复数据或版本变化同步兼容性说明及相关回归范围。游戏 bot 是产品电脑玩家，开发子 agent 是协作角色，文档不得混称。

## 子 agent 与素材记录维护

- 盒子／游戏 UI、布局、图标、头像、插画、动效和视觉审查在设计前必须查询 [用户美术偏好](art-preferences.md)；派工传入该文档与当次最新反馈。用户原话、明确要求实施的方案与 agent 的实现判断分别记录；新增或替代偏好合并到该唯一正文并保留来源，不复制进角色文档。偏好不覆盖对应游戏规则、秘密权限、可读性、触控及减少动态要求。
- 子 agent 职责统一放在 `docs/subagent/`，每个角色一份当前文档；新增、变更或停用角色时维护职责索引、总索引、目录职责和必要的 AGENTS.md 路由。具体派工和停用方式见 [职责索引](../subagent/README.md)。
- 子 agent 在明确的文件边界内工作，交付时说明改动文件、验证、未完成项和需整合事项；主 agent 复核后统一同步索引与提交。避免多个 agent 同时修改素材清单或共享主题页。
- imagegen 的提示词、输入图片角色、工具模式、来源、版本、实际尺寸／透明度、最终位置和核验结果维护在素材所属的清单与证据中；沿用现有清单格式，不默认建设新的 schema 或复制进职责文档。
- 保留既有原图和历史证据，候选、已核验资源及已导入 UI 的状态分别记录；引用到项目的资源保存到工作区，本地打包可用，不能仅引用工具默认输出目录。替换既有素材须属于明确任务范围。
- 角色说明不记录会话实例 ID 或一次性进度，不将职责文件等同于自动注册或持续运行的子 agent；职责修订与实际执行状态分别维护。

## Agent 开发效率规则

本节约束后续开发的执行顺序与证据，不改变产品要求或缩减验收范围。首次进入任务时确定适用项；任务收尾在既有任务页或验收记录中说明检查结果与未完成项，小改动可直接在交付回复中说明，不另建过程总结。

### 定向阅读与环境预检

- 首次进入任务先读 Agent 入口、文档索引、Git 状态和相关 diff，再按职责定位章节与源码。同一任务中，资料未变且上下文仍可用时，复用已知结论，仅用 `rg`、指定章节或增量 diff 补读；资料更新、上下文缺失或出现矛盾时才重读相应部分。输出截断后缩小读取范围，不原样重复整篇输出。
- 工具结果优先输出结论、失败项、必要字段和完整证据路径；完整日志、逐帧几何与资源清单留在证据文件，出现具体问题时再定向读取。先限制查询范围，再设置输出预算，避免为了截断结果重复执行同一检查。
- 新工作区首次安装或执行工程检查前，核对 `.node-version`、`global.json`、根目录 `package.json`、pnpm／原生包锁文件与实际 Node／pnpm／.NET SDK／WebView2 版本，确认包内 Node、原生编译及共享运行时可用；执行入口见 [开发环境](development.md#初次配置)。纯文档改动只预检所需文档工具，不安装完整运行环境。
- 优先使用现有工具支持的已核验下载缓存；跨工作区复用时确认版本、平台、架构与官方校验值一致，使用工作区自己的安装目标。没有可核验缓存时走正常安装；不共享可变 `node_modules`、跳过校验、修改全局环境或顺便升级工具链。

### 先解决集成与高风险场景

- 跨模块任务在派工或并行实现前明确共享接口、数据兼容性、文件负责人和交接条件；有其他会话修改目标文件时保留其改动，重新核对当前内容并避免同时重写。同一文件仍只由一名 agent 修改。
- 协议、权限、保存恢复、旧存档或游戏切换变化时，先打通最小真实跨层路径，核验越权、失败保持原状态和迟到旧动作，再扩展其他功能；集成验证不能全部推迟到交付前。
- 布局变化先检查最容易暴露问题的代表场景：六人、720p、125%／150% 显示缩放、暂停／恢复提示及短手机；按影响选择适用组合，并说明未覆盖项。修正后再运行规定的完整尺寸、三端与最终便携验证；沿用隐藏窗口和实际更新后的渲染，不将代表场景通过当作完整验收。
- 为已通过的检查保留对应版本／改动、命令、结果与证据路径。仅相关代码、资源、配置或运行环境变化，检查失败或仍有未解决疑点时重跑；先跑受影响项，再完成本次必需的最终检查，不机械重复无关全套构建或矩阵。
- 相同布局或流程失败先固定一个可复现案例，用真实渲染定位原因并验证修正，再跑完整受影响矩阵；不在每次微调后重跑所有场景。发布时只构建一次最终包，再验证该 ZIP，后续仅文档变化不重复打包。

### 批量检查与等待

互不依赖的搜索、读取和检查在同一批调用中执行，逐项核对结果；修改、审批、构建与依赖结果的操作保持顺序。授权并行协作时，交接集中提供改动范围、结果、证据与阻塞，避免连续发送重复进度询问；不因本节创建未授权的协作实例。

等待长任务使用完成通知或有界等待，只有实际状态变化、失败、需决策或完成时才读取相关详情。等待期间继续独立工作并按约定提供用户进度；没有新信息时不反复读取历史、重新分析同一结论或缩短轮询间隔。

### 素材先核验可行性

批量生成、下载或导入前，先用少量代表素材确认工具可用、来源可获取、输出符合尺寸／透明度／风格或声音要求，再扩大制作。素材仍按 [子 agent 与素材记录维护](#子-agent-与素材记录维护) 留存输入、来源、版本与实际核验结果。

相同原因连续失败且没有新增信息时，停止重复同一方法的批量尝试，记录失败原因与已试范围，使用用户已授权且可核验的替代来源或方案。用户明确要求逐项尝试或指定来源时优先遵守；需要改变未授权的范围或标准时，只就该缺口询问。不得改写提示以绕过安全拒绝，不把未试听、未核验或未导入的候选写成已完成素材。

### 耗时证据与收尾核对

较大任务或实际出现阻塞时，在已有任务记录、验证结果或验收记录中保留关键阶段的开始／结束时间或已测耗时，分开标记实现、依赖下载、验证、失败返修与等待用户决策，并注明失败原因、后续采用方法和证据路径。优先复用现有日志，不新增常驻监控、专用计时系统或每次会话总结。

并行阶段不能直接相加作为总耗时；Git 提交间隔、文件修改时间和两条日志之间的空白不能冒充实际开发时间。资料不完整时标明估算口径与未知项，不捏造总时长或占比。

分析 token 消耗时去除重复响应记录，分开统计总输入、缓存输入、未缓存输入和输出；推理 token 已包含在输出中，不能再次相加。按读取、实现、验证、返修及等待定位可减少的重复轮次；日志 token 总量不等同于订阅额度消耗，不据此编造节省比例。

收尾核对以下适用项：阅读范围是否收敛，环境与素材预检是否完成，跨层路径与风险场景是否先验证，最终必需检查是否通过，重复检查是否有具体原因，以及耗时结论是否有证据。未完成项说明影响与接续步骤；仅文档调整检查格式、链接／锚点与 diff，不触发无关游戏测试、构建或发布。

## 保持轻量

清理资源先检查正式页面、独立原型、动态资源表、脚本和文档引用；只删除确认未使用的副本或可再生中间物。素材退役时保留原图、提示词、来源与历史核验，把当前文件清单和退役记录分开，并同步链接。清理测试目录前确认相关进程结束，核对绝对路径与目录边界；不按 Git 忽略规则批量删除，开发依赖、默认玩家存档、原始资料和当前已验证交付 ZIP 不属于测试残留。

历史程序包与已结束的隔离测试／打包目录使用根目录清理入口，唯一操作说明在 [开发环境](development.md#清理本地中间物)。两个手动入口保持默认预览，显式执行才删除；日常开发在工程操作前后、相关进程全部结束的空闲边界，按用户授权调用 `Maintain-Project.ps1 -Apply`。它发现同仓库主工作区，磁盘逻辑占用超过 5 GiB 时按最旧合格候选清到 4 GiB 或候选耗尽；不重复计算 worktree，不创建常驻任务，不把磁盘清理描述为释放运行时 RAM。

自动维护继续要求当前 ZIP 与便携通过记录的哈希一致，保留 30 分钟近期修改、路径／链接／候选变化、进程及互斥保护。缺少验证包、目录仍在使用、无合格候选或安全检查失败时保留并报告，不结束用户进程、不放宽范围；`build/`、依赖与工具缓存、正式存档、原始资料及历史证据仍受保护。新验证脚本采用新临时前缀时，先核验实际用途，再更新 `scripts/cleanup-local.ps1` 白名单及隔离测试；当前 `experience-*` 与 `runtime-memory-*` 对应新版操作验证和内存测量，`modern-art-polish-*`／`modern-art-audio-verify-*`／`countdown-crosslayer-*` 对应本轮隐藏布局、音频及真实倒计时隔离数据，均只匹配六位随机后缀。不能扩大为清空整个 `tmp/` 或 `artifacts/`，不能通过手写批量删除绕过保护。

性能结论与证据对应到实际构建和测量范围：复制算法的分配／耗时、renderer heap、应用进程工作集、项目磁盘占用分别记录。保留原始测量与局限，不把一组 fixture 的降幅推广成整局 RAM 降幅，也不把界面反复切换无明显增长写成长期有界历史或绝无泄漏。

保留全部资料的磁盘优化使用 [透明压缩入口](development.md#工作目录透明压缩)，不扩大删除范围或有损重编码。实际分配按文件身份去重，避免硬链接重复计算；逻辑容量维护阈值与便携包门禁保持原口径。压缩前后逐文件哈希一致、逐项审计及运行验证应关联到本次报告，不能仅用压缩属性推断功能完整。
