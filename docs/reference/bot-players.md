# 电脑玩家（bot）规格

2026-10-01。状态：用户已要求加入基础人机；本页定义行为和后续设计责任，当前没有电脑座位、策略实现或通过记录。产品范围见 [需求基线](../requirements/TableMax_需求文档_v1.0.md#55-电脑玩家与基础决策)，重要变更见 [决策 003](../decisions/003-bot-and-maintainability.md)。游戏 bot 是对局中的电脑玩家，与 `docs/subagent/` 的开发协作 agent 无关。

## 已确认范围

- 首版必须支持添加电脑玩家；后续接入游戏同样提供覆盖全部游戏选择的简单策略。策略只需合法且可完成游戏，不要求最优、深度搜索或特定胜率。
- 每款游戏独立维护电脑决策文件，和规则执行、独立计分分开。策略可以按实际复杂度拆成小文件，但应有清楚的统一入口和版本。
- bot 在本地服务端运行，随程序本地构建与打包；正式游戏不依赖云端模型、联网服务或手机 App。
- bot 与真人遵守相同的游戏规则、合法动作和信息权限，其决定与真人决定共用权威动作和恢复流程。

B01 已采用独立 TypeScript 模块的项目默认方案，理由、边界和非产品承诺见 [决策004](../decisions/004-phase02-game-spec-and-bot-file.md)。首版逐节点入口、策略版本／授权／恢复及异常见 [游戏人机规格](../games/pokemon-encounters/bot.md)。策略实现仍属第五阶段，当前没有正式 bot 代码。

## 电脑座位与交互

房主可以管理电脑座位，默认在大厅开局前添加／移除；座位具有稳定标识、昵称和电脑标记。真人加电脑的总人数及开局条件以核验后的游戏规则为准。关闭手机加入不等于允许超过游戏人数；电脑不通过二维码取得玩家身份，也不向手机下发内部控制能力。

电脑参与对应游戏的准备和初始化选择，不能因没有手机而跳过选位、翻牌等步骤。只有准备与必要规则选择完成后才可进入相应阶段；界面显示电脑当前行动、等待或错误原因，动作结果在服务端保存后确认。

进行中新增玩家或切换真人／电脑控制者需要游戏明示支持并由房主执行。当前新增要求不自动授权随时改变对局人数；是否进一步支持中途接管在对应游戏流程确定时说明。掉线真人保留座位并等待重连，不自动转为 bot。

## 全部游戏选择的覆盖

“所有操作”指每个需要玩家作决定的游戏节点，包含本人初始化、普通行动、目标和参数、可选能力发动／放弃、强制能力的合法选择、其他玩家动作引发的被动响应，以及多步流程的后续选择。查看帮助、界面缩放、管理暂停／回退不是 bot 的游戏决策职责。

每款游戏维护逐选择覆盖表，至少写清节点与规则依据、可观察输入、动作及参数范围、简单选择方法、无合法目标的规则处理、预期结果和验证场景。已确认规则列明确策略，未知规则继续保留阶段缺口；不能用“选第一个”代替尚未定义的动作参数、信息权限或规则。

优先采用易解释、可独立验证的简单选择。合法动作和参数必须由规则／契约确定，策略不能通过试探未授权目标、读取完整牌库或调用秘密规则状态来筛选结果。规则自动处理的随机事件和结算由规则引擎完成，不伪装成 bot 策略选择。

## 授权输入与独立决策文件

建议通过游戏 SDK 定义受限策略上下文：该座位的授权视图、规则允许的可选动作／参数、当前决策标识及平台提供的策略随机源。具体接口签名在第三、四阶段依据真实选择确定；现有 SDK 未提供完整策略契约，不能把规划写成既有 API。

决策文件只返回动作意图，不持有数据库、连接、房主凭证或完整 checkpoint，不直接修改状态。服务端运行在同一进程不授予策略额外信息；管理界面的调试显示也不扩展正常 bot 输入。临时查看和策略记忆只保留游戏允许获知的内容，回退时按定义恢复，不沿用被撤销分支的额外记忆。

每个策略需声明稳定策略标识、版本、适用游戏／规则版本、输入与返回动作约定，以及是否有记忆、其普通数据格式和恢复兼容方式。当前默认独立 TypeScript 策略模块，B01 已落定；替换策略的构建和版本检查写入接入指南，不承诺运行中任意加载外部脚本。

## 调度、暂停与失败处理

1. 平台根据已保存权威状态判断当前有哪些电脑决策，绑定对应座位身份和当前游戏实例、阶段、修订／历史分支。
2. 生成对应授权输入并运行该游戏策略；多个待选玩家按规则允许的次序调度，单个座位不重复发起相同待决策任务。
3. 将返回意图送入统一校验、动作队列、去重和事务保存流程；保存完成后才能展示成功及推进后续选择。
4. 等待人类、暂停、回退或结束时，停止不再合法的调度；迟到结果再次校验决策与分支，不能替新阶段或真人提交。
5. 限制单次计算与连续自动推进，保留主机暂停／管理响应；策略异常、缺失或给出非法意图时显示安全原因并停止该次推进，不无限重试或偷偷切换策略。

具体计算预算和显示节奏在实现时验证，不新增真人行动时限。若设计回退策略，必须事先定义、验证并明确提示；不能为了掩盖策略错误直接修改游戏状态、越过规则或伪造成功。

## 随机、回退与存档

游戏的洗牌、抽牌与随机事件继续使用可恢复规则随机源。策略若随机挑选合法意图，应使用平台提供的独立策略随机状态，不直接依赖 `Math.random()` 或时钟，也不消耗未声明的规则随机序列。

电脑座位类型、策略标识／版本、恢复所需记忆和随机状态纳入存档。游戏 checkpoint 同时涵盖相关策略恢复数据，使相同边界和输入下的简单策略可复查。所有数据使用普通可序列化结构；定时器、运行对象、函数或计算中的 Promise 不入档。

回退作废旧任务与结果，恢复策略数据，再以新的递增修订／分支计算意图。座位身份和平台授权沿用既有不倒退约定，不能恢复旧网络身份或编号；策略观察和记忆按游戏边界恢复。结束后不再自动行动。

重启先完成存档兼容检查和权威状态恢复，再按房主恢复／暂停状态启动电脑调度；真人仍等待原有身份恢复。缺少原策略、版本不兼容或记忆无法恢复时保留原存档、明确提示，不默默改用另一策略重新随机。

## 代码组织与适度封装

策略、规则和计分按各自职责独立；平台只依赖抽象策略契约，注册入口组装具体游戏和策略。具有生命周期的调度器和依赖适配可适度使用对象，简单策略可为纯函数，不能为了人机引入巨型继承树或将 UI、存档和规则塞进策略类。

代码组织原则见 [工程结构](architecture.md#面向对象与适度封装)。新增接口须有实际节点依据，不先建立空工程或改写已经归档的第一阶段验证记录。

## 阶段与验证责任

| 阶段     | 新增责任                                                          | 完成证据                                     |
| -------- | ----------------------------------------------------------------- | -------------------------------------------- |
| 第二阶段 | 逐节点覆盖、授权输入、策略数据／异常语义、电脑 UI 及封装职责（B01 已采用TS默认） | [首版主题规格](../games/pokemon-encounters/README.md) 已交付；规格与原型走查通过，真实策略未实现 |
| 第三阶段 | 座位类型、房主添加／移除电脑、人数／准备、策略契约与授权绑定      | 房间与权限验证；待实现                       |
| 第四阶段 | 统一 bot 调度、取消与旧分支校验、去重／事务、记忆／随机恢复、模板 | 平台异常与回退／重启验证；待实现             |
| 第五阶段 | 首版独立决策文件、全部实际选择、混合人机整局                      | 逐节点策略与固定种子整局验证；待实现         |
| 第六阶段 | 正式离线包、人机权限、策略替换、故障与恢复验收                    | AC-19 至 AC-23 及既有适用 AC 记录；待验收    |

验证同时覆盖正常、无目标／可选放弃、强制选择、多步／被动响应、越权输入、非法参数、重复意图、暂停与结束、回退后的旧计算、重启恢复、策略失败及版本不兼容。全选择覆盖需由逐节点验证证明，少数完整对局不能替代边界场景；固定种子整局检查策略能实际推进，不以单个合法动作输出宣称完整人机可玩。

人机权限隔离测试检查输入与日志，而非只检查页面隐藏。原型演示、规格表、测试定义和实际产品验收分开记录；真实命令与证据在实现后补到 [开发说明](development.md)，现有检查没有证明 bot 已完成。
