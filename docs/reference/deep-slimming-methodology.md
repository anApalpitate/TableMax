# 深度瘦身方法论

本页从实际历史对话及逐文件退役证据提炼方法，说明如何在保护项目内容的前提下大幅减少逻辑体积。容量触发、执行权限和停止条件的唯一规则在[工作区维护](workspace-maintenance.md#容量触发与深度瘦身2026-10-15)；工具参数在[维护工具](../../tools/maintenance/README.md#人工深度瘦身)，实际轮次在[瘦身记录](project-slimming.md)。本页不把历史命令当作新的执行请求，也不把文档编写当作本轮清理。

深度分支使用十进制GB：完整逻辑体积 `B > 15,000,000,000` 字节时必须优先启动审计，完成目标为 `B < 6,000,000,000` 字节。未触发时沿用日常超过10GiB清至8GiB或安全候选耗尽的规则；二者不能相加执行或混用统计口径。

## 大幅缩小体积的主要来源

**优先退役重复的完整运行环境。**一次隔离验证往往复制 Node、桌面程序、网页、资源和模块，再产生浏览器 profile、测试库与截图。很多这样的副本累积后远大于正式产品资源。历史审计曾识别约 6.78 GB 隔离临时内容和约 5.6 GB 过期打包副本；这些是当时的候选估算，不与最终删除量重复相加。

**再处理过期证据的派生部分。**历史原包、文字结论、失败原因和哈希应保留或按授权审计退役；运行副本、派生资源和历史截图可按精确清单处理。当前验收与历史验收分开，不能因为都在 artifacts 就采用相同删除规则。

**需要保留的机器记录可做全文无损归档。**2026-10-13对历史报告及不再原位使用的冻结 JSON 保存完整成员、原路径、字节和 SHA，并核验归档解压结果；显式复查旧构建前按索引恢复。不能仅留摘要取代原记录，也不能把 ZIP 移到统计范围外冒充瘦身。当前快照、指针和启动／旧局恢复所需文件仍原位保留。

**保持产品资源质量。**空间分析曾记录正式产品位图仅约 14.16 MB，缩小它们不能解决多 GB 的运行副本膨胀。原图、音频、规则资料和已采用运行资源受保护，不因容量目标有损重编码或删除。源码重构、运行包压缩与工作区清理各有验证边界，不混成一次瘦身成果。[分析依据](../../tools/analysis/storage/README.md#图片保存策略与分析边界)

## 先测量，再分类和预算

1. **确认根与现场。**记录项目绝对根、Git 状态、当前交付指针及活动工程进程。可以先只读审计，但主线程或产品正在运行时不得进入 Apply；不能停止别人的工作来取得空闲条件。
2. **扫描一次，复用快照。**先收集普通文件路径、长度、修改时间、链接、嵌套仓库和错误；按目录、扩展名、大文件与重复运行时聚合，不反复全盘扫描。读取失败的部分统计不能认定为完整容量。
3. **补齐完整项目口径。**现有空间工具默认跳过链接和嵌套仓库。逐个对未重叠的实际嵌套根只读计量、加回主根总量，同时保护这些仓库不删；链接不跟随到目标重复计量。保留源码、主 Git 元数据、依赖、缓存、报告和归档的实际长度，不为达标新增排除项或挪出目录。
4. **从最大的已结束副本开始。**先看已结束运行／提取环境、过期载荷、测试 profile 和历史图；再看同字节派生资源与可归档记录。按预期收益排序，但大小、旧日期、目录名或 Git 忽略都不是删除依据。
5. **先做足安全预算。**设当前完整逻辑体积为 B，严格低于 6 GB 至少需要净减少 `B - 6,000,000,000 + 1` 字节，另考虑归档、报告、文档与并发写入的增长。候选不足时继续只读追溯来源，不能先删一批再自动追加另一轮。

Node的`lstat().isSymbolicLink()`可能漏报带`Global\<盘符>:\`目标的Windows Junction。遇到原生ReparsePoint与Node分类不一致时，用原生文件属性做完整不跟随遍历，将全部链接及其目标补入保护；不能把链接内文件作为普通副本删除。比较前后容量必须使用同一完整口径，旧Node采样只保留为审计，不与修正后的原生终值相减。原始目标表示和规范保护目标分别绑定，不为统计修复测试链接。

采用[空间分析工具](../../tools/analysis/storage/README.md)的 scan／analyze 和有必要时的 SHA 重复判断；命令只在工具索引维护。发现同大小／同名文件只说明值得核验，不说明可以删；完整 SHA 相同还须确认保留原件与引用。

## 形成一个可执行的冻结清单

在删除前建立保护基线：当前交付及恢复依赖、原件和正式存档的精确文件，必要时登记 SHA 与修改时间；绑定实际指针、快照、清单、来源报告、入链目标和归档。每个待删普通文件必须有精确相对路径、字节、UTC 修改时间、SHA、来源类型和退役理由。

私钥与凭证始终排除在退役清单之外；保护仅记录所在范围及必要的访问控制，不读取其内容、计算哈希或写入报告。容量统计可计入普通文件长度，不能为了重复判断扫描秘密内容。

混合目录逐文件列举；未列成员不受影响，空目录只在确认无未列内容时清除。对引用同 SHA 原件的副本，记录保留位置；对完整归档记录，绑定 ZIP 自身哈希及成员证明。修复文档与报告引用时保留原版完整记录，不回写历史通过、失败或时间。

预览应明确显示候选、保护与跳过原因。只在来源和预算完整、工程退出、近期保护满足且预览通过后冻结清单 SHA；没有资格的路径从清单移出，不能关闭保护。历史预览曾拒绝把目录冒充文件的项目，正确做法是修正清单后重新预览，而非降低校验。

## 一次 Apply，失败就保留现场

通过已有逐文件入口，以预览绑定的清单 SHA 执行唯一一次 Apply。开始删除即消耗单次 ID；删除前及过程中复核当前交付、每项路径、链接、成员变化、进程、共享互斥和 30 分钟近期修改。

遇到新工程进程、文件变化、占用、未知成员、错误归档或保护失败立即停止，保留已经完成的结果和剩余项。不得换 ID 续删同一失败清单、不自动重试、不降低近期保护、不结束其他任务进程。同一轮深度清理结束后不叠加日常 Maintain-Project 的第二次删除。

普通临时副本直接退役，不为它们复制「恢复归档」。需要保全全文的历史机器证据使用前述正式无损归档，这是保留资料的存储方式调整，不能拿它给所有待删内容再建备份；tmp 不存恢复档案。

## 收尾证明与完成标准

- 一次最终完整逻辑容量统计，计入嵌套仓库、归档和当时已有新记录，列采样时间与扫描错误；NTFS 实际分配量单独列，不代替逻辑目标。
- 从执行日志统计实际删除文件数与字节，另列同口径前后净变化；不得以候选容量或前后差值替代执行记录。
- 对保护基线复验 SHA／修改时间及冻结引用；验证保留原件／归档成员、链接、当前图片引用和剩余清单。预期文档编辑单独登记，不把它混同受保护内容意外变化。
- 修复已退役包与图片的链接，记录原因、逐文件 SHA、实际结果及未达标范围；保留历史原结论，不为文档收尾重打包产品。
- 只有完整逻辑体积严格小于 6,000,000,000 字节且保护核验通过，才能宣布达到目标。候选耗尽或被保护阻止时应记录未达标，不能为了数值删除唯一资料或正式数据。

本页历史数字不是当前项目容量。本轮方法与规则文档更新未做全盘容量扫描，也未执行任何删除、移动、压缩或归档。此前安装任务的一次维护结果集中见[瘦身记录](project-slimming.md#windows安装交付任务单次维护2026-10-15)，不因后续正式验收待完成追加本轮删除。

## 减少再次膨胀

通过现有增量构建、按内容复用内部包、单次同包会话、准确范围验证和成功证据复用减少完整运行目录复制。未来若要共享提取缓存，必须先实现实际包哈希、成员完整性、并发锁和数据隔离，不能把方法建议写成现有能力。

截图先完成全部断言，再按当前／失败／关键边界保留代表；一般预览采用已有合适编码策略，不改验收原图或原素材。开发依赖、工具缓存和原包各保留真实职责，避免为了短期小体积造成下轮全部重新下载或重建。

每轮结束及时登记临时副本、活跃状态和清理责任，正式结论归文档／报告、可再生副本归 tmp。发现总量异常时先按最新快照定位增长来源，尤其重复 Node、浏览器 profile 和高 DPI 截图；不用长期累积副本替代可追溯证据。
