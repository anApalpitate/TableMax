# Release流程与发布约定

2026-10-10同版本附件替换授权：用户明确要求重新导出并只替换原v1.0.5的附件，因此本轮保持Release标题、正文、版本与已有标签对象，上传完整EXE及从本次已验证源码提交导出的source ZIP。源码提交与保留的旧标签对象映射记录在本地发布审计，不移动标签、不新增Release，也不上传运行ZIP或JSON。本条是此次明确授权的同版本替换边界；后文新版本发布流程仍适用。

本页统一维护本地交付和GitHub Release的流程、前提与事项。工具链、增量构建、运行和安全清理的具体实现见[开发环境](development.md)，当前实际交付与未验证边界见[验收记录](acceptance.md)。本页是操作规范，不表示某版本已完成或已发布。

## 发布范围与版本

- 日常本地导出只生成运行ZIP和逐文件清单；明确发布到GitHub时才封装完整EXE、导出源码ZIP并创建Release。
- 未获用户明确新版本指示时沿用当前版本号。同版本重新导出保留旧文字结论、实际包哈希和构建边界，新包单独验收。
- 本地打包、提交或推送均不等同GitHub发布授权。用户只要求更新流程或文案时，不执行线上发布、改标签或替换附件。
- 保护其他任务未提交／暂存内容。发布源码与运行输入必须一致，不能把未完成工作混入发布提交；共享工作区的隔离构建办法见[开发环境](development.md)。

## 本地交付

1. 明确本轮范围、版本和适用验收，完成相关专项检查；开发期间仅构建受影响单元，冻结运行源码与资源后再构建正式包。
2. 默认执行 `pnpm package:win`，该入口包含生产构建。若本轮明确要求一次全量生产构建，先执行下列第一条命令，再用它返回的冻结清单执行第二条，避免重复编译：

   ```powershell
   node tools/build/build.mjs --production --full
   node tools/release/package.mjs --snapshot=<本轮冻结清单绝对路径>
   ```

3. 对生成的同一ZIP核验实际解压、逐文件字节与SHA-256、包内Node、本地资源、适用游戏加载／切换／恢复、离线外部请求及进程退出。实际界面和动态验收应来自该包；源码样板、旧包结论不可代替。
4. 核对运行ZIP与实际解压程序均严格小于120,000,000字节，遵守114MB工程预算及各模块预算。超出先优化，不自行上调。系统共享运行时、用户存档和缓存不计入交付大小。
5. 更新当前验收入口，绑定ZIP哈希、逐文件清单、证据和未测事项。测试窗口默认静音，包括游玩模式自动验证；专门试听显式开启。

本地产物为 `artifacts/releases/TableMax-<版本>-win-x64.zip` 与 `TableMax-<版本>-win-x64-manifest.json`。组装遇到进程占用时先遵守现有门禁，待占用解除后可用同一有效快照恢复；不得为通过门禁擅自结束用户日常程序。

## GitHub发布

仅在用户明确授权GitHub发布后执行以下步骤。

1. 确认本轮运行ZIP已通过验收，执行 `pnpm package:release`。此入口将已验ZIP封装为 `TableMax-<版本>-win-x64.exe`，不代替运行ZIP验收。
2. 执行 `node tools/release/verify-shipping-executable.mjs`。验证实际提取发布EXE、逐文件哈希、重复启动复用、实际资源目录体积及提取程序的原生安全行为。EXE验证后发生改变必须重新验收。
3. 整理本次源码、文档和更新说明，完成适用检查并提交最终发布源码；核对冻结运行输入无未提交差异。推送该提交和对应 `v<版本>` 标签，标签必须指向发布提交。已有同名标签或Release时先核对现状，不强推、不擅自覆盖历史。
4. 按下节格式准备已审阅的更新说明文件，执行 `pnpm release:github -- --notes=<说明文件路径>`。当前入口核对EXE验收证据、HEAD与标签一致、远端标签和已提交运行输入；随后从最终提交执行 `git archive` 生成源码ZIP、创建Release并上传附件。
5. 发布后核对线上标题、正文、标签、正式／预发布状态及附件名称、数量、大小与SHA-256。保存本地发布记录并更新验收入口；失败记录保留，不把部分上传写成发布成功。

当前 `package:release`、发布入口及默认EXE检查共用 `artifacts/maintenance/v<版本>/github-release-20261005/` 证据目录；该目录名是现有工具路径，不代表新版本的发布日期。EXE检查可用 `--evidence=<独立名称>`，但当前发布入口仍读取默认目录；使用独立证据时不能宣称发布入口已经自动采用。

### 附件与运行事项

GitHub Release仅上传以下两份文件，名称沿用v1.0.2风格：

1. `TableMax-<版本>-win-x64.exe`：完整可运行的单文件程序。
2. `TableMax-<版本>-source.zip`：由该发布提交的 `git archive` 导出。

JSON清单、运行ZIP、截图和过程报告留在本地，不上传。GitHub自动提供的仓库源码下载不属于手动上传附件。v1.0.1历史运行ZIP附件保留原发布边界，不因为新约定改写旧结果。

v1.0.3单EXE默认在旁边新建 `TableMax/`，运行资源位于 `TableMax/app/`；ZIP解压版直接使用解压目录。配置、存档、设置、日志和浏览器缓存由对应根目录内 `TableMax.config.json` 指定，不可写时不回退C盘。启动器只更新带有效标记的资源目录，未知文件或占用时拒绝替换，暂存失败回滚；旧数据保留，目录更换需重启。平台条件和迁移细节见[便携存储与启动迁移](development.md#v103-便携存储与启动迁移2026-10-06)。这些运行说明属于项目文档，不重复放进更新正文。

## Release标题与更新正文

2026-10-07用户要求：标题和附件文字沿用 [v1.0.1](https://github.com/anApalpitate/TableMax/releases/tag/v1.0.1)、[v1.0.2](https://github.com/anApalpitate/TableMax/releases/tag/v1.0.2) 的简洁风格，正文只写更新内容，先总结，再用有序列表简述。

- 标题固定为 `TableMax v<版本>`，不追加宣传副标题；历史标题末尾空格不作为新格式要求。
- 首段一至两句概括本版最主要的变化。
- 下方采用 `1.`、`2.`、`3.` 的有序列表，每项用一句话说明一组用户可感知的新增、优化或修复；只写本版已经交付的变化。
- 不重复常驻功能，不列开发流水账、测试数量、构建路径、哈希、体积、安装步骤、附件说明或内部维护记录。不将计划或未完成事项写成已发布更新。
- 发布说明使用真实换行，上传通过 `--notes-file`，避免命令行转义破坏格式。既有v1.0.1／v1.0.2正文保留其历史记录；本次新格式用于后续发布。

格式示意（方括号内容在发布前替换）：

```markdown
TableMax v[版本] 本次更新重点完善[主要变化]，并优化[相关体验]。

1. [新增内容及用途。]
2. [界面或操作体验的变化。]
3. [重要修复及结果。]
```

## 收尾与保留

全部工程进程退出后，按[安全清理入口](development.md#清理本地中间物)先预览、核对再应用，退役过期组装、解压及验证副本，检查项目逻辑体积并记录实际结果。超过10GiB时目标8GiB或安全候选耗尽；本轮用户另有明确目标时按该目标审计，保护范围不扩大。

日常release目录仅保留当前已验证运行ZIP与逐文件清单；明确发布时另保留当前完整EXE与source ZIP。当前交付及验收证据、原素材、规则资料和正式存档继续保护，历史退役保留结论、失败原因、哈希和删除记录并修复文档引用。已结束清理记录原样集中归档，执行结果归[项目瘦身](project-slimming.md)，不在本页复制每轮过程。
