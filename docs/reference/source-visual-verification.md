# 源码视觉验证（无需安装器）

本流程直接验证工作区中的 React 界面，不构建或运行完整安装器，不调用应用内更新器或下载器。它适合 UI 改动后的布局、文字、截图和触控交互回归；结果对应本次源码和模拟环境。

默认按[验证范围规则](validation.md#按变更范围选择检查)选择此流程；只有用户明确要求本次构建新的导出包，才进入安装器相关验证。规则与保存变化另配对应游戏的单测及直接 Socket／SQLite 测试。浏览器环境阻断时保留失败证据并纠正环境，不改走安装器。

## 执行方式

从项目根目录运行。脚本会用 Vite 将当前组件及其依赖临时构建到 `tmp/`，绑定 `127.0.0.1` 提供夹具页面，以 Playwright 启动隐藏、静音的 Microsoft Edge，模拟视口和触控，逐项检查并把截图与 JSON 报告写入指定的全新证据目录。临时构建和浏览器页面均为本机过程，不会访问产品下载服务。若 Edge 在当前桌面／沙箱会话无法启动，报告会失败且不会有布局或截图结果；不能把 Vite 成功打包当作视觉验证通过。

马尼拉目前分成三种互补覆盖：

```powershell
node tools/test/games/manila/verify-manila-design.mjs --evidence=<唯一名称>
node tools/test/games/manila/verify-manila-harbor.mjs --evidence=<唯一名称>
node tools/test/games/manila/verify-manila-touch.mjs --evidence=<唯一名称>
```

`design`现有检查仍覆盖主机、公共屏、手机，属于独立公共屏取消前的工具矩阵，待随实现迁移；其公共屏结果不能证明管理兼展示目标已通过。`harbor`检查手机港湾状态、布局边界及交互，可用 `--only=<检查组,...>` 和 `--widths=320,390,430` 收窄；`touch`覆盖手机触控、旋转和横屏状态。名称须为新的安全名称，脚本不覆盖既有证据。参数以各脚本当前实现为准，不能把尚未支持的角色筛选写成可用命令。

## 依赖和构建可行性

需要项目锁定的 Node.js 22.14.0、已安装工作区依赖（Vite、React、Playwright）及本机 Edge/Chromium。`design`、`harbor`、`touch`各自直接调用 Vite API，不依赖 `pnpm build`、Windows C# 桌面构建、签名、完整 EXE、安装器、标准账户或在线更新服务。若通过 `pnpm` 启动而 Corepack 尚未缓存锁定版本，Corepack 可能先尝试下载 pnpm；可直接执行上面的 `node` 命令绕过该包管理器引导步骤，但项目依赖本身仍须已安装。

检查输出的 `result`、错误和失败列表，并打开本轮证据目录核对 PNG 与 `screenshot-index.json`。设计报告在 `artifacts/manila/validation/<名称>/`；harbor 与 touch 报告在各自脚本报告的 maintenance 子目录。脚本会创建临时目录及新的证据目录；运行前确认目标证据名未使用。

## 三类布局的后续验证矩阵（2026-10-23）

后续布局改造按[三类布局规范](visual-design.md#三类布局与宽高比适配2026-10-23)选择代表尺寸、最小支持尺寸、切换边界及宽／高留白场景；相近且行为一致的视口归组，按任务影响选择角色与游戏。2026-10-24当前源码只保留管理兼展示与玩家；新矩阵不再要求独立公共屏，而须核验管理窗口的公开牌桌、按需管理入口及玩家私有操作。SDK的`public`公开投影和匿名wire继续保留，秘密隔离仍由对应服务／权限检查证明。保留短屏、最高人数、密集内容、浮窗、字号／热区、旋转及未提交草稿检查；4K、DPI与实体设备的必要证据继续适用，实际通过范围见[验收](acceptance.md#当前源码与本地交付)。

当前脚本、已有视口与旧报告不会因规范入档自动变成新矩阵或新通过证据；实施时须核对脚本实际覆盖，补齐受影响场景并记录具体尺寸、布局规则、角色和源码版本。本次文档更新未执行界面改造或重新渲染验收。

## 证据边界

固定构图模式复用现有统一源码入口，按公共适配、实际游戏内容和连续接入三层选择；具体参数、已登记玩法与父运行器输出契约见[测试工具](../../tools/test/README.md#当前源码界面与离线审阅)。公共夹具通过不代表游戏内容通过，游戏三套基准也不吞并最高人数、密集局面、终局、秘密或交互专项。只有旧ID到新内容／公共／接入ID的逐项替代证据齐全，才合并重复尺寸项。

原生固定profile专项使用隔离源码开发壳及生产WebView2／React适配器，证明窗口事件与倍率接线；当前物理DPI、虚拟窗口尺寸和实体4K分别记录。它不构建完整installer，不改current冻结载荷，也不证明游戏服务、自然整局或实体手机。

这些报告验证当前源码在桌面浏览器的模拟视口、触控事件和夹具状态下的渲染与交互。它们不证明物理手机、Safari、真实 DPI、真实服务通信或安装后的 EXE。需要证明候选安装器、系统登记、更新／卸载和数据保全时，仍按[正式安装验收](acceptance.md)单独执行；源码视觉证据不能替代安装验收。

## 常见问题

### 这套流程会下载或安装产品吗？

不会。脚本从工作区源码构建临时网页夹具，仅在 `127.0.0.1` 提供页面；不会构建、下载或安装 TableMax 完整 EXE，也不会调用应用内更新器。需要正式安装证明时，仍须使用独立的安装验收流程。

### 为什么不直接运行 `pnpm` 命令？

仓库锁定了 pnpm 版本。若当前机器的 Corepack 尚未缓存该版本，`pnpm` 会先尝试获取它；这与产品下载器无关。绕过 Corepack 可直接运行文档中的 `node tools/test/...` 命令，但 Node 版本和项目依赖必须已准备好。

### Vite 构建完成了，为什么报告仍然失败？

视觉脚本还必须启动 Playwright 控制的 Microsoft Edge，打开夹具页面、运行断言并截取图片。若 Edge 因当前桌面会话、沙箱或浏览器环境问题无法启动，Vite 打包完成也不会产生有效的视觉通过结果。检查报告的 `result`、`failures`、错误日志，以及是否有 PNG 和 `screenshot-index.json`；启动失败时应先修复浏览器运行条件，再用新的证据名称重跑。

### Edge 启动失败是否说明 UI 或安装器有问题？

不能这样判断。浏览器进程无法启动属于验证环境问题；它没有执行页面断言，也没有检查安装器。保留这次失败报告用于说明环境阻断，不要把它记为布局断言失败或安装器缺陷。

### 怎样确认这轮验证的是最新源码？

报告会保存验证器源码副本和哈希，具体脚本还会记录检查输入及其哈希。结合运行时的工作区状态和对应报告核对；已有旧报告只能代表其报告绑定的输入，不能自动代表现在的代码。

### 证据目录已经存在怎么办？

选择一个全新的 `--evidence` 名称。脚本采用新目录写报告，不应覆盖旧证据；失败报告也保留，下一次修复后用新名称记录。

### 这些截图等于真实手机验收吗？

不等于。手机宽高、方向和触控由桌面浏览器模拟；截图可用于审查源码布局和交互，但不证明真实设备、移动浏览器、物理 DPI、局域网连接或安装后的界面。
