# TableMax 固定构图与视觉验证收敛落地方案

状态：2026-10-25用户已明确授权按下列计划实施；首轮现代艺术360×640竖屏失败已留证，用户随后选择360×800重新试点。本轮现代艺术源码试点通过，公共可见区域修复与原生接线通过，正在进入宝可梦原版及扩展；两版均通过后才冻结参数并进入后续玩法。源码与模拟证据不替代实体设备或整体迁移完成。

本文由[任务索引的三类布局入口](README.md#后续独立范围)导航。实施完成后，长期契约归入现有[视觉规范](../reference/visual-design.md#三类布局与宽高比适配)和[验证规范](../reference/validation.md)，任务过程归档；不另建一套长期规格或验证统计。

## 一、目标与现状

目标是减少各游戏重复处理屏幕尺寸、重复验证布局的工作量，保留三套构图：

- 管理兼展示横屏。
- 玩家竖屏。
- 玩家横屏。

当前[统一源码矩阵](../../tools/test/platform/verify-public-screen-retirement-ui.mjs)的正式游戏布局为管理1280×720／1920×1080、玩家390×844／844×390，共4种组合；各游戏专项另有额外尺寸，尚未形成统一的固定画布契约。工具覆盖及证据边界见[当前源码界面与离线审阅](../../tools/test/README.md#当前源码界面与离线审阅)。

新方案采用“固定逻辑画布＋公共适配器＋分层验证”。不承诺所有机型仅靠比例即可兼容，也不把原先56个场景视为56种视觉类型。场景总数与构图数量分别计量，不将不同检查轮次、游戏范围或局面组合的数量直接相减作为收益。

| 项目                       | 原验证面                              | 新验证面                                      |
| -------------------------- | ------------------------------------- | --------------------------------------------- |
| 游戏构图                   | 每个玩法至少4种统一尺寸，另有专项尺寸 | 通过迁移验收后，每个玩法以3套基准构图验证内容 |
| 屏幕比例变化               | 各游戏分别响应断点                    | 公共适配器处理缩放、居中和边缘填充            |
| 最多人数、长名称、复杂操作 | 各游戏验证                            | 继续由各游戏验证                              |
| 安全区域、旋转、动态高度   | 分散处理                              | 公共层集中验证，保留游戏接入检查              |
| 实体手机与浏览器差异       | 专项证明                              | 继续独立证明，不由模拟视口替代                |

收益重点是后续定向复验与证据复用；首次迁移需要新增契约检查，工作量可能增加。

### 基准数量与场景数量（2026-10-25核对）

“布局类型”是三类空间组织规则；“玩法×基准构图”是需要分别审查的内容组合；“场景”还包含页面、局面、人数与交互状态。同一构图包含多个场景，以下数量不能互换。

当前源码为8款游戏、9个玩法，宝可梦原版与扩展分别计数；其余为现代艺术、电力公司、拉密、UNO、阿瓦隆、马尼拉、德国小强。来源为[游戏索引](../games/README.md)和统一脚本的`variants`。游戏清单变化时先重新计算，不沿用本节数字。

| 计数对象          | 当前统一矩阵                                                 | 迁移通过后的目标                                              |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------- |
| 布局类型          | 管理横屏、玩家竖屏、玩家横屏                                 | 仍为3类，不新增权限角色                                       |
| 每玩法的基准组合  | 管理1280×720、管理1920×1080、玩家390×844、玩家844×390，共4组 | 每玩法3套基准构图；尺寸待试点冻结                             |
| 9个玩法的基础组合 | 9×4＝36组                                                    | 9×3＝27组                                                     |
| 盒子基础组合      | 当前统一脚本另列4个场景                                      | 按3类布局接入；若各取1个基准，为3组，最终页面／状态清单待冻结 |

27组只表示游戏内容的基础覆盖。加上盒子的3组可得到30组基础组合，但30不是全项目最终验收场景数，也不包括公共适配器的边界检查。

当前统一脚本未传`--only`、使用`phase=after`时声明56个场景：玩法基础36、阿瓦隆终局4、盒子4、原型入口4、管理界面2、管理入口普通状态3、等待状态3。`phase=before`为52个场景；定向筛选后的执行数另计。这是2026-10-25读取脚本得到的清单数量，不是本轮执行或通过数量，也不包含各游戏专项矩阵。

未来总场景数由游戏局面、盒子／入口／管理状态、公共边界及必要接入场景逐项列出后确定。不得以56－27或56－30报告节省数量；可比较的仅是同范围基础组合36→27，减少9组（25%），该算术结果不代表测试耗时或总工作量降低25%。旧脚本中的窄屏管理／入口检查也不得因管理构图固定横屏而直接删除，须先明确其访问与提示用途。

基线补充（2026-10-24）：宝可梦原版／扩展版的紧凑布局修复已提交为`05fddd70`，68个专项源码场景的范围见[游戏验收记录](../games/pokemon-encounters/validation-scenarios.md#紧凑布局源码验收2026-10-24)。这属于已完成的单游戏工作，不代表本方案的公共适配器、固定画布或全游戏迁移已实施，也不与上述原统一矩阵的场景数混计。

## 二、布局与接入契约

### 已采用的实施选择（2026-10-25）

以下来自本聊天的明确选择及随后完整实施授权，是本任务的方案决策，不写入个人美术偏好。

- 支持范围内严格固定构图；真实窗口只改变留白、位置和布局选择。游戏必要的地图、牌架及详情浏览继续保留。
- 显式玩家偏好放不下时，先回退到能容纳的另一构图；两者均不足时保留原尺寸与完整滚动访问，不能缩字或裁操作，回退不覆盖保存偏好。
- 普通浏览器玩家按基准原尺寸居中，CSS倍率固定为1，浏览器缩放仍实际增大文字；不新增自动铺满或阅读模式。
- 管理端由真实原生WebView2独占倍率，保留1920×1080自动基准与100／125／150%、最高3倍；迁移页面使用1280×720容纳限幅，不叠加CSS拟合抵消设置。
- 新客户端仅通过可选`layout: { contract: 'fixed-v1' }`加入，`webHost 1`和旧`three-v1`不变。原生运行期profile为`legacy`／`fixed-host-1280-v1`，由平台可信顶层管理适配器选择，不落盘、不由游戏直接调用。
- 玩家选择区分`auto`／`portrait`／`wide`，只迁入确实存在的有效旧选择；自动方向切换采用150ms稳定窗口与5%滞回，不能容纳时立即处理。键盘仅改变高度时保持构图，但实际空间不足及焦点可达仍须报告／处理。
- 若试点只能靠缩字、隐藏必要信息或裁操作通过，停止后续迁移并交付失败证据和尺寸修订方案，不自行改为弹性重排。

### 已确认范围与待冻结决策

[现行视觉规范](../reference/visual-design.md#三类布局与宽高比适配)确认三类布局及权限分离；用户本次已授权试行严格固定逻辑画布，代表尺寸仍须经真实内容试点后冻结。试点失败按上述退出条件交付，不以实施方案反向覆盖可读性与操作要求。

实施前记录以下决策及依据，试点通过后再冻结：

- 三类内容区尺寸、最小支持窗口、最大放大比例、横竖选择与切换边界；边界须包含安全区、外框、浏览器动态高度和管理显示设置的影响。
- 自动选择的优先顺序、边界防抖和显式选择不可容纳时的回退／提示；两套均无法容纳时的完整访问方式。不得只按窗口宽大于高或设备类型判断。
- 浏览器缩放、Windows DPI、管理显示倍率与画布倍率的组合方式；分别记录CSS视口、内容区与物理输出，不用CSS缩放抵消用户的系统可读性设置。
- 页面与浮窗的坐标归属、滚动容器、键盘避让和焦点恢复；每个画布外元素须有明确的定位和可达性检查。

电脑客户端玩家模式只复用玩家横竖布局，不计为第四类。其加入入口、身份领取、管理／玩家模式切换及凭证隔离尚未形成实施方案，须独立定义并验证；布局迁移完成不能宣称电脑玩家功能完成，也不允许把管理员凭证交给玩家页面。

### 固定画布

用户已明确采用以下第二轮试点参数；仍须通过现代艺术与宝可梦两版试点后冻结，不作为用户个人偏好。首轮360×640失败证据见第七节，原记录不改写：

| 构图     | 基准逻辑内容区 | 用途               |
| -------- | -------------: | ------------------ |
| 管理横屏 |       1280×720 | 公开牌桌与按需管理 |
| 玩家竖屏 |        360×800 | 本人状态与主要操作 |
| 玩家横屏 |        640×360 | 横向组合本人工作区 |

尺寸指扣除安全区域及必要外框控件后的可用内容区。试点不满足可读性、触控或信息完整性时，保留失败结果并修订参数，不通过缩字、裁切或隐藏必要操作达标。

该测量口径与既有宝可梦360×640整页源码视口检查不同。试点须分别记录原始窗口、外框／安全区域扣减和实际内容区，确定对应的最小支持窗口，不能直接继承既有尺寸的通过结论。

- 画布内部保持固定逻辑尺寸；普通浏览器玩家原尺寸居中，管理窗口只使用原生倍率，剩余区域填充主题背景。
- 最小支持范围内不向下缩小画布，保证信息文字≥16、关键状态与主要动作≥18、电脑标题≥20 CSS px，触控目标≥44px。
- 小于支持下限时保留完整访问与明确提示，不静默裁掉内容，也不自动新增第四套构图。
- 牌桌、主要卡区和操作区使用稳定空间；空态、持牌、成功反馈和短状态变化不推动主体。
- 规则、记录和详情浮窗可独立滚动；地图平移、牌架整理及游戏必要的局部浏览继续按各游戏规则处理。

### 公共适配器

扩展现有外框能力，避免建立第二套独立外框。

- 输入包括可用内容区域、端侧、玩家布局偏好、画布配置及现有管理显示设置。
- 输出统一的布局类型、画布尺寸、缩放比例和边缘偏移。
- 管理端固定横屏；玩家端保留显式横竖屏选择，无显式选择时按可用空间选择，空间不足时安全回退。
- 管理原生倍率由未缩放DIP及已有设置计算，CSS画布倍率固定1，避免重复叠加或反向抵消；浏览器用户缩放不被自动拟合抵消。
- 浮窗、提示、焦点定位、拖动坐标和特效锚点必须使用相同坐标契约；不能只缩放主牌桌。
- 调整窗口或切换布局不得重挂载对局、重新入座、清除草稿或提交动作。

游戏仅消费布局类型和稳定的逻辑内容区。游戏内容、样式与资源继续内聚，公共层不按游戏ID分支。

试点须用可复查的输入／输出记录验证适配器：可用宽高与安全区扣减、用户选择、最终布局、逻辑宽高、原生倍率及CSS偏移。`min(可用宽/逻辑宽, 可用高/逻辑高)`只判断容纳能力，不作为浏览器自动CSS放大倍率。原生固定profile保留`requested=max(1,min(目标宽/1920,目标高/1080))×用户倍率`，再按未缩放内容区对1280×720的容纳上限及3倍限幅；不足最低1倍时进入完整访问及不足空间状态。

拖动与点击使用同一逆变换还原逻辑坐标，滚动、安全区和嵌套外框偏移只计算一次；须检查边缘命中与拖动终点。布局切换采用同一会话与状态，稳定组件身份，不能仅靠截图证明草稿未丢失。浏览器键盘出现时，应优先保证焦点与提交入口可达，避免可用高度的瞬时变化反复切换构图。

## 三、迁移顺序与退出条件

1. **冻结基线**  
   记录各玩法当前入口、布局条件、关键状态和真实截图。保留宝可梦已完成的修复，迁移时复核其最新源码并纳入基线；不覆盖其他任务未提交改动，也不把单游戏修复视作公共迁移通过。

2. **验证公共适配器**  
   先用包含长文本、按钮、浮窗、滚动和拖动对象的契约夹具检查坐标与布局稳定性，再接入真实游戏。

3. **完成两类试点**  
   现代艺术先验证已有布局接入与复杂表单；宝可梦原版／扩展在已完成修复的基线上，验证六人密集局面、卡牌正背和多阶段操作。试点通过后才冻结画布参数。

4. **逐游戏迁移**  
   后续按UNO／德国小强、阿瓦隆、拉密、马尼拉、电力公司推进；盒子与管理浮窗单独接入。每款游戏独立验收，不要求一次改完全部目录。

5. **收敛旧检查**  
   只有证明某项屏幕变化完全由公共适配器承担后，才合并对应游戏的重复尺寸检查。未迁移游戏、特殊交互和实体设备缺口保留原验证责任。

每批接续必须列明：负责文件与冻结源码SHA、迁移的玩法／页面、选用的构图参数、必要局面和检查ID、通过／失败／未执行项、旧检查替代映射及回退方式。两个试点包含现代艺术、宝可梦原版和扩展共3个玩法；不能把“两类试点”误计为2个玩法。尚未迁移的玩法沿用原矩阵，不能提前统一删减为3组。

每个迁移批次必须能够独立回退。旧发行、存档、公开投影、权限和SDK旧接口保持兼容；不恢复独立公共屏。

## 四、验证与证据复用

### 游戏层：3套构图，保留必要局面

覆盖最高人数、合法长昵称、初始／密集／结果状态、主要操作、错误与待确认，以及实际使用的浮窗。额外检查：

- 文字完整，无省略号、裁切、遮挡和不可达操作。
- 正背与空占位尺寸一致，状态变化前后主要区域稳定。
- 玩家秘密不进入管理投影、DOM或动画。
- 旋转、缩放与浮窗开闭保留草稿、连接及正确焦点。
- 拖动、触控、特效锚点与视觉位置一致。

### 公共层：按边界验证

覆盖基准尺寸、刚好可容纳与不足一像素的边界、宽／长留白、最大放大、布局切换、安全区域、地址栏变化、键盘及焦点。管理端保留适用4K与DPI检查。

首次接入的游戏还须检查非基准窗口，证明其构图没有随真实屏幕尺寸变化；通过后才允许复用公共层证据。

### 场景清单与旧检查替代条件

实施批次在现有报告／清单中逐项登记场景ID、玩法或页面、角色、布局、原始视口与实际内容区、合法局面／人数／名字、操作和断言、源码输入及证据位置。选定、实际执行、通过、失败、未执行和复用分别计数，复用不计新增通过；不为本草案另建运行器或统计系统。

游戏基础3组均须检查实际内容；初始、密集、终局及关键决策是否可以共用夹具由游戏语义决定。阿瓦隆终局等既有独立状态必须有明确去向，不能被27组基础组合吞并。盒子、管理界面、认证前入口和等待入口分别列状态，不能因同属管理横屏而视为同一个页面。

合并某个旧尺寸检查前，逐项记录旧ID及断言、新的游戏基准／公共边界ID、相同内容或行为的覆盖理由、真实渲染结果及输入版本。仅屏幕几何变化可由公共层承接；游戏内容溢出、权限、保存、特效和交互断言仍落在实际游戏／平台检查。首次迁移保留新旧对应结果，缺失替代证据的旧项继续执行或明确留为未完成，不能标为已合并。

公共边界清单至少分别列出三类布局的最小可容纳尺寸及宽／高各不足1 CSS px、放大上限、极宽／极长留白、手动选择与自动回退、连续旋转／缩放、安全区、地址栏和键盘变化。组合按风险选择，记录未覆盖项；这些边界类型不是已经冻结的执行项总数。最大人数和三种合法长昵称边界按[验证规范](../reference/validation.md#按变更范围选择检查)覆盖，额外游戏状态按各游戏既有专项确定，不全量机械相乘。

### 复验选择

| 改动                     | 必须复验                             |
| ------------------------ | ------------------------------------ |
| 单游戏内容或布局         | 对应游戏受影响构图与局面             |
| 公共缩放、坐标或布局选择 | 公共边界矩阵及实际依赖游戏的接入检查 |
