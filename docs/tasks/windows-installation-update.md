| R4   | 卸载整个 TableMax           | 默认移除程序、受管理快捷方式和安装登记，保留存档、配置、历史模块及用户额外文件；额外删除数据须单独明确选择并显示准确范围 |

R6 指已保存的玩家身份、有效授权和设置，不恢复已撤销凭证，也不保证旧连接或管理员临时 hostToken 保持原值；服务重启后仍按现有身份与管理员启动协议重新连接。

### 首版建议范围

优先支持一个安装范围、一套程序替换机制：**完整离线安装器 + 安装框架生成的卸载器 + 盒子检查／下载 + 用户明确重启升级**。在对局期间可以下载，应用更新建议只在盒子无进行中对局时开放，仍须建立保存关闭屏障。

首版不建议加入差分下载、运行中热替换、后台自动应用、常驻更新服务、计划任务、全机与单用户双模式、多实例管理、跨盘自动搬迁或用户主动降级入口。它们未被确定为本次要求；若后续纳入，应单独补范围和验收。故障恢复旧程序文件与产品级主动降级是不同能力。

### 保存、权限与恢复

- [ServiceProcess.Stop](../../apps/desktop/native/ServiceProcess.cs) 通过私有管道发 stop，等待 5 秒后可关闭 Job 兜底；目前没有返回区分「正常关闭并完成保存」与「强制终止」的结果。[DesktopContext.Quit](../../apps/desktop/native/DesktopContext.cs) 关闭窗口、服务并清理本程序 WebView2。
- [service.ts](../../apps/server/src/service.ts) 在 preClose 停人机调度、断开 Socket，再在 onClose 关闭 repository／storage；[RoomCoordinator.enqueue](../../packages/platform-core/src/room.ts) 有串行异步动作队列，但未提供明确的停止／排空接口。**源码推断风险：正在异步加载模块的已接收动作可能与数据库关闭交错。现有退出测试不能直接当作升级提交屏障。**
- [desktop-pipe.ts](../../apps/server/src/desktop-pipe.ts) 严格校验 start／stop 和配置，凭证只走私有管道；现有桥接校验本源、受管理窗口及 host／public 角色，但没有应用更新桥接。新增系统写入能力必须收窄到本机原生主机管理员；公共屏、玩家、子 frame 和远程浏览器管理页不能调用。
- Launcher 已校验逐文件 SHA、归属标记、链接与额外文件，使用 mutex、stage／backup／rename，在当次目录切换异常时恢复；未提供跨重启更新事务记录，也未等待新版健康确认后才退役原程序。不能据此宣称已有断电恢复或失败启动回滚。
- [LegacyGames.Preserve](../../apps/desktop/native/LegacyGames.cs) 和 [PackageStore](../../apps/server/src/game-packages/store.ts) 保留精确历史模块及内容寻址仓库；[save-repository.ts](../../apps/server/src/save-repository.ts) 的旧档迁移另有备份、校验和恢复事务。安装升级需保护这些真实对象，不把目录名带 `.legacy`、`.transactions` 或 backup 的文件当作普通缓存删除。

## 项目前期工作

### 1. 收敛安装身份、目录与内容归属

先形成安装契约，至少包括产品固定标识、安装范围、架构、公开／构建版本、安装根、稳定启动入口、配置根、数据根、模块仓库、受管理文件清单、卸载登记和快捷方式目标。路径须规范化并验证链接、越界、共享／嵌套目录、不可写目录与原有未知文件；路径或注册信息本身不构成删除授权。

建议首版采用单用户、用户可选的可写安装根，优先保留项目现有用户选盘习惯。若选择 Program Files 或全机安装，则必须先解决普通运行的可写配置／数据根、UAC 和跨用户数据隔离；不能偷偷回退 C 盘，也不能依靠每次以管理员身份运行。

建议布局草案如下，**并非已采用结构**：

```text
<用户选择的可写安装根>/
  TableMax.exe             稳定启动入口
  app/                     安装器管理的完整运行资源
  <框架生成的卸载文件>     例如 Inno 的 unins*.exe／dat
  <可选更新辅助程序>       只在退出交接需要时独立
  TableMax.config.json     可写配置，升级保留
  games/                   当前／历史模块仓库，默认卸载保留
  <用户数据>               现有默认根或已配置外部路径
```

是否把默认数据集中到 `data/`、配置根是否独立，须在阶段 0 定案；不能先变目录再临时修相对路径。卸载和清理按归属分类，而非按是否在安装目录中判断。

### 2. 调整程序替换与保存关闭边界

installer 与 updater 共用一套安装／替换规则，明确框架文件操作和项目事务各自的职责。普通启动入口不再重复承担已由安装框架执行的全载荷解压；保留校验／本地修复能力的范围另行设计。更新协调器需能在 app 被替换期间存活，且不被服务 Job 连带终止。

优先补齐：拒收新动作 → 停止人机与定时提交 → 等待已接收动作及保存事务完成 → 关闭数据库 → 返回明确关闭结果 → 核验本安装相关进程退出。保存失败、超时或强制终止不能被当作可直接提交更新的成功路径。实施前先用受控延迟动作、异步模块加载、保存失败验证风险。

记录可恢复的升级状态，区分下载完成、校验完成、旧版已关闭、程序切换、新版启动确认和清理。恢复程序文件之前必须判断数据库是否已经迁移；不得自动用旧程序打开不兼容的新数据库。既有存档迁移备份和更新事务记录各有职责，不用简单复制覆盖替代它们。

新版确认应从实际启动进程与服务核对安装标识、四位构建版本、载荷／当前游戏映射身份及健康结果，与所选 installer 的目标完全对应。只看到进程创建或 HTTP 可达不足以排除旧实例、错误入口和启动到了另一个数据根；此确认从阶段 3 手动升级起就必须具备。

### 3. 调整构建、签名和发布描述

- 冻结单元与内部模块继续复用；安装器直接消费核验载荷，程序／卸载器／更新辅助文件列入安装清单。框架版本、编译器来源及哈希锁定，保留许可证，不全局升级工程工具。
- 新交付分配规则沿用[版本规则](../reference/release.md#三位公开版本与四位本地构建2026-10-12)，一个冻结交付身份覆盖所有组件。首次安装与升级使用相同固定产品标识；版本不能成为产品标识的一部分。
- 自动执行前验证整个 installer 的可信来源。选择 Authenticode 或受信公钥签名的产品级更新描述，明确密钥保管、轮换与验证失败行为；单纯内部 SHA 或从同一响应得到的摘要不等于独立发布者认证。GitHub HTTPS／附件 digest 可提供传输与内容核对，具体信任边界需写清。
- 若采用文件签名，先签需签的程序／辅助文件，再冻结它们的安装清单；框架生成的卸载器按框架签名流程处理，最终 installer 签名／时间戳完成后才计算大小、SHA、当前指针和实际包证明。签名改变字节后旧证明失效，不能只修改摘要沿用原验收。
- 发布描述绑定公开／构建版本、目标系统／架构、安装协议、文件大小、SHA、安装器资产 ID／地址和签名；更新过程固定所选资产，避免检查与下载期间同版本附件变化。描述的承载位置待选，保持完整 EXE＋source ZIP 两附件目标。
- 若绑定 GitHub 分配的资产 ID，发布事务需先上传并核对最终附件，再生成签名描述和最终正文，最后完成正式发布；也可选择预先可确定的定位字段并校验摘要。现有发布工具按已审 notes 核对远端正文，若正文承载机器描述，须同步定义文案／描述的核验规则和生成顺序，并在发布后验证签名及资产绑定，不能追加正文后沿用旧全文证明。
- 当前 `current.json`、证明类型、公开附件复制／白名单及发布审计需要识别 installer。历史便携包按原哈希和原证明读取，不倒改旧证据或替换原标签／附件。

### 4. 调整卸载与旧便携迁移方法

卸载框架只默认移除已登记程序文件、快捷方式及本产品登记。保留数据时明确告知保留位置；可清除数据的范围必须从已核验配置与归属取得，显示具体路径并单独选择。遇到未知文件、链接、共享／嵌套目录或配置损坏时停止额外删除，不扩大到父目录或外部自定义目录。卸载时运行中的保存屏障与升级相同，失败保留可诊断状态。

旧便携版没有新 updater，第一次进入安装体系需手动运行 installer。迁移流程应显式选择原配置根，同时识别它指向的数据根及 `games` 仓库；先停止原实例，再复制到隔离候选、核验完整引用与哈希、提交新配置并试运行。成功后仍保留原目录，后续清理须单独明确授权。不得默认扫描整个磁盘、猜测唯一存档位置、移动正在使用的数据库或改写原历史模块。迁移后新旧入口共同指向同一数据根时的实例冲突也要验证。

### 5. 调整文档与职责

源码落地时同步需求基线、README 下载／安装／卸载／升级说明、构建与运行、Release、目录职责、验证与验收；本页只保留尚未完成的阶段和缺口。现行便携说明在实施前保持有效，历史说明按原版本追溯。

预计改动归属：安装打包脚本放 `tools/release/`；窄范围安装／升级运行协调放 `apps/desktop/` 的明确子职责；退出屏障属于 server／platform-core；盒子入口及文案属于 `apps/web/`；夹具和实际安装验证归 `tools/test/support/`、`tools/test/desktop/` 及对应 release 回归。不预铺新目录、重复注册表或单独更新服务器；游戏规则、UI 与素材不因安装改造搬入共享层。

### 建立安装夹具与证据链

1. **先建隔离夹具，再落地安装功能。** 在私有临时根使用不同的旧版／新版程序标记、配置、外部数据、历史模块和无关文件，覆盖中文／空格路径与取消；后续升级为真实冻结完整包。夹具只证明对应机制，不能替代最终 installer 的实际安装。
2. **记录系统写入的前后差异。** 检查受管理文件、快捷方式 `.lnk` 的实际目标／参数／工作目录、产品卸载登记、安装身份、版本、配置和数据哈希。测试不能碰已有真实安装；固定产品 ID 场景需用干净 Windows 用户／虚拟机／快照，不能只改成测试 AppId 就宣称正式升级链通过。全机安装写 HKLM／公共快捷方式等状态时，单独新建用户不足以隔离，必须使用可回收的虚拟机／系统快照或等价独立环境。
3. **分别验证向导与静默安装。** 静默流程便于自动化，但不能覆盖用户目录选择、快捷方式开关、取消、权限提示和普通权限启动；自动化隐藏运行，向导关键场景在隔离环境从实际 UI 留证。
4. **真实包证据闭环。** installer SHA＋公开／构建版本 → 冻结 snapshot／payload SHA → 安装配方与文件清单 → 实际安装目录逐文件 SHA → 已安装入口的原生运行／保存／退出 → 同包游戏专项。卸载器、更新辅助程序及框架生成文件单独登记，不能混进旧 payload 清单造成错误复用。
5. **先验证失败和恢复。** 无权写入、空间不足、文件占用、并发安装／更新／卸载、校验坏包、保存失败、切换各阶段进程终止、下次启动恢复、新版启动失败和数据库迁移失败，均需精确故障点与有界等待。模拟进程终止不写成真实断电验证。

安装／卸载结果依赖当前机器的状态，不能仅凭同字节 installer 复用成功证据。需绑定安装前的文件／数据／登记／快捷方式状态、用户身份、提升状态和 ACL，并核对本次运行输出的新鲜性；只绑定安装后证明仍不充分。状态绑定未完整前，安装／卸载／升级系统变更场景强制实测、不缓存复用。仍可复用准确同哈希的静态载荷核验，不将历史通过增加统计。

| ----------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |

执行入口落地后统一维护在[构建与运行](../reference/build-and-run.md)、[验证](../reference/validation.md)和[工具索引](../../tools/README.md)，任务页不复制第二套日常命令。沿用静音、隐藏窗口／后台、实际渲染截图、显式 `127.0.0.1`、累计 3 项失败停止、不自动重试和精确日志留证；不改防火墙、不全局升级工具、不在开发机真实安装根反复卸载。

技术路线比较：Inno Setup 可复用向导、目录、快捷方式和卸载登记，较适合当前 WinForms 体系；WiX／MSI 提供更系统化的升级管理，但产品／组件身份与版本维护更复杂；全自研 installer／uninstaller／updater 需要自己承担系统登记、权限和删除恢复，维护成本最高。上述比较为实施建议，不改现行技术栈或确定额外依赖。
