### 首版建议范围

优先支持一个安装范围、一套程序替换机制：**完整离线安装器 + 安装框架生成的卸载器 + 盒子检查／下载 + 用户明确重启升级**。在对局期间可以下载，应用更新建议只在盒子无进行中对局时开放，仍须建立保存关闭屏障。

首版不建议加入差分下载、运行中热替换、后台自动应用、常驻更新服务、计划任务、全机与单用户双模式、多实例管理、跨盘自动搬迁或用户主动降级入口。它们未被确定为本次要求；若后续纳入，应单独补范围和验收。故障恢复旧程序文件与产品级主动降级是不同能力。

### 保存、权限与恢复

- [ServiceProcess.Stop](../../apps/desktop/native/ServiceProcess.cs) 通过私有管道发 stop，等待 5 秒后可关闭 Job 兜底；目前没有返回区分「正常关闭并完成保存」与「强制终止」的结果。[DesktopContext.Quit](../../apps/desktop/native/DesktopContext.cs) 关闭窗口、服务并清理本程序 WebView2。
- [service.ts](../../apps/server/src/service.ts) 在 preClose 停人机调度、断开 Socket，再在 onClose 关闭 repository／storage；[RoomCoordinator.enqueue](../../packages/platform-core/src/room.ts) 有串行异步动作队列，但未提供明确的停止／排空接口。**源码推断风险：正在异步加载模块的已接收动作可能与数据库关闭交错。现有退出测试不能直接当作升级提交屏障。**
- [desktop-pipe.ts](../../apps/server/src/desktop-pipe.ts) 严格校验 start／stop 和配置，凭证只走私有管道；现有桥接校验本源、受管理窗口及 host／public 角色，但没有应用更新桥接。新增系统写入能力必须收窄到本机原生主机管理员；公共屏、玩家、子 frame 和远程浏览器管理页不能调用。
- Launcher 已校验逐文件 SHA、归属标记、链接与额外文件，使用 mutex、stage／backup／rename，在当次目录切换异常时恢复；未提供跨重启更新事务记录，也未等待新版健康确认后才退役原程序。不能据此宣称已有断电恢复或失败启动回滚。
- [LegacyGames.Preserve](../../apps/desktop/native/LegacyGames.cs) 和 [PackageStore](../../apps/server/src/game-packages/store.ts) 保留精确历史模块及内容寻址仓库；[save-repository.ts](../../apps/server/src/save-repository.ts) 的旧档迁移另有备份、校验和恢复事务。安装升级需保护这些真实对象，不把目录名带 `.legacy`、`.transactions` 或 backup 的文件当作普通缓存删除。

## 项目前期工作

### 1. 收敛安装身份、目录与内容归属

先形成安装契约，至少包括产品固定标识、安装范围、架构、公开／构建版本、安装根、稳定启动入口、配置根、数据根、模块仓库、受管理文件清单、卸载登记和快捷方式目标。路径须规范化并验证链接、越界、共享／嵌套目录、不可写目录与原有未知文件；路径或注册信息本身不构成删除授权。

建议首版采用单用户、用户可选的可写安装根，保留用户明确选择安装位置的能力。若选择 Program Files 或全机安装，则必须先解决普通运行的可写配置／数据根、UAC 和跨用户数据隔离；不能偷偷回退 C 盘，也不能依靠每次以管理员身份运行。

阶段 0 的具体推荐见[目录结构推荐](#目录结构推荐)。建议保留启动 EXE 旁的 `TableMax/` 配置根，**并非已采用的新安装结构**：

```text
<用户选择的可写安装根>/
  TableMax.exe             稳定启动入口
  <框架生成的卸载文件>     例如 Inno 的 unins*.exe／dat
  UpdateHelper.exe         更新交接程序，按安装清单管理
  TableMax/
    app/                   安装器管理的完整运行资源
    TableMax.config.json   可写配置，升级保留
    games/                 当前／历史模块仓库，默认卸载保留
    <用户数据>             现有默认根或已配置外部路径
    updates/               下载暂存与升级事务，按状态分别管理
```

本轮推荐不新增 `data/` 搬迁，保留 `dataDirectory:"."` 的含义；用户确认后才冻结。卸载和清理按归属分类，而非按是否在安装目录中判断。

### 2. 调整程序替换与保存关闭边界

installer 与 updater 共用一套安装／替换规则，明确框架文件操作和项目事务各自的职责。普通启动入口不再重复承担已由安装框架执行的全载荷解压；保留校验／本地修复能力的范围另行设计。更新协调器需能在 app 被替换期间存活，且不被服务 Job 连带终止。

优先补齐：拒收新动作 → 停止人机与定时提交 → 等待已接收动作及保存事务完成 → 关闭数据库 → 返回明确关闭结果 → 核验本安装相关进程退出。保存失败、超时或强制终止不能被当作可直接提交更新的成功路径。实施前先用受控延迟动作、异步模块加载、保存失败验证风险。

记录可恢复的升级状态，区分下载完成、校验完成、旧版已关闭、程序切换、新版启动确认和清理。恢复程序文件之前必须判断数据库是否已经迁移；不得自动用旧程序打开不兼容的新数据库。既有存档迁移备份和更新事务记录各有职责，不用简单复制覆盖替代它们。

新版确认应从实际启动进程与服务核对安装标识、四位构建版本、载荷／当前游戏映射身份及健康结果，与所选 installer 的目标完全对应。只看到进程创建或 HTTP 可达不足以排除旧实例、错误入口和启动到了另一个数据根；此确认从阶段 3 手动升级起就必须具备。

### 3. 调整构建、签名和发布描述

- 冻结单元与内部模块继续复用；安装器直接消费核验载荷，程序／卸载器／更新辅助文件列入安装清单。框架版本、编译器来源及哈希锁定，保留许可证，不全局升级工程工具。
- 新交付分配规则沿用[版本规则](../reference/release.md#三位公开版本与四位本地构建2026-10-12)，一个冻结交付身份覆盖所有组件。首次安装与升级使用相同固定产品标识；版本不能成为产品标识的一部分。
- 自动执行前验证整个 installer 的可信来源。选择 Authenticode 或受信公钥签名的产品级更新描述，明确密钥保管、轮换与验证失败行为；单纯内部 SHA 或从同一响应得到的摘要不等于独立发布者认证。GitHub HTTPS／附件 digest 可提供传输与内容核对，具体信任边界需写清。
- 若采用文件签名，先签需签的程序／辅助文件，再冻结它们的安装清单；框架生成的卸载器按框架签名流程处理，最终 installer 签名／时间戳完成后才计算大小、SHA、当前指针和实际包证明。签名改变字节后旧证明失效，不能只修改摘要沿用原验收。
- 发布描述绑定公开／构建版本、目标系统／架构、安装协议、文件大小、SHA、安装器资产 ID／地址和签名；更新过程固定所选资产，避免检查与下载期间同版本附件变化。描述的承载位置待选，保持完整 EXE＋source ZIP 两附件目标。
- 若绑定 GitHub 分配的资产 ID，发布事务需先上传并核对最终附件，再生成签名描述和最终正文，最后完成正式发布；也可选择预先可确定的定位字段并校验摘要。现有发布工具按已审 notes 核对远端正文，若正文承载机器描述，须同步定义文案／描述的核验规则和生成顺序，并在发布后验证签名及资产绑定，不能追加正文后沿用旧全文证明。
- 当前 `current.json`、证明类型、公开附件复制／白名单及发布审计需要识别 installer。历史便携包按原哈希和原证明读取，不倒改旧证据或替换原标签／附件。

### 4. 调整卸载与旧便携迁移方法

卸载框架只默认移除已登记程序文件、快捷方式及本产品登记。保留数据时明确告知保留位置；可清除数据的范围必须从已核验配置与归属取得，显示具体路径并单独选择。遇到未知文件、链接、共享／嵌套目录或配置损坏时停止额外删除，不扩大到父目录或外部自定义目录。卸载时运行中的保存屏障与升级相同，失败保留可诊断状态。

旧便携版没有新 updater，第一次进入安装体系需手动运行 installer。迁移流程应显式选择原配置根，同时识别它指向的数据根及 `games` 仓库；先停止原实例，再复制到隔离候选、核验完整引用与哈希、提交新配置并试运行。成功后仍保留原目录，后续清理须单独明确授权。不得默认扫描整个磁盘、猜测唯一存档位置、移动正在使用的数据库或改写原历史模块。迁移后新旧入口共同指向同一数据根时的实例冲突也要验证。

### 5. 调整文档与职责

源码落地时同步需求基线、README 下载／安装／卸载／升级说明、构建与运行、Release、目录职责、验证与验收；本页只保留尚未完成的阶段和缺口。现行便携说明在实施前保持有效，历史说明按原版本追溯。

预计改动归属：安装打包脚本放 `tools/release/`；窄范围安装／升级运行协调放 `apps/desktop/` 的明确子职责；退出屏障属于 server／platform-core；盒子入口及文案属于 `apps/web/`；夹具和实际安装验证归 `tools/test/support/`、`tools/test/desktop/` 及对应 release 回归。不预铺新目录、重复注册表或单独更新服务器；游戏规则、UI 与素材不因安装改造搬入共享层。

### 建立安装夹具与证据链

1. **先建隔离夹具，再落地安装功能。** 在私有临时根使用不同的旧版／新版程序标记、配置、外部数据、历史模块和无关文件，覆盖中文／空格路径与取消；后续升级为真实冻结完整包。夹具只证明对应机制，不能替代最终 installer 的实际安装。
2. **记录系统写入的前后差异。** 检查受管理文件、快捷方式 `.lnk` 的实际目标／参数／工作目录、产品卸载登记、安装身份、版本、配置和数据哈希。测试不能碰已有真实安装；固定产品 ID 场景需用干净 Windows 用户／虚拟机／快照，不能只改成测试 AppId 就宣称正式升级链通过。全机安装写 HKLM／公共快捷方式等状态时，单独新建用户不足以隔离，必须使用可回收的虚拟机／系统快照或等价独立环境。
3. **分别验证向导与静默安装。** 静默流程便于自动化，但不能覆盖用户目录选择、快捷方式开关、取消、权限提示和普通权限启动；自动化隐藏运行，向导关键场景在隔离环境从实际 UI 留证。
4. **真实包证据闭环。** installer SHA＋公开／构建版本 → 冻结 snapshot／payload SHA → 安装配方与文件清单 → 实际安装目录逐文件 SHA → 已安装入口的原生运行／保存／退出 → 同包游戏专项。卸载器、更新辅助程序及框架生成文件单独登记，不能混进旧 payload 清单造成错误复用。
5. **先验证失败和恢复。** 无权写入、空间不足、文件占用、并发安装／更新／卸载、校验坏包、保存失败、切换各阶段进程终止、下次启动恢复、新版启动失败和数据库迁移失败，均需精确故障点与有界等待。模拟进程终止不写成真实断电验证。

安装／卸载结果依赖当前机器的状态，不能仅凭同字节 installer 复用成功证据。需绑定安装前的文件／数据／登记／快捷方式状态、用户身份、提升状态和 ACL，并核对本次运行输出的新鲜性；只绑定安装后证明仍不充分。状态绑定未完整前，安装／卸载／升级系统变更场景强制实测、不缓存复用。仍可复用准确同哈希的静态载荷核验，不将历史通过增加统计。

### 安装范围与框架推荐

**推荐单用户安装。**平台由一台 Windows 主机运行，朋友通过浏览器加入，并不需要为这台电脑的全部 Windows 账户安装共享服务。全机安装虽更接近传统 Program Files 布局，却要求可写数据根分离、管理员提升、公共快捷方式、跨会话运行保护和全机卸载登记，扩大首版验证面。首版不提供单用户／全机双模式切换。

Inno Setup 的 `PrivilegesRequired=lowest` 不主动请求提升、采用非管理员安装；产品登记归 HKCU，快捷方式归当前用户。运行程序保持当前 asInvoker，不增加开机自启、系统服务、文件关联或防火墙规则。用户手动以其他管理员账户运行安装器时不能假装仍属于原用户安装，应拒绝或明确返回正确用户上下文；运行组件的官方安装可能有独立权限提示，不能把安装器不提升误写成所有依赖都无需提升。[安装权限](https://jrsoftware.org/ishelp/topic_setup_privilegesrequired.htm)、[安装范围](https://jrsoftware.org/ishelp/topic_admininstallmode.htm)

**推荐 Inno Setup，不自研完整向导和卸载器。**WiX／MSI 的组件与升级管理更适合企业部署，本项目暂没有此需求；全自研需要长期维护登记、快捷方式、权限和失败删除。Inno 可处理系统集成，项目负责动作排空、精确模块保全、持久更新状态和健康确认，不能把这些职责交给框架默认文件覆盖。只采用完整安装和升级，不增加下载游戏的安装类型。

框架版本在阶段 1 按官方完整发行、许可证和哈希锁定于项目工具缓存；本轮不安装编译器。官方当前列出稳定 7.1.0，可作为评估候选，不因推荐而全局升级工具。个人朋友项目与未来商业使用的许可背景需按实际用途核对；不在本轮采购。[官方发行](https://jrsoftware.org/)、[许可说明](https://jrsoftware.org/isinfo.php)

### 更新架构、时机与事务推荐

**推荐原生更新管理＋C# helper＋完整 installer。**盒子网页仅显示状态并提交受限请求；网络获取、下载路径和校验由原生层决定，不接受网页传入任意 URL、目标路径或 shell 命令。仅受管理本地主机管理员可应用更新，公共屏、玩家、frame 和远程浏览器均不得获得系统写入能力。

常驻更新服务、计划任务和单独 Node 更新守护进程都不是首版必要组件。小型 net48 helper 与现有技术栈一致；在替换开始前把受校验 helper 复制到本事务的暂存位置，从该位置运行，等待原入口／主机／服务／本程序 WebView2 退出。安装器可更新 I 中的 helper，临时 helper 完成交接后退出，下次启动再清理该已完成事务；不能边运行根目录 helper 边要求 installer 覆盖同一个 EXE。

首次安装和升级的文件复制由同一 installer 实现。手动运行 installer 升级也走同一停止、互斥、状态与确认流程；网页内更新只是准备可信候选并协调调用，不再实现第二套替换算法。

推荐首版主动点击「检查更新」，无启动自动检查或周期后台轮询；下载可取消并在当前程序运行时进行。下载完成只进入待应用状态，无进行中对局且用户点击后才进入关闭屏障；「暂停了对局」仍属于进行中，不能作为随时可升级的空闲条件。需继续对局时保留候选，结束后再应用。

事务推荐至少区分：准备／下载 → 完整校验 → 请求保存关闭 → 全部相关进程退出 → 安装切换 → 目标实例确认 → 已完成清理。安装互斥锁与数据实例锁分开；不以通用进程名结束其他程序。关闭失败、强制清理、尚未保存或无法排空均不能直接转到切换成功。

目标确认绑定具体安装实例、B／D、构建版本、payload／当前映射及实际服务健康，由已启动目标进程的受控通道取得；不能只扫描端口。超时仍须判断迁移是否开始，必要时停留在可诊断失败状态。恢复旧程序文件仅限尚未产生不兼容数据库变化的阶段；用户新产生的数据不得用旧快照覆盖。对数据库迁移采用原有备份／校验事务，并增补升级交接，不承诺框架的普通覆盖天然具备全应用原子回滚。

### 发布源与更新描述推荐

**推荐 GitHub 正式 stable Release，无自建更新服务器或 Pages。**保持两附件：完整 installer EXE 和 source ZIP。普通用户无需 GitHub token；公开附件名继续三位版本，签名描述记录四位构建与实际摘要。只有本轮明确授权发布后才改变线上程序类型。

在 Release 正文追加一个带固定标记的机器块，内容为签名 envelope；网页更新说明只显示人类说明，机器块独立解析和留证，不把它当 Markdown 执行。本轮推荐隐藏 HTML 注释中的 Base64 envelope，具体单块提取和限长规则需在阶段 1／4 用真实 GitHub API body 回归，不通过抓取浏览器排版结果取描述。

选择**预先可确定的资产定位字段**，签名包含固定仓库、releaseTag、assetName、长度和 SHA-256；不强制把 GitHub 上传后才分配的 asset ID 纳入签名。获取时从该仓库／标签的资产中找到唯一匹配者，记录实际 release／asset ID，校验名称、大小与流式摘要；未知或重复匹配拒绝。这样最终 EXE 字节固定后即可生成并审阅完整正文，减少上传与签名之间的循环依赖。

| 描述字段组（推荐）                                           | 作用                                                     |
| ------------------------------------------------------------ | -------------------------------------------------------- |
| schemaVersion、productId、channel、os、arch、installProtocol | 固定解释与目标边界，拒绝未知协议和不适用平台             |
| releaseVersion、buildVersion、releaseTag、repo、assetName    | 区分公开版本和精确构建，限定可信资产定位                 |
| bytes、sha256、payloadManifestSha256、currentMappingSha256   | 验证外层候选与新版实际运行身份；签名后不再改包           |
| keyId、可授权后继公钥的信息                                  | 选择内置信任根并支持提前轮换，不能由网络任意指定验签算法 |

发布顺序为：冻结并验收最终字节 → 生成签名描述及已审完整正文 → 经授权创建草稿并上传两附件 → 核验实际附件与描述一致 → 发布 → 复查正文、资产与签名映射。现有全文 notes 校验需针对已审最终正文调整输入，不发布后临时追加未审机器块。

### 项目更新签名与 Windows 代码签名推荐

**两者分别设计。**项目更新签名证明候选来自内置受信发布密钥；Authenticode 向 Windows 证明文件发布者并支持系统策略。前者不会让 Windows 自动信任 EXE，后者也不代替安装范围、资产和精确版本校验。

| 路线                               | 适用性与代价                                                                            | 推荐结论                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 独立应用 RSA 签名描述              | Node 22 打包端签名、net48 原生端验签；仅增加很小的公钥／签名，无需新运行时和证书购买    | 首版自动更新的必要基础                                         |
| 复用现有游戏 Ed25519 密钥          | Node 可复用实现，但现有原生工程没有对应验签依赖；游戏密钥同时获准发布整个程序会扩大权限 | 不复用现有私钥；如选 Ed25519，应独立应用密钥并另评估原生验证库 |
| 原生依赖服务 Node 来验签           | 能调用已有 Node crypto，但服务关闭与 helper 更新交接更复杂                              | 原生应用更新认证不依赖服务 Job 存活                            |
| 可信 Authenticode                  | 能提供系统可识别的发布者，但需要证书／服务资格、成本和凭证管理                          | 广泛分发推荐；朋友试用是否立即投入由用户单独决定               |
| 自签 Authenticode 并让用户导入证书 | 不自动获得公开 Windows 信任，增加用户系统信任修改                                       | 不推荐作为朋友安装的常规步骤                                   |

RSA 方案推荐 RSA-3072、SHA-256 和固定 PKCS#1 v1.5 **签名填充**，不涉及 RSA 加密。它利用 .NET Framework 的现成 RSA API，避免为 net48 引入 Ed25519 验签库，也不引入不同提供者的 PSS 支持差异；具体公钥导入方式和 Node／C# 互操作仍须在阶段 1 用固定向量验证，不能从文档支持推定已通过。[Node 22.14.0 crypto](https://nodejs.org/download/release/v22.14.0/docs/api/crypto.html#cryptosignalgorithm-data-key-callback)、[.NET RSA API](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rsa.verifydata)

应用私钥与现有游戏私钥分离，只存在受保护签名环境／本地 secrets，并通过私有管道或受保护文件提供给签名工具；不进 Git、installer、命令行输出或测试日志。本轮不生成密钥。程序只内置应用公钥及 keyId；正常轮换先用旧根签署包含后继公钥的可信更新，再在后续发行切换签名。密钥丢失／泄露不能靠网络提供一把新钥直接恢复信任，需设计受审手动安装恢复路径。

首版朋友试用可在明确接受系统提示与兼容限制的前提下，先使用项目签名更新描述、暂不购买 Authenticode；这不是系统安全兼容保证。Smart App Control 的可信证书要求、自签证书和 SmartScreen 信誉是不同问题；即使有可信证书也不能保证新 EXE 从不出现信誉提示，不建议关闭保护功能。[代码签名选择](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)、[SmartScreen 信誉](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)、[Smart App Control 签名](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control)

若采用 Authenticode，只对项目自有启动器、原生壳、helper、框架卸载器和 installer 按所选策略签名；官方 Node／WebView2 等第三方字节保持原发行，不重新签名破坏当前哈希来源。内部自有文件签名后再形成清单，最终 installer 签名及时间戳后再计算外层 SHA 和更新描述。更新协议从开始就允许记录 Authenticode 策略，后续增强不得让用户可随意绕过项目签名。

### 版本、安装身份与旧程序推荐

固定产品 ID 与每次安装生成的实例 ID 分开：前者供安装框架判断本产品升级／卸载，后者绑定安装根、用户和更新事务。产品 ID 不带公开版本；只支持当前用户一份受管理安装，旧便携 EXE 不自动变成已登记的安装实例。

| 情况                                                    | 推荐行为                                                                                                       |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 目标四位构建大于当前，公开标签和安装协议匹配            | 提供升级，下载前后均校验已签描述和字节                                                                         |
| 同三位公开版本、目标本地修订更高                        | 作为已发布修订提示，仍需经发布授权更新签名描述                                                                 |
| 同四位构建、相同 SHA                                    | 视为相同候选，不重复升级；损坏修复属于显式安装器修复流程                                                       |
| 同四位构建、不同 SHA                                    | 拒绝作为正常在线更新；冻结恢复／原载荷重封仍按现行规则不递增修订，但重签改变外层字节须明确受审重签／再发布策略 |
| 目标低于当前，或本地维护修订高于线上                    | 不自动降级；不把三位附件名当作本地修订 0 强制覆盖                                                              |
| 历史 Release 缺可信更新描述、安装协议更高、原局模块缺失 | 保留当前程序和数据，解释需手动处理的版本／协议；不降级信任或替换旧局规则                                       |

保存最高已接受的有效构建／描述身份，拒绝回退或同身份换字节；签名只证明来源，不保证服务器提供的是全世界最新版本。首版不建设在线密钥吊销或完整抗冻结协议，不能宣称能排除首次联网遇到旧但合法描述的情况。

旧局缺原发行时，原便携程序仍按原字节保留，用户可在明确的隔离／原数据路径下使用兼容旧完整程序；新安装器不因此提供一键降级或覆盖新数据库。初次从旧便携进入安装体系仍手动安装，线上切换不改原标签、原 SHA 映射或旧附件。

### 阶段 0 交接与状态

本轮已交付逐项取舍、推荐目录／身份、更新职责、签名与发布描述方案；**用户定案尚未完成，阶段 0 不标为契约已冻结，阶段 1–6 不开始。**推荐形成不产生新的公开版本、安装目录、注册表项、密钥或测试结果。

下一次定案主要涉及：是否接受单用户及显示在安装页的用户程序默认路径；是否采用保持原配置根的目录布局；朋友试用阶段是否先不购买可信 Authenticode。框架／RSA 描述／完整更新方案可作为一组可评审建议；确认后将有效需求合并基线，并把固定向量、机器块解析、helper 自更新和体积计量列入阶段 1 的实际验证输入。
