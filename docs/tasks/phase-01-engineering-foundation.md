# 第一阶段：确认技术栈、环境配置、代码结构设计

状态：待执行。本文件是阶段任务定义，尚未确认具体依赖版本、安装开发环境或建立代码工程。

依据：[需求基线](../requirements/TableMax_需求文档_v1.0.md) 第 6、8、11、12、13 节及 [开发阶段总览](README.md)。本阶段为后续平台和游戏开发建立可复现的工程基础。

## 阶段目标与边界

完成技术栈确认、开发环境配置和代码结构设计，使后续任务有明确的工具链、模块职责、开发入口和验证方法。

本阶段交付限于工程基础及必要的兼容性验证。大厅、身份、游戏规则、回退恢复等产品功能按后续阶段推进；本阶段的最小验证只用于证明选型与工程可用，不能计为对应产品验收通过。

Windows 便携、局域网离线运行、服务端权威、秘密信息隔离、决策点回退与自动恢复、多游戏模块扩展是设计约束。尚未核实的桌游人数、卡牌和规则不作为平台结构的硬编码依据。

## 任务一：确认技术栈

- 以需求第 11 节的 TypeScript、Vue／Vite、Node.js／Fastify、Socket.IO、SQLite、Electron、pnpm workspace、Vitest／Playwright 建议为候选，逐层确认采用方案、版本范围、理由与取舍；同时明确运行时校验及本地二维码方案。
- 核对开发工具链、服务端、桌面运行时与 SQLite 绑定的兼容性，确定桌面壳启动本地服务、提供构建后网页与资源的方式；通过最小验证确认 Windows 便携打包路径可行。
- 将重要技术选择写入 `docs/decisions/` 并更新索引。未确定项记录具体影响与解决方式，不把候选方案写成已采用方案。

交付：技术栈决策记录、关键兼容性与便携打包可行性验证结果。当前这些交付尚未产生。

## 任务二：环境配置

- 清点现有开发环境，在选型确认后配置所需运行时、包管理器及项目依赖，记录版本、安装前提和实际执行方法；项目工具配置优先放在仓库内。
- 建立最小工程配置与依赖锁定方式，提供真实可执行的开发、类型检查、测试和构建入口；按需要设置代码格式与静态检查，不为尚不存在的功能编造命令。
- 记录开发期间联网安装与正式游玩离线运行的区别，明确本地配置、端口、日志、缓存、构建产物和未来存档的位置；调整 Git 与工作区排除策略，使长期资料和交付物可见。
- 在目标 Windows 开发环境验证最小工程，并记录环境、执行命令、结果和仍有影响的限制。此处不要求完成整局游戏或正式交付验收。

交付：环境配置说明、必要工程配置与锁文件、最小工程验证记录。具体文件和命令在建立后回填。

## 任务三：代码结构设计

- 以需求第 6.3 节的 `apps/`、`packages/`、`games/` 为候选结构，确认桌面壳、服务端、网页端、协议、游戏 SDK、平台核心、通用 UI 和游戏模块的职责及依赖方向。
- 明确公共屏、手机端和房主管理的入口边界；定义服务端权威状态与按身份投影视图的责任归属，保证游戏规则逻辑不依赖 UI、通信、数据库或桌面框架。
- 明确可序列化状态、动作校验与去重、统一随机源、决策点、分支修订、存档版本和游戏资源命名空间由哪些模块负责。本阶段设计边界，后续阶段实现完整机制。
- 区分模块内验证、平台验证、跨端流程和打包验证的位置；只建立本阶段实际需要的目录与最小工程文件，记录后续才创建的结构。
- 把已采用的目录、依赖方向与开发入口同步到 `docs/reference/`、根 README 和 AGENTS.md；重要结构取舍进入决策文档。

交付：代码结构与依赖方向设计、必要工程目录和最小配置、更新后的项目入口。具体目录与方案仍待本阶段确认。

## 完成标准

- [ ] 主要技术层已有明确采用方案、版本或版本约束、理由与兼容依据；影响环境和代码边界的选择已解决。
