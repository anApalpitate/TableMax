# 第一阶段：确认技术栈、环境配置、代码结构设计

状态：已完成（2026-10-01，Asia/Shanghai）。技术选型、固定环境、最小工程、结构设计与本机便携 ZIP 验证均已交付；首版产品功能仍按后续阶段推进。

## 已确认与落实结果

- 开发取舍：优先开发和维护省心，接受较大的程序包。
- Windows 覆盖：仅需支持用户本机的 Windows 11；只读环境检查确认架构为 x64，不扩大到其他 Windows 版本或架构。
- 前端选择依据：用户无框架硬性偏好，要求优先考虑 AI 协作开发质量。按此授权采用 React + TypeScript + Vite；这是项目工程判断，不宣称 React 的 AI 生成质量已有优于 Vue 的通用证据。
- 确认方式：通过分轮选项问答确认关键取舍，再开展依赖安装与工程实现。
- 开发环境：保留本机 Node.js v22.14.0、pnpm 10.12.1、Git 2.55.0，依赖精确版本与锁文件已建立并验证冻结安装。
- 基础技术：Electron、Node.js／Fastify、Socket.IO、SQLite、pnpm workspace、Zod、Vitest／Playwright 已落地，实际版本与兼容依据见技术决策和开发说明。
- 网页组织：公共屏、手机端和房主管理共用一个网页工程，分开入口与布局；权限由服务端独立校验。
- 数据位置：存档和日志放在 Windows 当前用户的本地应用数据目录，与程序包分离。
- 服务运行：桌面主进程用 Electron `utilityProcess` 启动独立服务，分离窗口管理与 HTTP／实时通信／数据库职责；开发与打包运行时均通过最小验证。
- 游戏组织：每款游戏集中在 `games/<游戏标识>/`，内部区分规则、公共屏 UI、手机 UI、资源和验证；规则与客户端采用独立入口。

- 编辑器与执行范围：用户选择保存时自动格式化，并直接完成第一阶段全部交付与 Git 提交；项目 Prettier 配置与实际验证入口已建立。

采用依据见 [工程基础技术决策](../decisions/001-engineering-foundation.md)，实际依赖方向与后续机制归属见 [代码结构设计](../reference/architecture.md)，完整命令和验证记录见 [开发环境](../reference/development.md)。

依据：[需求基线](../requirements/TableMax_需求文档_v1.0.md) 第 6、8、11、12、13 节及 [开发阶段总览](README.md)。本阶段为后续平台和游戏开发建立可复现的工程基础。

## 阶段目标与边界

完成技术栈确认、开发环境配置和代码结构设计，使后续任务有明确的工具链、模块职责、开发入口和验证方法。

本阶段交付限于工程基础及必要的兼容性验证。大厅、身份、游戏规则、回退恢复等产品功能按后续阶段推进；本阶段的最小验证只用于证明选型与工程可用，不能计为对应产品验收通过。

Windows 便携、局域网离线运行、服务端权威、秘密信息隔离、决策点回退与自动恢复、多游戏模块扩展是设计约束。尚未核实的桌游人数、卡牌和规则不作为平台结构的硬编码依据。

## 任务一：确认技术栈

- 以需求第 11 节的 TypeScript、Vue／Vite、Node.js／Fastify、Socket.IO、SQLite、Electron、pnpm workspace、Vitest／Playwright 建议为候选，逐层确认采用方案、版本范围、理由与取舍；同时明确运行时校验及本地二维码方案。
- 核对开发工具链、服务端、桌面运行时与 SQLite 绑定的兼容性，确定桌面壳启动本地服务、提供构建后网页与资源的方式；通过最小验证确认 Windows 便携打包路径可行。
- 将重要技术选择写入 `docs/decisions/` 并更新索引。未确定项记录具体影响与解决方式，不把候选方案写成已采用方案。

已交付：[技术决策](../decisions/001-engineering-foundation.md) 中的固定版本与取舍，以及 [开发说明](../reference/development.md) 中的两种运行时、SQLite 与便携打包验证结果。

## 任务二：环境配置

- 清点现有开发环境，在选型确认后配置所需运行时、包管理器及项目依赖，记录版本、安装前提和实际执行方法；项目工具配置优先放在仓库内。
- 建立最小工程配置与依赖锁定方式，提供真实可执行的开发、类型检查、测试和构建入口；按需要设置代码格式与静态检查，不为尚不存在的功能编造命令。
- 记录开发期间联网安装与正式游玩离线运行的区别，明确本地配置、端口、日志、缓存、构建产物和未来存档的位置；调整 Git 与工作区排除策略，使长期资料和交付物可见。
- 在目标 Windows 开发环境验证最小工程，并记录环境、执行命令、结果和仍有影响的限制。此处不要求完成整局游戏或正式交付验收。

已交付：[环境说明](../reference/development.md)、根与各工作区 `package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、类型／静态／排版／打包配置，以及 `scripts/` 中实际可执行的命令入口。

## 任务三：代码结构设计

- 以需求第 6.3 节的 `apps/`、`packages/`、`games/` 为候选结构，确认桌面壳、服务端、网页端、协议、游戏 SDK、平台核心、通用 UI 和游戏模块的职责及依赖方向。
- 明确公共屏、手机端和房主管理的入口边界；定义服务端权威状态与按身份投影视图的责任归属，保证游戏规则逻辑不依赖 UI、通信、数据库或桌面框架。
- 明确可序列化状态、动作校验与去重、统一随机源、决策点、分支修订、存档版本和游戏资源命名空间由哪些模块负责。本阶段设计边界，后续阶段实现完整机制。
- 区分模块内验证、平台验证、跨端流程和打包验证的位置；只建立本阶段实际需要的目录与最小工程文件，记录后续才创建的结构。
- 把已采用的目录、依赖方向与开发入口同步到 `docs/reference/`、根 README 和 AGENTS.md；重要结构取舍进入决策文档。

已交付：[结构与依赖设计](../reference/architecture.md)、[实际目录职责](../reference/project-structure.md)、桌面／服务／网页工程、`protocol`、纯类型初始 `game-sdk`，以及更新后的 README 与 AGENTS.md。`platform-core`、独立公共 UI 包、游戏规则与完整模板按后续阶段创建。

## 完成证据与后续事项
