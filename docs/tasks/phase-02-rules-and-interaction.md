# 第二阶段：规则与交互准备

状态：进行中，规则关口未通过。2026-10-01 已开展来源检索，交付通用权限／恢复交互规格、独立可点击低保真原型、通用资源方案与验证场景；目标版完整规则与卡牌原文仍未取得，完整游戏规格尚未冻结。

依据：[需求基线](../requirements/TableMax_需求文档_v1.0.md) 第 4 至 10、12、13 节、[开发阶段总览](README.md) 与 [工程结构](../reference/architecture.md)。第一阶段工程基础已完成，本阶段为后续平台、恢复机制及首版游戏开发提供可核验的规格。

## 阶段目标与边界

确认《宝可梦奇遇：皮卡丘和朋友们》对应版本的完整规则与卡牌数据，将实体玩法转化为服务端状态、授权信息、决策点及两端交互规格，使后续实现不依赖猜测规则或临时决定信息权限。

本阶段交付规则研究、规格、可点击低保真原型、资源清单和验证场景。原型使用模拟授权视图、清晰占位美术，在既有网页工程中设置独立入口，复用锁定依赖；不连接真实服务，不包含完整秘密状态或真实凭证，不修改正式协议或游戏 SDK。大厅与身份等平台功能由第三阶段实现；可靠动作、回退和持久化恢复由第四阶段实现；完整游戏与正式美术、声音由第五阶段实现；实机和便携产品验收由第六阶段完成。原型仅用于设计验证，不计为产品功能已实现或 AC 验收通过。

继续采用已确认的本机 Windows 11 x64、React／TypeScript 与独立本地服务方案，不重新选择技术栈。公共屏横屏、手机竖屏优先，默认简体中文；服务端权威、秘密信息隔离、房主决策点回退、无默认超时和掉线不代操作均为既定约束。

## 执行顺序与未知项处理

先取得并核验对应版本原文，再形成规则与卡牌规格；信息权限和决策点随规则同步整理，游戏布局及操作草图以已核验结果为依据。资源盘点和通用加入、暂停、重连等流程可以并行准备。

目标为用户指定的《宝可梦奇遇：皮卡丘和朋友们》简体中文版，但对应出版信息、规则版本与适用勘误尚未核实。人数、组件数量、卡牌数值与能力、布局、初始化、行动、结束、计分和平局等仍待核验。需求中的 Paper Safari 文件入口只是研究线索，不能视为宝可梦版本规则一致的证据，也不能因其他语言资料易取得而替换目标版本。

研究优先自行检索出版方原文、勘误及对应版本资料，不把“用户先提供全部资料”作为启动前提。每项结论区分已核验、存在冲突和待核验，记录出处及影响；检索无法解决且会改变规则或设计的关键问题，再用少量明确选项向用户确认。未核实内容不能写成正式规则，也不能凭用户选择把猜测标为出版方规则。

影响完整玩法、权限或回退边界的缺失与争议必须解决后，本阶段才能完成。尚未取得规则全文时可以整理来源和通用流程，但不能据此冻结完整游戏规格。

## 任务一：核验版本、规则与卡牌数据

- 确认对应版本的出版信息、语言、规则版本与适用勘误，取得可复查的完整规则原文；优先采用对应版本出版方规则、勘误及出版方上传资料，第三方介绍用于交叉核对。
- 建立来源记录：来源名称、链接或本地资料路径、语言与版本、获取日期、适用章节／页码、可信程度及核验状态。原始资料保留，区分原文、提取数据与研究结论。
- 整理人数、组件、准备与初始布局、合法查看、全部行动及目标限制、阶段推进、特殊效果、回合／整局结束、计分和平局。规则条目关联具体来源；只在核验确有相关机制后写入具体流程。
- 建立完整卡牌与组件的可机器读取结构化文件，记录稳定标识、名称、数量、数值、能力原文位置及数字化解释，附数量一致性核验结果；区分类别、对局中单张实例和资源标识。字段及文件格式按取得的原文确定，不预先创建空游戏工程。
- 若使用普通 Paper Safari 或其他主题版本作参考，明确哪些内容可比、哪些差异已证实、哪些仍无法确认；不直接沿用未经证明一致的数值与能力。
- 对来源冲突、缺失条目和歧义记录问题、影响范围、解决依据及最终结论，保证后续可以追溯采用理由。

交付：对应版本来源清单、规则规格、卡牌／组件数据及已处理的差异与争议记录。

## 任务二：定义信息权限、状态与决策点回退

- 按已核验流程列出阶段、行动者、合法动作、参数与目标、动作结果、自动推进及待处理选择；区分游戏规则、平台管理动作和仅影响本地界面的操作。
- 建立逐项信息矩阵：服务端完整状态、公共屏、本人、其他玩家及房主分别可知什么、何时获知。卡背与未知位置、临时查看结果、公开操作记录和错误提示均纳入；房主管理权不额外授予其他玩家的秘密信息。
- 对每项合法且改变权威状态的玩家决策，定义决策前后的状态边界、历史标签、待处理选择和恢复后可执行动作。复合操作是否拆分、原子动作包含哪些步骤，必须依据核验后的规则说明；翻页、缩放和打开帮助不记录为游戏决策点。
- 标记信息揭示与随机节点，说明需要保存的牌堆顺序、随机状态及已生成结果，恢复后哪些结果应保持相同。回退提示说明玩家可能已经看到信息；不新增全员同意条件，不因信息已揭示而一律禁止回退，不悄悄重新随机。
- 列出可序列化的游戏状态、恢复所需字段及一致性条件。区分随游戏恢复的数据与不倒退的身份、授权、连接信息；修订号／分支号递增，旧分支动作、选择与动画失效。
- 明确哪些内容可进入公共历史、玩家视图和房主管理记录，哪些仅留服务端 checkpoint；完整秘密状态不能用于前端草图数据或公开回退标签。

交付：状态与流程表、信息权限矩阵、决策点清单、恢复字段和揭示／随机回退规格。这里只定义行为和边界，不实现动作队列或存档机制。

## 任务三：设计公共屏、手机与房主管理交互

- 形成从启动、选择局域网地址、创建房间、扫码加入、入座与准备，到开局、行动、等待和结算的流程。人数及游戏准备条件使用已核验规则；本次已选重名提示、关闭新加入、开局前座位调整及房主确认换手机绑定，其他未选便利项不自动升级为必须要求。
- 为首版游戏分别设计公共屏与手机草图：公共屏突出公共布局、阶段、当前行动者和结果；手机突出本人信息、合法动作、目标选择和允许查询的公共信息。牌面和卡位按核验规则组织，避免将大屏布局直接缩小作为手机方案。
- 区分房主管理界面与房主作为玩家时的私人界面，覆盖开局、暂停、恢复、座位管理、结束及决策点选择；公共屏和加入二维码不得暴露房主凭证。
- 覆盖提交前、提交中、保存后确认、拒绝／失败及需重新同步的反馈。重复点击、过期动作、旧分支和重连后旧选择有可理解的处理方式，界面动画不能被当作服务端成功确认。
- 补齐掉线等待、锁屏／切换 App／刷新重连、暂停、回退后清空旧选择、重启恢复及不兼容／损坏存档提示。当前行动玩家掉线不自动代操作；恢复失败保留原存档的产品行为在流程中说明。
- 对局域网无法连接、错误网卡、端口占用、设备隔离、系统浏览器打开，以及关闭公共屏与退出整个程序的不同效果给出说明入口和反馈草图。
- 用现有 Playwright 检查公共屏 1920×1080、手机 360／390 CSS 像素宽度及安全区域，走查文字溢出、触控目标、操作步骤、提交反馈、旧选择清除与各角色的模拟授权展示；运行时不请求外部资源。关键视觉或操作取舍明确后再交给实现阶段，实机验收由第六阶段完成。

交付：完整使用流程、各角色页面／状态清单、公共屏与手机草图及必要的管理草图。规则尚未明确的部分标注待核验，不能用草图默认值反向确定游戏规则。

## 任务四：盘点本地资源与声音需求

- 按核验后的组件与界面列出封面、卡面、卡背、角色／组件、背景、图标、字体、规则帮助和必要提示音，明确用途、数量、稳定资源标识及对应规则／组件标识。
- 区分可取得资源、需要加工或生成的资源、暂缺资源及占位方案；记录来源链接、取得日期、使用说明和已知使用限制。生成资源计划说明需保留提示词与版本，不把网上可查看等同于可公开分发。
- 将规则文字、数字和关键符号与美术分开排版，保证替换图片不改变游戏规则；资源清单不包含本局隐藏卡位与实际卡牌的映射。
- 明确正式资源、字体、脚本、帮助与音频随包本地加载，不依赖运行时 CDN。提示音只由公共屏播放，可静音，需用户手势激活；失败不阻断游戏，刷新、重连和回退同步不重播历史声音。
- 列出第五阶段需要补齐、压缩和视觉核验的资源及检查方法。本阶段完成资源方案和来源盘点，不要求批量生产全部最终美术；影响规则核验的缺失卡牌原文不能当作普通美术待办延期。

交付：资源与来源清单、本地打包要求、声音触发方案及后续制作缺口。

## 任务五：建立验证场景与后续交接

- 基于已核验规则准备典型完整对局、每类合法动作、特殊效果、边界条件、结束／计分／平局场景，注明初始数据、操作步骤、预期状态和规则依据；示例数据不冒充未取得的真实卡牌数据。
- 为每类决策点准备恢复场景，覆盖连续回退、复合操作中间选择、已揭示信息、随机结果一致、旧分支迟到动作及回退后继续游戏和重启恢复。列明各端应看到的授权结果与不得泄露的信息。
- 补齐重复／并发／越权提交、移动端重连、掉线等待、房主同时参与、存档兼容和离线资源等场景，关联需求 AC-02 至 AC-17 中适用条目，并区分规则验证、平台验证和实机验收责任。
- 根据具体玩法指出当前初始 SDK 需要支持的动作、投影、决策和资源能力，将第三、四、五阶段的接口输入与待处理事项分别列出。只提出有实际依据的需求，不把宝可梦卡位或回合形式硬编码进平台，也不提前实现后续扩展游戏。
- 记录规格走查结果、仍可留给后续阶段的制作事项，以及会阻止实现的关键缺口；验证场景已制定不代表测试已经运行或产品验收通过。原型执行类型、静态、格式与独立构建检查，文档检查引用、相对链接、索引和 diff；构建、截图与走查证据放入 `artifacts/phase-02/`，保持文件树可见。

交付：验证场景清单、需求追踪及第三至五阶段交接事项。

## 完成标准

- [ ] 对应版本完整规则原文可复查，版本与适用勘误明确；重要规则条目有出处，影响玩法、权限或恢复的来源冲突和缺失已解决。
