## 阶段目标与边界

整理《宝可梦奇遇：皮卡丘和朋友们》的当前采用规则与卡牌数据，分别追踪原文认证及用户授权的项目方案，将玩法转化为服务端状态、授权信息、决策点及两端交互规格，使后续实现不依赖猜测规则或临时决定信息权限。

本阶段交付规则研究、规格、可点击美术原型、资源清单和验证场景。原型使用模拟授权视图、已确认的明亮桌游主机美术与明确的游戏布局示意，在既有网页工程中设置独立入口，复用锁定依赖；不连接真实服务，不包含完整秘密状态或真实凭证，不修改正式协议或游戏 SDK。大厅与身份等平台功能由第三阶段实现；可靠动作、回退和持久化恢复由第四阶段实现；完整游戏与正式美术、声音由第五阶段实现；实机和便携产品验收由第六阶段完成。原型仅用于设计验证，不计为产品功能已实现或 AC 验收通过。

继续采用已确认的本机 Windows 11 x64、React／TypeScript 与独立本地服务方案，不重新选择技术栈。公共屏横屏、手机竖屏优先，默认简体中文；服务端权威、秘密信息隔离、房主决策点回退、真人无默认超时和掉线不代操作均为既定约束。

新增基础人机要求见 [人机规格](../reference/bot-players.md)，适度面向对象封装见 [工程结构](../reference/architecture.md#面向对象与适度封装)。本阶段补规格、逐决策策略覆盖及工程交接，不实现 bot；既有原型、10 组走查和规则来源不证明新增要求已完成。

### 基本流程

随机洗牌，按采用的起始座位顺时针逐人一张、循环六次，形成每人两行三列。剩余牌为牌库，弃牌堆为空，不额外翻一张。每人手机选择一张初始明牌，禁止偷看其余五张；全员完成后进入普通回合。出处：S12、S13、S16。

行动者选择牌库顶或非空弃牌堆顶。普通牌从牌库摸到可替换己方明／暗牌或直接弃掉，从弃牌堆摸到则必须替换。换入朝上；换出暗牌先翻开，普通弃牌放顶。直接弃牌不要求翻己方暗牌。三种强制牌不能走普通直接弃牌分支，改按下节逐牌效果；可选牌只有新摸到并换入后才提供能力选择。出处：S13 至 S16。

弃牌正面朝上，手机只显示顶牌，合并主机可展开全部弃牌。喷火龙的查看仅授予行动者本人，结束后清除临时显示，牌仍在原位朝下；房主普通模式无额外暗牌信息。完整中间步骤的投影仍需逐字段整理。出处：S13 至 S15。

普通操作完成或当前特殊能力完全结算后，若任意玩家六张全部朝上，直接进入小局最终结算，不执行其他玩家最后回合。所有传牌、补位、可选发动／不发动及查看确认先完成，计分时场地各六张、无暂持牌或待处理选择；翻开剩余暗牌、解析百变怪、同列配对再加总，无额外奖励／惩罚。最低分玩家各加一胜，默认先赢三小局，同时达标为共同整局赢家；未达阈值时从本局赢家随机一人开下一局并保存结果。出处：S13、S15 至 S17、S19；确定化处理见 P01、P02、P06、P07。

能力处理中不提前揭示全部暗牌、不关闭剩余选择、不推进下一正常回合。闪电鸟必须完成所有接牌选位和最后弃底；火箭队皮卡丘面必须补齐所有位置；梦幻必须完成两次替换；可选能力须完成发动结果或不发动选择（无暗牌的喷火龙自动跳过）。每个中间决策仍可保存、回退和重启恢复，恢复后继续同一能力，不能仅因中间某人全明就结算。全部完成再检查结束；结算揭示不触发能力。出处：S19、P01、P02、P05、P08。

项目采用 2–5 人，依据 S07、S11 中文介绍及 56 张容量；时长仅是社区估计，不产生自动超时。配对比较有效分值，不比较角色名称或美术；完整实体组件原文和版次仍待认证。

### 未明示细节的项目方案

S19 授权先检索中文规则、未取得依据时自行选定方案，不再追问。S20 没有给出下列完整边界；以下 P01 至 P08 为本项目采用的数字化约定及已有规则的确定化解释，不标为官方原文。它们关闭玩法选择，后续仍需状态／权限字段、决策规格和实现验证。

| 编号 | 采用方案 | 理由与适用范围 |
| --- | --- | --- |
| P01 结束优先级 | 普通操作完成，或当前能力全部完成（包括可选能力的发动／不发动、查看确认）后，检查是否有人六张全明；满足则揭示并计分，否则正常顺时针推进。没有其他玩家最后回合 | S19 改变能力结算优先级；沿用 S18 的直接最终结算，其余回合不追加。临时查看不改变暗牌朝向 |
| P02 有效结算状态 | 每位玩家有完整六张，所有传牌和补位完成、无暂持牌和待处理选择，才允许规则计分。异常空位／实例重复属于状态损坏，停止推进并走恢复／纠错，不给空位虚构分值 | 火箭队完整补位、闪电鸟最后弃底后不再产生 Q25 的合法终局空位；保留 56 张实例守恒 |
| P03 弃底与补位顺序 | 弃牌序列按底到顶保存；每次“放底”插到现有序列最底。火箭队皮卡丘面先放行动者选出的牌、再放新摸火箭队、然后顺时针逐人放同位置牌；全部移出后，从行动者起顺时针各摸一张朝上补位 | S14 图示规定弃底、S17 要求按真实操作先后。明确同一批弃牌顺序，避免恢复或检视时重排；新摸火箭队已从来源堆取出，不重复计入 |
| P04 随机与新小局 | 初始及每个新小局重洗全部 56 张，重新发牌／各翻一张，弃牌仍为空；胜局数和座位保留。火箭队两面等概率，洗牌采用均匀随机算法；随机首位从候选者等概率选取。所有结果和随机状态由服务端保存 | 用户已有随机洗牌、赢家起始及三胜要求；新小局复用初始化。公平随机是项目方案，时间戳仅用于首次随机源初始化，重连不重新抽取 |
| P05 无目标与不连锁 | 喷火龙无己方暗牌时自动跳过查看并记录无目标；有目标可发动或不发动。卡比兽选择不同两格或不发动。梦幻目标仅其他玩家，由行动者完成两次选位；传递牌、补牌和结算揭示均不触发主动能力 | S14 至 S17；2–5 人完整场地下强制三牌均有合法目标，不增加跳过／抢换动作。无目标查看不阻止能力完成 |
| P06 百变怪确定解 | 左右指同一行紧邻位置，不跨行或环绕；可沿另一个百变怪解析到真实固定数值牌，纯循环无数字锚点的赋值无效。联合枚举合法组合，先比较含配对的全场地总分；同分按行优先、从左到右的解析值序列升序，再按复制方向左优先右，选固定展示解 | S14 左右、S16 全场地联合最低分、S17 仅两张；完整三格行始终有数字源。同分确定展示不改变得分，不生成随机结果 |
| P07 计分与胜局 | 解析全部百变怪，再逐列比较有效数值；相等两张都计 0（负值同样适用），否则相加，不加奖励／惩罚。小局最低分所有人各加一胜，任意人到三胜结束大局，同时达标为共同整局赢家 | S13、S16、S17；能力牌的固定数值同样参与配对，角色名称不影响比较。未达三胜才生成下局起始赢家 |
| P08 中间恢复 | 能力完整结算是结束判定边界，不要求把多人的选择合成一次不可回退操作。保存当前回合行动者、能力类型与步骤、暂持牌、已选目标、传递／补位进度、硬币结果和牌序；恢复中间选择后继续同一能力，全部完成才查结束 | 延续平台决策点回退；一次选位与其确定性移牌／公开／自动推进共同保存，下一选择另有边界。身份连接不回退，旧分支选择失效，随机结果不重抽 |

主机和普通手机仅获得当前授权信息：公开新摸牌、场地明牌、硬币及进度；暗牌保持背面，喷火龙查看值只向行动者临时下发。安全历史可写“选择梦幻目标”“接收传牌选位”“火箭队补位完成”等，不把暗牌值写入标签。查看确认／同步清理时清除临时显示，回退仍提示已经看到的信息无法从记忆撤回。游戏计分保持独立纯模块；本轮不修改正式协议、SDK 或游戏源码。

采用规则修订以 S19 标识，正式接入时写入规则／状态版本；旧 S18 中断规则形成的终局快照不能静默按新规则加载。版本不兼容时保留原文件并拒绝恢复；只有具备完整状态与历史、经过独立迁移验证后才允许转换，不凭空补牌或重新生成随机结果。

数字化对局使用 56 张卡牌实例、一个两面随机币结果和每个座位的胜局计数；币面与胜局以状态及 UI 表示，不依赖未知数量的实体标记物。卡牌正式名称、盒内其他实物和印次继续作为出版资料核验事项，不能以这些事实未知推导额外动作或得分。

## 任务一：核验版本、规则与卡牌数据

- 确认对应版本的出版信息、语言、规则版本与适用勘误，取得可复查的完整规则原文；优先采用对应版本出版方规则、勘误及出版方上传资料，第三方介绍用于交叉核对。
- 建立来源记录：来源名称、链接或本地资料路径、语言与版本、获取日期、适用章节／页码、文件哈希、可信程度及核验状态。原始资料保留，区分原文、提取数据与研究结论；扫描件检查全部页与可读性，提取数据回查图片。
- 整理人数、组件、准备与初始布局、合法查看、全部行动及目标限制、阶段推进、特殊效果、回合／整局结束、计分和平局。规则条目关联具体来源；机制依据使用已核验来源、用户裁定或 S19 授权的明确项目方案，三者分别标识。
- 建立完整卡牌与组件的可机器读取结构化文件，记录稳定标识、名称、数量、数值、能力原文位置及数字化解释，附数量一致性核验结果；区分类别、对局中单张实例和资源标识。字段及文件格式按取得的原文确定，不预先创建空游戏工程。
- 若使用普通 Paper Safari 或其他主题版本作参考，明确哪些内容可比、哪些差异已证实、哪些仍无法确认；不直接沿用未经证明一致的数值与能力。
- 对来源冲突、缺失条目和歧义记录问题、影响范围、解决依据及最终结论，保证后续可以追溯采用理由。

交付：对应版本来源清单、规则规格、卡牌／组件数据及已处理的差异与争议记录。

## 任务二：定义信息权限、状态与决策点回退

- 按已核验流程列出阶段、行动者、合法动作、参数与目标、动作结果、自动推进及待处理选择；区分游戏规则、平台管理动作和仅影响本地界面的操作。
- 建立逐项信息矩阵：服务端完整状态、公共屏、本人、其他玩家及房主分别可知什么、何时获知。卡背与未知位置、临时查看结果、公开操作记录和错误提示均纳入；房主管理权不额外授予其他玩家的秘密信息。
- 对每项合法且改变权威状态的玩家决策，定义决策前后的状态边界、历史标签、待处理选择和恢复后可执行动作。复合操作是否拆分、原子动作包含哪些步骤，必须依据核验后的规则说明；翻页、缩放和打开帮助不记录为游戏决策点。
- 标记信息揭示与随机节点，说明需要保存的牌堆顺序、随机状态及已生成结果，恢复后哪些结果应保持相同。回退提示说明玩家可能已经看到信息；不新增全员同意条件，不因信息已揭示而一律禁止回退，不悄悄重新随机。
- 列出可序列化的游戏状态、恢复所需字段及一致性条件。区分随游戏恢复的数据与不倒退的身份、授权、连接信息；修订号／分支号递增，旧分支动作、选择与动画失效。
- 明确哪些内容可进入公共历史、玩家视图和房主管理记录，哪些仅留服务端 checkpoint；完整秘密状态不能用于前端草图数据或公开回退标签。

- 将 bot 纳入逐座位授权矩阵和状态边界：只传对应玩家视图与合法选择，明确策略记忆／随机数据的存档、版本和分支失效要求，不把进程内策略与服务端全状态混为一体。

交付：状态与流程表、信息权限矩阵、决策点清单、恢复字段和揭示／随机回退规格，含电脑策略授权与恢复边界。这里只定义行为和边界，不实现动作队列或存档机制。

## 任务三：设计公共屏、手机与房主管理交互

- 形成从启动、选择局域网地址、创建房间、扫码加入、入座与准备，到开局、行动、等待和结算的流程。人数及游戏准备条件使用已核验规则；本次已选重名提示、关闭新加入、开局前座位调整及房主确认换手机绑定，其他未选便利项不自动升级为必须要求。
- 设计房主添加／移除电脑、人数合计、电脑标识、准备流程和行动反馈；电脑初始翻牌等规则选择也由策略完成，真人掉线不自动变为 bot。中途加入／接管只有游戏明示允许时才设计，不默认开放。
- 为首版游戏分别设计公共屏与手机草图：公共屏突出公共布局、阶段、当前行动者和结果；手机突出本人信息、合法动作、目标选择和允许查询的公共信息。牌面和卡位按核验规则组织，避免将大屏布局直接缩小作为手机方案。
- 按[需求第 9.5 节](../requirements/TableMax_需求文档_v1.0.md#95-操作动效)设计简单操作动效，覆盖适用的选择、翻牌、组件移动、状态切换与结算呈现；记录触发条件、结束状态和过渡节奏，使动效协调、自然、美观，与游戏主题一致，不遮挡信息或妨碍操作。具体游戏效果以已核验玩法为依据。
- 区分房主管理界面与房主作为玩家时的私人界面，覆盖开局、暂停、恢复、座位管理、结束及决策点选择；公共屏和加入二维码不得暴露房主凭证。
- 覆盖提交前、提交中、保存后确认、拒绝／失败及需重新同步的反馈。重复点击、过期动作、旧分支和重连后旧选择有可理解的处理方式，界面动画不能被当作服务端成功确认。
- 补齐掉线等待、锁屏／切换 App／刷新重连、暂停、回退后清空旧选择、重启恢复及不兼容／损坏存档提示。当前行动玩家掉线不自动代操作；恢复失败保留原存档的产品行为在流程中说明。
- 对局域网无法连接、错误网卡、端口占用、设备隔离、系统浏览器打开，以及关闭公共屏与退出整个程序的不同效果给出说明入口和反馈草图。
- 用现有 Playwright 检查公共屏 1920×1080、手机 360／390 CSS 像素宽度及安全区域，走查文字溢出、触控目标、操作步骤、提交反馈、旧选择清除与各角色的模拟授权展示；运行时不请求外部资源。关键视觉或操作取舍明确后再交给实现阶段，实机验收由第六阶段完成。

交付：完整使用流程、各角色页面／状态清单、公共屏与手机草图及必要的管理草图、操作动效设计与原型动态走查记录。规则尚未明确的部分标注待核验，不能用草图默认值反向确定游戏规则。

## 任务四：盘点本地资源与声音需求

- 按核验后的组件与界面列出封面、卡面、卡背、角色／组件、背景、图标、字体、规则帮助和必要提示音，明确用途、数量、稳定资源标识及对应规则／组件标识。
- 区分可取得资源、需要加工或生成的资源、暂缺资源及占位方案；记录来源链接、取得日期、使用说明和已知使用限制。生成资源计划说明需保留提示词与版本，不把网上可查看等同于可公开分发。
- 将规则文字、数字和关键符号与美术分开排版，保证替换图片不改变游戏规则；资源清单不包含本局隐藏卡位与实际卡牌的映射。
- 按实际动效需要列出可独立移动或翻转的组件素材、卡面／卡背、透明切图及裁切留白要求，交给第五阶段制作；图片制作与界面动效实现分别交接，不把生成静态素材记为动效完成。
- 明确正式资源、字体、脚本、帮助与音频随包本地加载，不依赖运行时 CDN。提示音只由公共屏播放，可静音，需用户手势激活；失败不阻断游戏，刷新、重连和回退同步不重播历史声音。
- 列出第五阶段需要补齐、压缩和视觉核验的资源及检查方法。本阶段完成资源方案和来源盘点，不要求批量生产全部最终美术；影响规则核验的缺失卡牌原文不能当作普通美术待办延期。

交付：资源与来源清单、动效所需素材及制作约束、本地打包要求、声音触发方案及后续制作缺口。

## 任务五：建立验证场景与后续交接

- 基于已核验规则准备典型完整对局、每类合法动作、特殊效果、边界条件、结束／计分／平局场景，注明初始数据、操作步骤、预期状态和规则依据；示例数据不冒充未取得的真实卡牌数据。
- 为每类决策点准备恢复场景，覆盖连续回退、复合操作中间选择、已揭示信息、随机结果一致、旧分支迟到动作及回退后继续游戏和重启恢复。列明各端应看到的授权结果与不得泄露的信息。
- 补齐重复／并发／越权提交、移动端重连、掉线等待、房主同时参与、存档兼容和离线资源等场景，关联需求 AC-02 至 AC-17 中适用条目，并区分规则验证、平台验证和实机验收责任。
- 补充 AC-17 动效场景，通过动态走查检查节奏与过渡是否协调、自然、美观，以及是否遮挡信息或妨碍连续操作；同时覆盖服务确认、拒绝、回退和重新同步时的动画处理，不提前泄露秘密，不播放失效动作。第二阶段验证原型设计，第五阶段验证实际游戏实现，第六阶段验证实机表现；静态截图不能单独证明动效质量。
- 为 bot 的全部选择覆盖、混合人机整局、信息隔离、暂停／回退／重启、旧计算失效、异常及策略替换制定场景，关联 AC-19 至 AC-23；明确规则验证、平台验证和实机责任，策略测试不读取规则未授权信息。
- 根据具体玩法指出当前初始 SDK 需要支持的动作、投影、决策和资源能力，将第三、四、五阶段的接口输入与待处理事项分别列出。只提出有实际依据的需求，不把宝可梦卡位或回合形式硬编码进平台，也不提前实现后续扩展游戏。
- 记录规格走查结果、仍可留给后续阶段的制作事项，以及会阻止实现的关键缺口；验证场景已制定不代表测试已经运行或产品验收通过。原型执行类型、静态、格式与独立构建检查，文档检查引用、相对链接、索引和 diff；构建、截图与走查证据放入 `artifacts/phase-02/`，保持文件树可见。

交付：验证场景清单、需求追踪及第三至五阶段交接事项。
